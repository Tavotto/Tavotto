# Tavotto 1.0 稳定化：退出条件、缺陷分级、post-1.0 backlog

> 建立于 2026-08-21。适用范围：从这一天起到 1.0 发布。
> 与 `docs/RELEASING.md` 的分工——那边是**怎么发**，这里是**什么时候可以发**。

## 0. 这份文档为什么存在

1.0 前的 code review 已经不再主要产出独立 bug，而是同**少数几条不变式**反复
被踩。那时最危险的不是缺陷本身，是节奏：

    Codex 找一个 → 修一个 → push → 等全量 CI → 再找一个

这条路没有终点，因为它优化的是「已发现缺陷数」，而那个数只要还有人看就永远
不是零。所以本阶段换一个目标：

**收敛（convergence），不是架构完美（architectural perfection）。**

具体地说：找出让同类缺陷反复出现的底层不变式，用**结构性测试**和**单一权威
实现**把整类问题一次性钉住；剩下的风险要么修掉，要么**看得见地**留在 backlog
里。1.0 不要求「review 零发现」——那是做不到的目标，追它只会让发布无限推迟。

## 1. 退出条件（必须全部满足）

### 1.1 Code review

- [ ] unresolved **P0** = 0
- [ ] unresolved **P1** = 0
- [ ] unresolved **release-blocking P2** = 0
- [ ] 其余 P2 全部落成 issue，带编号、带判据（不是「以后再说」）

### 1.2 核心正确性（结构性不变式全绿）

看护文件：`tests/test_invariants_engine.py` + `tests/support/engine_invariant_probe.py`

**要在多个 matplotlib 版本上跑**——不变式验的是引擎自己的契约，而**契约的
对手方会随版本变**。本轮的实证：`interpolation` 的 `"auto"` 只在 3.9+ 存在
（3.8.4 上点了报错），`Text._linespacing` 的默认值从 3.11 起变成字符串
`'normal'`（撤销后整块文字挪半像素）——**一条只在旧版本现形、一条只在新版本
现形**，任何单一版本都验不全。PR 档跑锁文件那一版，nightly 的
`compat-version-matrix` 三个 target（minimum / bundled / browser）各再跑一遍。

- [ ] **能力真实** —— 宣称可编辑 → handler 在 → dispatch 得到 → **画面真的变**
- [ ] **逐字还原** —— 改一条 → 撤销 → 像素与 manifest 都逐位回到脚本原样
- [ ] **热态 == 全量重放** —— 含**删除**的 patch 序列（A/B/C/D 四类）
- [ ] **不许静默消失** —— 登记范围内的 artist → elements XOR unsupported(reason)
- [ ] **单一权威** —— family / 能力 / gid 前缀 / 别名目标各只有一处判据

另有既有的四路等价性矩阵（`tests/test_equivalence_matrix.py`）与写回事务
（`tests/test_write_back.py`）——它们比的是几何，不变式比的是像素与全量
manifest，**两者不能互相替代**。

## 2. 缺陷分级（Release Bug Severity Policy）

分级的作用是**决定它挡不挡发布**，不是决定它重不重要。

### P0 —— 必须阻塞

- 数据损坏
- 静默写坏用户源文件
- 安全边界失效
- 项目打不开
- crash / 启动阻塞
- 用户的工作无法恢复

### P1 —— 必须阻塞

- 受支持的 workflow 用不了
- 受支持的 OS / runtime 不工作
- **silent wrong**（界面说成功、实际无效或结果错误）
- undo / replay 错误
- 浏览器与桌面对同一脚本产生**语义分叉**
- release CI 门禁**空转**（报平安的门禁比没有门禁更坏）
- installer / runtime / package 不工作

### P2 —— 分两类

**Release-blocking P2**（仍然要修）：

- silent correctness issue
- 用户会**合理相信**一个错误结果
- capability claim 不真实（宣称可编辑却改不动，或能改却不宣称）
- 常见 matplotlib workflow
- 已公开宣传过的功能不成立

**Backlog P2**（建 issue，不延长当前 PR）：

- 仅开发工具的不便
- 罕见 / 未支持的 artist
- 诊断质量
- 不常见的边界情况
- 不影响用户数据、不影响受支持的 workflow
- **有明确的非静默回退**（用户看得见发生了什么）

> 判 P2 归哪一类，最有用的一问是：**用户会不会拿着一个错的结果继续往下走，
> 而中间没有任何提示？** 会 → release-blocking。

## 3. 新测试的反空门禁纪律

> 一条新的不变式测试，提交之前必须确认：**把对应的修复拿掉，它真的会红。**

这不是要求长期维护一套 mutation testing。是要求每条新增的核心不变式做**一次
手工反证**，并把结论写进 PR：

```
Regression proof:
- 抽掉 X → 用例 Y 失败，失败信息是 ...
```

要挡的是这种情形：**另一道防线恰好也挡住了这个问题 → 新测试仍然绿 → 我们
误以为这条不变式被覆盖了**。本轮就真撞到过一次：给 `_alias_by_artists` 加过
一道「窄端那族有没有这条 prop」的过滤，拿掉之后**没有任何用例变红**——下游
两条路径早就挡住了。那道过滤于是被删掉，理由写在原处。**读的人会以为它在挡
什么，而它什么都没挡**，这比没有它更坏。

同一条纪律的另一面：**豁免表必须写得出理由，而且要区分「豁免」与「使能」**。

- **豁免**（`_NON_VISUAL_PROPS`）＝ 它本来就不画。全局只有两条。
- **使能**（`_ENABLERS`）＝ 它画在一个当前关着的通道上（花纹画在边色上、
  `facecolor` 要 `fill` 开着）。**这不是豁免**：加上使能项之后画面必须变，
  验不出来照样红。

夹具挡住效果的一律**改夹具**，不加豁免。

## 3.5 一条贯穿整轮的形状：**真正的原样有时是一个「模式」，不是一个值**

本轮修的十几条缺陷里，成因最集中的一类是「getter 回的形状 ≠ setter 吃的
形状」。它的**恶性子类**值得单独写下来，因为它预测得了下一条：

有些属性的「脚本原样」根本不是一个值，而是一个**模式**——getter 会把模式
**解析成**一个当下的具体值，而把那个具体值回灌回去，模式就永久没了。

| 属性 | 原样是什么模式 | 解析成什么 | 回灌具体值的后果 |
|---|---|---|---|
| 文字背景框 | **没有框** | 一个白色的框 | 撤销之后框留下了，`bbox_visible` 再也关不掉 |
| `markerfacecolor` | `'auto'`（跟着线色走） | 当前的 `color` | marker 永久停在当时那个颜色，**再也不跟线色联动** |
| `[xy]lim` | **自动缩放** | 当前的上下限 | 自动缩放关掉且回不来；后面任何触发重新缩放的 prop 让**热态 ≠ 全量重放** |

三条的修法是同一个：getter 回**可回灌**的表示（哨兵 `_NO_BBOX` /
`_AUTOSCALE`，或原始属性 `_markerfacecolor`），显示那一侧继续用解析后的
具体值——**显示与回灌本来就是两个口径**，合成一个才是 bug 的来源。

判断一条属性属不属于这一类，问一句就够：**「脚本没有表态」与「脚本表态成了
当前这个值」，在这个 getter 上分得开吗？** 分不开就要哨兵。

反过来那一半同样要有活样本：显式设过的轴必须还原成**那对数字**，不能被"修好"
成重新打开自动缩放。修一个 bug 造出一个更坏的，是这一类最容易的失手。

看护：`test_undoing_a_background_edit_removes_the_box_it_created`、
`test_same_element_pairs_restore_exactly`、
`test_hot_equals_replay_after_removal[C-autoscale-*]`、
`test_explicit_script_limits_are_not_turned_into_autoscale`。

## 3.5.5 本地跑「跨版本」时，先核实那几个环境**真的是不同版本**

本轮我一直声称不变式套件跨 3.8.4 / 3.10.8 / 3.11.1 三个版本验证过，写进了十几
条提交信息和 PR 描述。**实际只跑了两个**：本地那两个环境（`compat` / `mpl311`）
装的是同一个 matplotlib 3.11.1，我把它当成两条腿用了一整轮。

后来真建了 3.10.8 补跑，结论没变（100 条全过）。但这不影响这条教训成立：

> **声称验过而实际没验，比没验更坏。** 它与「空门禁」是同一个东西，
> 只是长在自己的话里而不是代码里。

CI 那侧没问题：nightly 的 `compat-version-matrix` 三档由
`tests/compat/matrix.json` 解析出来确实是 3.8.4 / 3.11.1 / **3.10.8**（browser
档），覆盖是真的。有缺口的只是本地。

**做法**：跨版本跑之前先 `python -c "import matplotlib; print(matplotlib.__version__)"`
把每个环境打一遍，把版本号连同结果一起记进提交信息——报出来的数字要能追溯到
一次真实的运行。

## 3.6 「抽掉不红」有两种成因，而它们的结论相反

反空门禁纪律（§3）说的是「抽掉修复，确认用例真的红」。它的**逆用**有个陷阱，
本轮踩了一次，代价是一条 P1：

> 写了一版查 `state.pending` 的方向判据 → 抽掉它一条用例都不红 →
> 判定死代码 → 删掉，还在注释里写明了理由。

那段代码不是死的，是**夹具少了一维**：当时所有 lim 用例都只 apply 一次，而
缺陷只在**跨两次 apply** 时出现。一天之后它以 P1 的形式回来了。

**判定死代码之前先问「它当初是为了防什么」，再问「那个场景在夹具里出现过吗」。**
答不上来就别删——把场景补进夹具再判。

同一条纪律的另一面：注释里写「实测过 X」时要写清**实测覆盖的是哪一维**。
本轮有三条缺陷的注释都写着「实测过」，而每句都只对它当时那一维成立：

| 缺陷 | 判据对不对 | 漏掉的那一维 |
|---|---|---|
| lim 方向 | 对 | 同一次 apply 内 ✓ / 跨两次 apply ✗ |
| 色条宿主 | 对 | `mappable.axes` ✓ / 独立 mappable ✗ |
| 色条能力闸 | 对 | 集合侧 ✓ / 色条侧 ✗ |

## 3.7 能力真实是**双向**的，而第一版只写了一半

`test_capability_truthfulness` 走的方向是「宣称了就得改得动」。它结构上抓不到
反过来的那一半——**改得动却没宣称**：不宣称的 prop 根本不会被扫到。

本轮真被这个方向咬了一次（`scatter(facecolors="none")` 拿不到 facecolor，而它
实测涂得出 9235 个请求色像素），而且**抽掉修复一条用例都不红**。补的是
`faces_table` 那种**双向实测表**：判据说给的必须真能改，判据说不给的必须真改不动。

量这类表有两个必须避开的坑，本轮两个都踩了：

* **判据要在动手之前采。** 写在 setter 之后的话，`get_facecolor()` 已经被这次
  设值填上，判据对每一族都回 True——一张恒真的表。与 `stroke_style_table`
  当初「把描边当成没人验的基线」是同一个坑。
* **量「变成请求的值了没有」，不是「像素变没变」，更不是「读回属性」。**
  `contour` 的 `set_facecolor` 改了 34565 个像素，可请求色一个都没有——它只是
  把原本 `none` 的面打开、随后由映射色重画。读回属性同样不算数：没人盖它属性
  的 artist（`LineCollection`）属性永远等于请求值。

## 3.8 不变式套件与四路等价矩阵各有盲区，两套都要跑

本轮有一处修复的第一版判据在**不变式套件里全绿**，被四路等价矩阵
（`s8-alias-mixed-reversed`）抓出来：不变式的夹具里没有「容器广播到成员、且
成员 prop 同名」的组合，而等价矩阵的场景里有柱系列。

反过来的例子也有（§3.5 那几条颜色缺陷，等价矩阵只比几何、看不见）。所以 §13
要求「不变式套件单独跑一遍**再加上**全量」不是冗余，是两把不同的尺。

## 4. Post-1.0 architecture backlog

以下都是**已知的、有据可查的**结构问题。1.0 前刻意不动：用不变式把现有行为
钉住，1.0 之后再重构。**顺序是 test → guard → stabilize → refactor，不是反过来。**

### 4.1 图例重建路径不是幂等的（已知缺陷，P2 backlog）

图例的重建型 prop（`ncol` / `borderpad` / `labelspacing` / `handlelength` /
`entry_order`）撤销之后回不到脚本原样。实测（mpl 3.10.8）：

| 喂给 `_init_legend_box` 的 handles | 结果 |
|---|---|
| `leg.legend_handles` | 误差棒那条图例的 handle 从 `LineCollection` 退化成 `Line2D`（图例上的误差棒示意消失，393 px），**包围盒一个像素没动** |
| `ax.get_legend_handles_labels()`（原始容器） | 幂等（连做三次结果不变），但**第一次就把图例盒撑高 21px** |

两条路都回不去，说明这不是「喂错了 handles」，是 `_init_legend_box` 本身复现
不出 `Legend.__init__` 当初那次布局。

**为什么今天只算 P2**：撤销之后 manifest **一个字节不变**，所以它不污染写回
自检、不让四路等价矩阵报假分歧；而写回落盘的是全新 worker 重放出来的那份
（＝脚本原样），方向是安全的——跑偏的是用户屏幕上那份。但「所见 == 所写」
这条不变式确实破了。

**真修法**：撤销时还原保存下来的 `_legend_box`，并把这五条 prop 建模成互相
覆盖的一组（复用 `ALIAS_GROUPS` / `dirty_groups` 那套机制）。那是一次图例
重建路径的改造，风险不适合放在稳定化期。

**边界看护**：`test_legend_rebuild_drift_stays_where_it_is` 钉死三件事——
只许留在图例里、只许改像素不许改 manifest、不许是复利的。它一旦扩大就会红。

### 4.2 alias / originals / dirty group / replay 的建模

现在这套机制（广播 prop 代采「脚本原样」、`dirty_groups` 强制重放、
`alias_seeded` 回收）能工作，但它是**按 prop 名手写的一张表**。更彻底的形态
可能是：

- `property setter target graph`（每条 prop 声明它写哪批 artist），或
- `artist identity overlap graph`（哪些 gid 指着同一个对象）

**1.0 前明确禁止重写**。已经有大量行为依赖它，而不变式 3（含删除的
HOT == REPLAY）现在能覆盖它的核心语义——先钉住，再谈换。

### 4.3 `honours_stroke_style` 仍然是按类名写的例外

`QuadMesh` / `TriMesh` 交给 `renderer.draw_quad_mesh` /
`draw_gouraud_triangles`，那两个渲染原语不接花纹与虚线。matplotlib 没有公开
谓词，而 `draw` 被 `@allow_rasterization` 包过、按字节码反查拿到的是包装器的
code（试过了）。

暂时保留 isinstance，但**每次跑都重新渲染核对**
（`test_the_mesh_stroke_style_table_still_holds`）。matplotlib 哪天补上，
那条用例会红——例外不会悄悄过期。这是本轮从 `Arc` 那条错误结论学到的：
问题不在于用了 isinstance，在于那条例外**从没被复测过**，而它的原始测量
不是同类对比。

### 4.4 CompatBench 的分类是**声明**出来的，报不出「变好了」

`classify()` 的返回值来自 `manifest.json` 里那条 case 自己写的
`classification`。所有阶段都绿 + 声明 `partial_support` → 结果仍然是
`partial_support`，连同那条**可能早已过时**的 `reason` 一起原样进报告。

本轮撞到两次：

* 四条网格 case（`art_hexbin` / `art_pcolor` / `art_pcolormesh` / `art_hist2d`）
  的 reason 还写着「Tavotto 不认这个 artist，那块网格选不中」——而 PR #48 的
  Collection family 加上本轮 `_collection_bbox` 的数据范围判据之后，四条的
  `recognized` 已经等于 `total`。实测（3.11.1 与 3.8.4 逐条一致）之后改成
  `full_support`，并补上 `roles_present` / `editable` / `mutations` 把这份支持
  **锁住**——只改声明不加断言，等于把一句旧话换成一句新话。
* `art_stem` 反过来：PR #48 把茎容器化之后，corpus 里那条
  `axes_0.linecoll_0` 的期望不再成立，case 从 `full_support` 掉成
  `product_bug`。而它 `smoke: false`，**PR 档的 compat-smoke 看不见它**——
  要等合进 main 跑 `--gate main` 才会红。

两条都指向同一件事：**声明式的边界会过时，而报告不会告诉你**。想做的话，
runner 可以在「所有阶段都绿、却声明成非 full_support」时打一条 notice
（不是失败——声明可能有阶段之外的理由），让过时的声明有机会被看见。1.0 前
不动 runner，先把这轮发现的五条声明改对。

**改了 artist 登记模型的 PR，合并前请本地跑一次 `--all`**：smoke 是 20 多条，
corpus 是 150+，而「哪一条 case 会被这次改动打到」不是 smoke 选集能预判的。
`art_stem` 已经加进 smoke——容器里只有它的成员**横跨两条 artist 列表**
（markerline 在 `ax.lines`、stemlines 在 `ax.collections`）并且带着两个旧 gid
别名，是这一族里结构最特别的一条，值得进 PR 档。

### 4.5 把「按对扫」的 harness 收进仓库（**最值得做的一条**）

本轮四条 P1（`fill`→`facecolor`、`color`→`marker*color`、`scale`/`invert`→`lim`）
是并行会话用一个**枚举排列的 sweep harness** 扫出来的：给它一个图构造器和
一组 prop，它跑遍所有顺序，apply → 全量撤销 → 比 manifest **与像素**，并检查
这次 apply 是否非空转。我们自己的不变式扫描一次只改**一条** prop，所以这一
整类它一条都逮不到——那是结构性缺口，不是运气。

已经补了 `test_same_element_pairs_restore_exactly`（手写的最小对表），但手写表
「只和写它的人那天的想象力一样好」。真正的做法是**从 `HANDLERS` 自动枚举**，
新加一条 prop 当天就被覆盖，不靠谁记得。

对方量过预算，不是估的：**3712 组同族有序对**（axes 1806、text 600、
legend/ticks 各 210、collection 182…），单次 apply→undo→两次渲染→比字段约
**16 ms**，单进程穷举 ≈ **1 分钟**。真实成本会是它的几倍（色条翻转、3D 与
图例重建远比改个线色贵，而且每族要一张真含那种 artist 的图），即便 3–4 倍
也是几分钟——**够得上 PR 档**，穷举放 nightly、每族取代表放 PR。

**harness 已经留在** `/Volumes/Projects/tavotto-sweep-harness/`（27 个文件、
112K，普通目录，**不是 git 仓库、不在本仓库里**）：`sweep.py` 是引擎，
`cases_a..e.py` 是那 31 组，`prototypes/` 是逐条缺陷的复现与修法原型。
路径处理已经改成相对 `__file__` + `TAVOTTO_ENGINE` / `TAVOTTO_SRC` /
`TAVOTTO_WORKER_PYTHON` 三个环境变量，所以本 worktree 消失之后它照样跑得起来。
接手的人**从这份开始，别重写**。

### 4.6 Collection 能力表的剩余同族 case（**1.0 前不再逐个修**）

本轮在 Collection 族上按同一个形状连着修了四条——「宣称了、设得进去、画面
纹丝不动」：

| artist | 不认的能力 | 实测（像素） |
|---|---|---|
| 映射的 Collection | `facecolor`（面在映射时） | 0，且 `edgecolor` 会**永久杀掉** cmap |
| `QuadMesh` / `TriMesh` | `hatch` / `linestyle` | 各 0（`PolyQuadMesh` 是 10692 / 1100） |
| `TriMesh` | `edgecolor` / `linewidth` | 各 0（`QuadMesh` 是 4086 / 8010） |
| `contour` / 非映射 `LineCollection` | `hatch`（没有面） | `get_facecolor()` 长度 0 |

**剩余面是可以量的，不是「还有一些」**：`matplotlib.collections` 有 **14 个**
Collection 子类，Collection 族对外开放 **14 条** prop——笛卡尔积 **196 格**。
`test_the_mesh_stroke_style_table_still_holds` 那张复测表现在覆盖 **6 类 ×
3 条能力**。剩下的多数格子是显然成立的（`alpha` / `visible` / `zorder` 由
draw 的公共机制兑现），但**没有逐格实测过**。

**1.0 前不再逐个补**，理由是这一族已经不再产出新的缺陷**类别**，只产出同一
类别的边缘实例，而那一类的结构性看护已经就位：

  * 能力真实那条扫的是**这张图上宣称的每一条 prop**，改一条就比一次像素；
  * 网格实测表**每次跑都重新渲染**，例外不会悄悄过期；
  * 判据一律按运行时实况（`collection_caps` 读 getter 实况、
    `color_mapping_is_live` 照抄 matplotlib 自己的规则），而不是类名白名单
    ——`honours_stroke` / `honours_stroke_style` 两条按类名的例外是仅有的
    两处，各自都有复测。

**1.0 之后**由 §4.5 那个「按对扫」的 harness 顺着 `HANDLERS` 自动枚举来收
——它枚举的正是这个笛卡尔积，而且是**从代码枚举、不靠谁记得**。在那之前，
新增单条例外的门槛与 CompatBench 一致：**先拿出同类对比的测量**
（见 §18.2 那次把 `Arc` 判反了的教训），并且例外要带一条每次重新渲染的复测。

### 4.8 多宿主色条只记第一个宿主（**既有行为**，1.0 已 guard，架构修复排 v1.1）

`fig.colorbar(im, ax=[ax1, ax2])` 的色条在视觉上横跨两个子图，而我们记的宿主
只有一个——`mappable.axes` 回的是拥有这个 mappable 的那一个（`ax1`）。翻转
方向时 `_cb_target_rect()` 只拿得到 `ax1` 的范围，于是本该跨两图的色条被缩到
一图宽。

实测（mpl 3.10.8 / 3.11.1，`subplots(1, 2)` + `ax=[a1, a2]`，翻成横向）：

    a1 的 x 跨度  (0.125, 0.407)
    a2 的 x 跨度  (0.463, 0.745)
    翻转后色条    x0=0.125  宽 0.282     ← 只跨 a1
    应当          x0=0.125  宽 0.620     ← 跨两图

`ax2` 也不在 `axes_follow` 里（拖动它色条不跟着走）。

**为什么是 backlog 而不是 release-blocking**：

* **这是既有行为，不是本轮引入的**。常规 mappable 与独立 mappable
  （`_colorbar_info["parents"][0]` 那条回退）**实测表现完全相同**——
  取第一个宿主这件事从来如此，新增的回退只是照着做。
* **不静默**：色条肉眼可见地缩到了一边，用户看得见发生了什么，也能用
  position override 自己摆回去。与「色标换了色而数据没动」那类不是一回事。
* 真修法要把宿主从**一个 axes** 改成**一组 axes**，`_cb_place` /
  `_cb_target_rect` / `axes_follow` 三处都要按并集算——那是色条落位模型的
  改动，不适合放在稳定化期（与 §4.1 图例重建同一条理由）。

触发条件要写清楚：**多宿主 + 翻转方向**。只是多宿主、不翻方向的话，落位归
matplotlib 自己的 `_ColorbarAxesLocator` 管，一切正常。

**1.0 的 guard（2026-08-22 落地，issue #69）**：按
`docs/engineering/review-severity-policy.md` §3 的标准顺序
`detect → guard/hide → unsupported reason → issue → v1.1 fix`：

* **detect**：`overrides.colorbar_host_count(cb)` —— 判据是 matplotlib 自己记的
  `cax._colorbar_info["parents"]` 的长度。**唯一实现**，manifest 与 setter
  共用（六种建法在 3.10.8 上逐个量过，`cax=` 那条没有 `_colorbar_info` → 按 1 算，
  而那是对的：用户自己摆好了位置，落位本来就不归我们算）。
* **guard**：多宿主时**不宣称** `orientation` 能力。
  一个「点了就把图排版弄坏」的控件，比一个不存在的控件糟糕得多。
* **reason**：manifest 的元素上多一个可选的
  `unsupported_props: [{"prop": "orientation", "reason": "multi_host_colorbar",
  "detail": {"hosts": N}}]`。reason 是**稳定 code**，供界面按 code 翻译。

  **界面已经在渲染它**（issue #76 已修）：`ManifestElement` 声明了
  `unsupported_props`，`inspector/UnsupportedProps.tsx` 把属性名置灰、下面跟一句
  按 code 翻出来的原因。用户看到的是「这条色条横跨 2 个子图，方向切换在当前版本
  不支持」，而不是「方向开关就是没有了」。不认识的 reason code 走通用兜底，
  **绝不把 code 本身透传到界面**。看护：`unsupportedProps.test.tsx` 四条
  （原因真渲染出来、中英各一、未知 code 有兜底、没有该字段时不多出任何东西）。
* **第二个消费点**：`_set_cb_orientation` 同样拦，且**抛异常**（→ warning →
  写回阻断）。manifest 不宣称挡不住一份**旧文档**——1.0 之前存过的 override
  重开时照样会发过来。只修一处等于没修。
* **对照组**：单宿主色条的 orientation **一条都没少**
  （`test_a_single_host_colorbar_still_offers_orientation`）。
  把一个真能力藏起来正是 `Arc` 那次的教训。

看护 `tests/test_colorbar_orientation.py` 末节六条；8 条变异逐条确认变红。

## 5. CompatBench 的边界

CompatBench 是**外部脚本的 acceptance**，不是内部缺陷的垃圾桶。新增 case 的
条件（满足其一）：

- 代表真实用户脚本模式
- 代表一个 matplotlib API family
- 代表受支持的平台 / 运行时契约
- 过去确实发生过 regression
- 能防住一个重要的 silent wrong

如果只是**内部某个 restore 实现的 bug**，它该落在 unit / invariant contract
test 里。本轮扫出的三条能力真实缺陷一条都没往 corpus 里塞——它们全部落在
`tests/test_invariants_engine.py`。

两套 corpus（`tests/acceptance/` 与 `tests/compat/`）**不许合并**：合了就再也
分不清「我们退步了」和「我们本来就不支持」。
