# 第三路径审查（Third-Path Review）：提出取舍之前先找结构

> 根 `AGENTS.md`「第三路径审查」一节的全文（2026-10-20 立）。根文件只留触发条件与本文链接；
> 这里是唯一出处。PR 记录的结构由 `scripts/dev/third_path_review.py` 校验（本地，不进 CI），
> 看护 `tests/test_third_path_review.py`。

**最高原则：当几个方案都要牺牲一项合理的核心能力时，先怀疑问题的分解方式，而不是先让维护者
选牺牲哪一个。** 先确定有没有结构性的第三条路，再判断是不是真的要取舍。

这条纪律来自本仓库自己的两次「换了分解方式，冲突就不在了」：

| 起初的取舍 | 冲突根因 | 第三路径 |
| --- | --- | --- |
| 持久 TightLayoutEngine 吃掉子图位置 override → 禁用子图拖动（#140） | 布局引擎与用户编辑**争同一份状态**（axes position） | `PinnedTightLayoutEngine`：钉住被用户改过的子图、其余照常自动布局（ADR 0042，#162 / PR #262） |
| 插件判 pip 镜像：不断复刻 pip 的配置发现，每修一处冒出下一处 | Tavotto **复刻了外部系统的规则**，两份规则必然漂移 | 直接问 pip（`pip config list`），问不到报 unknown 不猜（#737 / PR #767） |

两次的共同点：争论停在「A 还是 B」时，A 与 B 共享同一个错误前提；去掉前提，两个目标同时成立。

## 一、什么时候必须做

方案或结论里出现下面任一形状，动手（或把选项交给维护者）之前先做本审查：

1. 用禁用、隐藏、置灰某项功能来解决兼容问题。
2. 让用户在两个都有明显缺陷的方案之间选。
3. 降低精度、质量、验证能力或保真度换性能。
4. 缩减用户原本拥有的数据、历史或编辑能力。
5. 把错误改成警告、失败改成提示，或只改文档来结束 issue。
6. 继续加白名单、黑名单、特殊分支或只针对单个案例的补丁。
7. 同一类问题修过两轮以上，仍不断冒出新边界。
8. 两个模块对同一事实给出不同结论。
9. 为兼容外部系统，Tavotto 在复刻那个系统自己的规则。
10. 解决方式要求用户改变原本合理的工作流程。
11. 方案只是把错误提前暴露，而没有恢复原有能力。
12. 某个临时限制正在被当成永久的产品行为。

**不触发**：普通的确定性 bug（判据写错、漏一个分支、类型 / 编码 / 路径错）直接修，不写本审查、
不开 ADR。触发与否看方案的**形状**，不看改动大小。

## 二、怎么做（A–F）

**A. 写出用户要保持的不变量。** 以用户目标为中心，不以现有实现为中心：「用户能拖动子图，同时
未改过的子图继续自动布局」，而不是「TightLayout 下何时禁用 position 控件」。

**B. 把目标与约束分开。** 逐项标出：产品目标 / 科学正确性 / 安全要求 / 外部系统的真实限制 /
仓库历史决策 / 当前实现偶然形成的约束。历史决策不等于技术事实；但推翻 Accepted ADR 要有证据与
兼容迁移方案，写进新 ADR 或修订。

**C. 找冲突的根因。** 对照这张清单问一遍，并写出现有各方案的**共同前提**：

- 两个模块在争同一份状态的控制权？
- 同一事实有多个来源分别判定（前端按后缀猜、后端按计划算）？
- 缺来源身份、快照或版本边界（「这份文件是哪一次保存的」）？
- 验证发生在错误的时刻？
- 显示能力与编辑能力被混成一个条件？
- 任务的生命周期与前端连接 / 某个进程的内存耦合？
- 复刻了外部程序的语义？
- 让静态分析承担运行时安全职责？
- 用了不适合被验对象的度量？

**D. 至少提出一个跳出既有选项集合的候选。** 方向举例：统一权威来源、版本化来源快照、分离职责或
状态、生命周期解耦、可恢复任务、事务与持久化协议、权限与执行分离、更准确的表示层、复用底层库的
原生能力、把全局限制改成针对性的能力判定、在正确的时刻捕获原始证据。**第三路径不是把 A 与 B
拼起来**：它要说清为什么消除了 A、B 共同面对的那个冲突。

**E. 反证与实验，不靠推理宣布更好。** 至少有：一份最小复现；一条能杀死原有错误实现的用例（拿掉
修复 → 红，按退出码，规则见 `docs/rules/repo/predicate-subject.md`）；一次对候选关键假设的实验；
一张回归风险清单。较大的架构改造要两个独立视角：一方提出方案，另一方专门找它兑现不了承诺的反例。
找不到更好的方案时，报告**已实测排除**的方向与证据——「实现复杂」「风险太高」不是证据。

**F. 给结论**（审查记录用的结论档；与产品运行时的 `rendercore.inspector.VERDICTS` 等状态无关，
不要混用）：

| 结论 | 含义 |
| --- | --- |
| `structural_solution_found` | 找到并验证了更高层的方案，原来的两个目标同时保留 |
| `promising_unverified` | 有明确的第三路径，但关键实验还没做；写出缺哪一个实验 |
| `necessary_tradeoff` | 目标确实不可兼得（数学 / 安全边界 / 已证实的技术限制），附证据 |
| `temporary_mitigation` | 暂时缓解，核心用户目标未实现；必须挂一个跟踪根因的 issue |
| `not_applicable` | 普通局部修复，不涉及架构性妥协 |

## 三、第三路径不是什么

不能以第三路径之名：牺牲安全、权限或科学数据正确性；静默降低验证标准；伪造原件一致性或可编辑性；
绕过代码审查或 `docs/ci/pr-review-tiers.md` 的分档与评审预算；重新实现仓库已有的权威系统（第二套
导出管线、第二个任务库、第二棵 Figure 对象树）；用大量新抽象替换已经稳定、可验证的简单实现；用
无法证实的架构理想取代实验数据。

**也不是 1.0 收敛纪律的例外。** 结构性恢复既有能力、correctness / safety / compatibility 修复、
默认行为不变的新协议，按标准流程走；新增用户可见能力仍要 feature flag、ADR 与维护者在
`docs/1.0-release-readiness.md` 意义下的批准——审查结论替代不了这份批准，也不得替维护者写「已批准」。

**也不是拖延。** 有明确可行的安全止血就先交付止血（结论 `temporary_mitigation`），根因另开跟踪；
不要用一个未验证的大架构挡住当下需要的修复。允许阶段性交付，**不允许把阶段性交付写成最终解决**。

真正不可兼得时：写出不能同时成立的条件、为什么不存在满足全部条件的方案、最小损失的建议——维护者
只裁决真正的政策或产品取舍，不替作者做本该完成的技术研究。

## 四、PR 里怎么记

触发了本审查的 PR，在正文加一节 `## Third-Path Review`（模板 `.github/PULL_REQUEST_TEMPLATE.md`
里有；不触发的整节删掉），逐行填：

```text
## Third-Path Review

- 结论：<五档之一>
- 用户目标：<最终希望用户能做什么>
- 现有冲突：<为什么现有方案必须牺牲某项能力>
- 共同前提：<现有各选项共享的那个架构前提>
- 第三路径候选：<研究过的结构性替代，含被实测排除的>
- 证据：<复现 / 反证用例 / 实验，标明证据等级>
- 最终决定：<为什么选这个>
- 遗留限制：<仍未实现的目标与退出条件；没有写「无」>
- 跟踪：#<根因 issue>（temporary_mitigation / promising_unverified 必填）
```

证据等级照实写：代码推断 / 本地最小复现 / 真实集成 / 跨平台 CI / 真机 / 尚未验证。不得把推理或
模拟写成真实场景已通过。

**临时缓解不关闭根问题。** 结论是 `temporary_mitigation` 的 PR，正文里单独写一行
`Temporary mitigation — root problem unresolved`，用 `Refs #N` 引用根 issue，**不写**
`Fixes` / `Closes` / `Resolves #N`（GitHub 合并时会自动关掉它）；`promising_unverified` 同理。
合并一个缓解 PR 不是「用户的问题已经解决」的证据。

## 五、Issue 的完成语义

关闭 issue 时在关闭评论里写明属于哪一类（GitHub 的原生状态不必改）：

- **根本解决**：原始用户目标已满足，验证通过。
- **结构性改进**：共性根因已解决，仍有已记录的能力边界（边界另有 issue）。
- **临时缓解**：不关闭；或关闭前已开继任的根因 issue 并互相引用。
- **已证实不可行**：附技术、安全或数学证据。
- **不再需要**：需求失效，或被另一项已验证能力覆盖（写出是哪一项）。

已关闭但目标没达成的 issue（例如靠改文档关掉的）：先查有没有继任 issue；没有就开一个根因跟踪
issue，引用此前的修复与遗留缺口。不为状态数字重开历史上关得正确的 PR / issue。

## 六、哪些能机器判、哪些不能

`scripts/dev/third_path_review.py <PR 正文文件>`（或 `--pr N` 经 `gh` 取正文）只判**结构一致性**：

- 有 `## Third-Path Review` 节时，九个字段都在且非空、结论在五档闭集里；
- `temporary_mitigation` / `promising_unverified` 必须有 `#N` 跟踪，且正文没有用关闭关键字
  （Fixes / Closes / Resolves 及其变形）指向任何 issue；`temporary_mitigation` 还要有那行声明；
- `necessary_tradeoff` 的「证据」不能是空话占位。

它**判不了**审查做得好不好——出现几个字段名不证明做过架构思考。语义质量靠作者按 A–F 做、靠评审
人读；这个脚本只防「声明的结论与 PR 的实际效果（会不会自动关 issue）自相矛盾」。不要为它写只看
关键词的门禁，也不要把它接进必需检查（判据的主语是 PR 正文，正文随时可改，见
`docs/rules/repo/predicate-subject.md`「判不出就别判」）。
