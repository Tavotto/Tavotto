- **反空门禁纪律**：新增的核心不变式测试，提交前必须手工反证一次——把修复
  拿掉，确认它真的红，并把结论写进 PR。「读的人会以为它在挡什么，而它什么
  都没挡」比没有更坏。豁免表要写得出理由，并区分「豁免」（本来就不画）与
  「使能」（画在一个关着的通道上，开了就必须变）。反证是**事后**那一半；
  事前那一半（写判据之前先说出主语：谁的、哪个进程、哪个时刻、哪个维度）
  的唯一出处是根 `AGENTS.md` 的「判据的主语」一节。
- **空转的门禁比没有门禁更坏**：nightly 曾对早已退役删除的 `packaging/tavotto.iss`
  报平安；macOS 冒烟曾借 worker-env 让「runtime 没打进去」全绿。判「最近
  跑过没有」要数**有结论的 run**。
- 每个「只在别人电脑上发生」的 bug 先变成 `tests/test_windows_regressions.py`
  的用例再谈修（cp936 编码、文件占用、盘符/反斜杠/中文路径、端口占用、
  CLI 只有 .cmd、解释器探测）。
- **做变异反证的手法（错题本 L-005 升级，2026-11-03）**：变异前工作区必须干净——先把修复提交；
  变异按锚点替换，锚点对不上就报错退出，不用 sed 地址范围；跑用例加 `python -B`（不读旧 `.pyc`），
  结论只认退出码；还原只动被变异的那个文件（修复已提交，还原才不会连带抹掉它），跑完 `git status`
  核工作区与变异前一致。
  为什么：用 `git checkout` 还原变异，把未提交的修复一起抹掉，累计十余次；变异没应用上时的红绿
  也曾被当成门禁有效的证据（#128、#162、#181、#189、#457、#550、#561、#1095、#1118、#1157）。
- **变异后不管绿还是红，都核「该跑的路径真跑了、红的是目标路径」（错题本 L-030 升级，2026-11-05）。** 绿有多种
  成因：分支从没被夹具执行、选择器缩到一条而判据在别的用例里、变异本身是语义 no-op（`set() or 推导式` 仍求值到
  后者）。先排除这些，再谈判据弱，免得去加强本来就好的判据（#181、#187、#189）。
- **推送前跑仓库级扫描用例，不只跑自己改到的那几份（错题本 L-108 升级，2026-11-03）。** 改了
  `scripts/`、新增 subprocess 调用或用例、动了 workflow 时，`grep -l '<改到的文件名>' tests/*.py`
  找出读同一文件的结构判据一起跑，`src/tavotto/` 新增 subprocess 另跑 `tests/test_windows_regressions.py`
  （按结构判，只在 macOS 执行的那行也算）；叠栈 PR 不跑 CI，更要本地跑全。派子代理建这类文件时
  把这几条写进提示。为什么：入口脚本编码扫描、下载步骤闭集、subprocess 未钉 encoding / creationflags
  在五个不同日子各到 CI 才红，各多耗一轮（#1135、#1139、#1280、#1635、#1639、#1641）。
  升级后再犯：#1671、#1702（subprocess 没钉 encoding，只跑了相关用例）。
- **变异杀不死、或抽掉修复不红时，先查夹具，别急着改判据（错题本 L-019 升级，2026-11-05）。** 依次查三处：
  夹具缺维度；对象复用（`mockResolvedValue` 只求值一次，两次响应是同一引用，「不换对象」的断言恒真）；
  同一保证有两份实现（fallback 的两个出处填了同值，判据分辨不出走的是哪条）。造区分性数据要选现实中真会不同的值。
  为什么：四个不同日子（2026-08-21 至 09-04，迁入时未留 PR 号）都是判据没问题、夹具量不到。
- **读 CI 结论按 workflow 最新一轮列全 job，裸名状态不算结论（错题本 L-099 升级，2026-11-05）。** 每一项 SKIPPED 或
  CANCELLED 各写出可验证的理由，别把清单念出来当评估；PR 显示 BLOCKED 时先确认现役那轮跑完，跑完还 BLOCKED 再查原因，别推空提交
  换 head。为什么：裸名状态常来自矩阵父占位或被挤掉的旧 run，两个方向都会骗人（#303、#314、#315、#317、#299、#296、#302）；
  补打 full-ci 让同一 sha 起两轮，被取消那轮留下一批 1 至 2 分钟的红项，曾被误读成卡住（2026-11-04，#1739）。
- **偶发红或无关红先读一层根因，别加等待、标 flaky 或直接重跑（错题本 L-100 升级，2026-11-05）。** 重新入队或重跑前
  写得出「它为什么红」；读不出就记 issue，不能一句「无关」放过。为什么：「偶发」常是断言与缺陷在赛跑——Radix 关闭浮层
  归还焦点又把气泡打开，鼠标点开必现、键盘打开不现，加个 await 能让用例绿，缺陷原样留在产品里（#311、#315）；
  2026-11-02 合并组红在与本 PR 无关的桌面壳握手超时用例（实为 spawn 失败），一分钟内重新入队、没记 issue（#1603）。
  2026-11-11 合并组除两个 Gate 外全是 cancelled，被当成机器故障连排两次；
  快速失败下先红的腿自己也显示 cancelled，Gate summary 的 `root_failures` 早已点名 posix-e2e 里一条钉旧行为的用例，check-run 注解里也有「本腿失败」（#1828）；同日另一 PR 的 summary `root_failures` 为空、被踢四次，要按 completedAt 找最早结束的非 success 腿、看它注解里有没有「本腿失败，merge_group 快速失败」（#1846）。
