> **单一权威原则**（根 `AGENTS.md`）：一条规则只有一个出处。
> 因此本文件里**大部分决策已经是仓库既有 ADR**，这里只写"本轨道怎么用它"
> 并指向权威；只有轨道内新产生的决策才在 `docs/adr/` 新开一份。

> 编号 `T-nn` 只是本文件内的索引，不是 ADR 编号。

## T-01 自动刷新只做静态扫描，绝不运行用户脚本

**权威**：`docs/adr/0014-safe-native-execution-profiles.md`、
`docs/adr/0020-native-matplotlib-bridge.md`、根 `AGENTS.md` 安全边界段。

**背景**：打开项目、autosave、watcher、readiness、问题检查、自动刷新都想
"知道图现在长什么样"，而最直接的做法是跑一遍用户的脚本。

**决定**：这些路径只允许静态扫描、读 AST、合并 registry、算 fingerprint、
校验文档。**执行**（probe / 渲染 / native 会话 / 依赖安装）一律由用户显式触发，
并显示目标环境与结果。

**现状已落实**：`POST /api/registry/probe` 是显式动作；watcher 只比 mtime；
`/api/native/*` 全部要用户批准（`engine/nativeperm.py`）。

**禁止的替代实现**：在 readiness / watcher / 打开项目里"顺手 probe 一下"；
为了拿一个尺寸就跑一次 `main()`。

## T-02 项目文档必须版本化、可迁移、原子写入

**权威**：本轨道新增 → `docs/adr/0023-document-persistence-authority.md`（Prompt 02 落地）。

**背景**：起始 commit 上有 6 处以上各自手写的 "tmp + replace"，其中
`POST /api/layouts/<name>`（用户的"另存为"，最显眼的一次保存）**根本不是原子写**；
没有一处做 fsync，没有一处在失败时清理临时文件，没有一处返回结构化错误。

**决定**：Python 侧只保留**一个**原子写实现，所有文档类写入经它；
文档格式有显式 schema version 与显式 migrator；写入前拒绝非有限数
（NaN / Infinity）。

**后果**：新增写入点必须复用它；`ruff`/测试会挡住第二份实现。

**禁止的替代实现**：在新端点里再抄一遍 tmp+replace；用 `write_text` 直接盖；
用 `json.dumps` 默认参数（它会写出非标准的 `NaN` 字面量，浏览器 `JSON.parse` 解不动）。

## T-03 用户文档与派生元数据严格分离

**权威**：本文件 + `UX_CONTRACTS.md` §3 的所有权表。

**决定**：派生数据（registry 映射、fingerprint、worker id、缓存路径、SSE 状态）
的刷新**不得**把文档标脏，也不得进普通撤销历史。出口只有
`documentStore.silent(recipe)` 一个。

**理由**：一旦派生刷新能置 dirty，autosave 就会在用户什么都没做的时候
写出新的 `updatedAt`，多标签页立刻互撞 `stale_write`（这条路径在
`documentStore.ts:892` 的注释里已经被踩过一次并写进了代码）。

## T-10（Session 03）保存状态是文档的字段，但不是一个大枚举

**权威**：`docs/adr/0024`、`web/src/store/documentStore.ts`。

**决定**：`saveState` 只装保存生命周期的六个值
（`clean` / `dirty` / `saving` / `saved` / `save_error` / `conflict`）。
Prompt 03 §二 与它们并列的 `recovery_available` / `read_only` 走正交的
`docNotice`。

**理由**：它们与保存进度是**两根互不相干的轴**。塞进同一个枚举，两者会互相
顶掉——恢复副本还在本机躺着，一次成功的自动保存把状态推成 `saved`，横幅没了，
副本要等到下次启动才再被想起来（实现过程中真的撞见过这一下）。`read_only`
更明显：schema 太新的那份**根本没有打开**，当前文档是一份能存能改的空白文档。

**与 Prompt 字面不同是有意的**：Prompt 的退出条件是行为（恢复可预览可恢复、
只读不伪装可保存），不是枚举里必须出现那两个字面量。

## T-11（Session 03）判据要把两条边都钉住

**权威**：`app.py::_revision_conflict`、`web/src/lib/api.ts::REVISION_ABSENT`。

**决定**：外部修改检测的基线有 `absent` 哨兵（「我读过，磁盘上没有这份文件」），
且基线缺席时**一律**先 GET 确认一次，没有例外。

**理由**：只挡「hash 对不上」的话，两个标签页同时新建同一份文档时双方都拿不出
hash，后写的整份盖掉先写的——而这正是这条判据要挡的事。同理，「只有读盘失败
时才确认」看着更省一次 GET，但新建 / 载入 / 启动初始文档三种情况一样是两个基线
都没有。**判据留了例外就会从例外那一侧漏。**

反方向也要说清：hash 基线遇上磁盘无文件（被外部删了）**放行**。这条判据挡的是
「覆盖别人的内容」，不是「重建一个被删掉的文件」。两侧不对称是结论，不是疏漏。

---

## T-12（Session 03）「缺席」不许补默认值

**权威**：`web/src/lib/versionTarget.ts`、`app.py::_version_meta`。

**决定**：旧版本检查点没有 `canvasId`，读到的地方**不补**当前画布 id，
也不补空串；它是独立的一档 `unknown`，恢复前必须用户点头。

**理由**：补出来的身份恰好总是「允许直接覆盖」。同一形状在本次还出现两次：
修订号「读到了但没有 hash」不能并进「磁盘上没有」，摘要「读不出来」不能并进
「各项为 0」——每一次图省事的合并，都把一个「不知道」说成了一个具体的断言。

## T-13（Session 04）刷新的编排只有一份，副作用出口靠注入

**权威**：`docs/adr/0025`、`engine/project_refresh.py`、`app.refresh_project()`。

**决定**：registry 合并 / 重载 / diff / worker 失效 / 事件发布的编排只在
`refresh_project_index()` 里；SSE 与 watcher 重挂由 app 层作为 `RefreshSink`
注入。`app.py` 的 `reload_registry()` 删除，三个老调用点全部改走统一入口。

**理由**：改造前这条链路在 `app.py` 里有三份，而它们的**答案不一样**——
三份里没有一份作废过 worker（改了 entry、挪了 stem，热会话手里还是老的），
没有一份说得出"什么变了"，素材根本不在视野里。第四条路径（Prompt 05 的
watcher）照着任意一份再抄一遍，分叉就有四份。

**注入而不是回头 import**：`engine/project_refresh.py` 要能被 Flask 父进程
安全 import（`.venv` 没有 matplotlib），而 SSE / watcher 回调是 app 层的东西。
它连 `engine/documents` 都不 import——"派生刷新不碰文档"因此是结构性的，
不是一条注释。

## T-14（Session 04）恒等成立的 diff 与"没变化"长得一模一样

**权威**：`engine/project_refresh.refresh_project_index()` 里那段注释、
`RefreshState.assets`。

**决定**：素材 diff 与**上一轮的清单**比（基线存在 `RefreshState`，项目打开时
`seed_state()` 落一份），不与同一次调用里的"刷新前快照"比。

**理由**：Prompt 04 §四 的流程写的是"刷新前素材快照 → …… → 刷新后素材快照"。
照着实现，这条 diff **永远是空的**：刷新会改注册表，所以 registry 的前/后有
内容；素材它一个字节都不碰，同一次调用里的两张快照必然逐项相同。

这是"对拍的尺子量不了那个维度"那一族——判据没错，它只是恒等成立，而恒等
成立的 diff **看起来和"什么都没变"一模一样**，没有任何信号提醒你它坏了。
本次是靠一条真的加了图片的用例红出来的（先写用例、后发现设计错）。

**顺带**：没有基线的那一轮报 `assets.baseline=true`，不报"没变化"——第一次
刷新报空比不报还糟，它是一句**错的断言**而不是"我还不知道"（同 T-12）。

## T-15（Session 04）"没跑过"与"跑了没发现"是两档

**权威**：`refresh_project_index()` 的 `registry.conflicts`。

**决定**：没跑静态扫描的那些刷新（probe / 手工登记，`allow_static_merge=False`）
返回 `conflicts=null`；跑了且没有冲突返回 `{}`。

**理由**：合并成 `{}` 的话，调用方会把"不知道"读成"已确认没有冲突"，而
RegistryDialog 正是靠这个字段决定要不要显示冲突区。同一形状 Session 03 已经
踩过三次（T-12），这次在写之前就分开了。

## T-16（Session 04）watcher 认自己写的那一下靠内容，不靠时间窗口

**权威**：`project_refresh.is_self_written()`、`RefreshState.registry_revision`。

**决定**：Prompt 05 的 watcher 用**内容修订号**判"这份注册表我已经消化过"，
不用"写完之后忽略 registry 事件 N 秒"。修订号在**装载成功之后**更新。

**理由**：时间窗口两头都错——慢磁盘上 N 不够，快机器上 N 会吞掉用户真实的
外部修改。内容比较两头都对：用户把文件改回原样 = 内容没变 = 确实不用刷新。

**顺带把源头也堵上**：无变化的刷新**不回写**注册表（按字节比）。以前
`/api/registry/scan` 无条件重写，文件内容一样、mtime 变了——而 mtime 一变，
watcher 就会看到一次"外部修改"，于是刷新自己触发下一次刷新。

## T-17（Session 04）挂不上的桩会让用例恒绿

**权威**：`tests/test_discover.py::test_registry_write_is_atomic`。

**决定**：`discover.write_config()` 并进 `atomicio` 的同时，把那两条看护用例的
故障注入点从 `Path.replace` 挪到 `os.replace`。

**理由**：`atomicio` 调的是 `os.replace`。注入点不挪的话，故障根本打不中，
用例会**恒绿**——而"没红"只说明桩没挂上，不说明失败路径是对的。这次它是以
`DID NOT RAISE` 红出来的（那条用例的注释早就写明了这个红法），换一条形状
（比如只断言"文件没坏"）就会静默变成一条空门禁。

## T-18（评审回合 1）对的判据放错了位置，一样挡不住

**权威**：`app.py::api_autosave_put` 的锁段、`docs/adr/0024` §外部修改检测。

**决定**：自动保存的「读修订号 → 判冲突 → 写 → 读回修订号」整段进锁
（按落盘路径取的固定 64 条锁带，不是 doc_id→锁 的表）。

**理由**：`_revision_conflict` 两条边都钉住了（T-11），但**判完到写完之间没有
互斥**，于是它只在请求串行时成立。两个标签页同时新建同一份文档：双方都在对方
落盘之前读到「磁盘上没有」、双方都判没冲突、后写的整份盖掉先写的，**而两边都
收到 200**——这正是 `absent` 哨兵要挡的那个场景，被交错执行绕了过去。

**这是一族**：T-11 说的是判据的内容要对，这条说的是判据的**位置**要对。
判据与它守护的动作之间只要有一个可以被别人插进来的间隙，判据就退化成
「在没人跟我抢的时候成立」。同一形状还有：交回去的修订号也必须在锁里读，
否则 A 拿到的可能是 B 刚写下的那份的 hash，而 A 的下一次写会带着它当基线
——后端一比「和磁盘一致」就放行，A 于是能静默盖掉 B。

**锁带而不是锁表**：锁表要自己治理生命周期，而「什么时候能删掉一把锁」没有
可靠信号（同 04 的 `RefreshState` 挂在 ctx 上的理由）。固定条数的锁带内存是
常数，不同文档偶尔共用一把只是多串行一点点。

## T-19（评审回合 1）两个 `except` 挡的不是同一件事，就不能同一个处置

**权威**：`engine/atomicio._fsync_dir()`。

**决定**：`os.open` 目录失败（Windows）继续忽略；`os.fsync` 失败只放过
EINVAL/ENOTSUP（确实没有这一步的文件系统），其余抛 `dir_fsync_failed`。

**理由**：以前两个 `except` 都是 `pass`，而它们挡的是两件不同的事——前者是
「这一步在这里不存在」，后者是「这一步失败了」。吞掉后者的后果不是少一次
fsync：调用方收到成功，前端据此把本机兜底副本删掉，用户手上从此只剩一份
可能撑不过掉电的文件。docstring 当时只解释了第一个 `except`，**第二个连
解释都没有**——那正是「被吞掉的 except 让门禁变空」的典型形状。

**反方向也要量**：把 EINVAL 也当成失败的话，那些文件系统上**每一次保存都会
报错**。判据宽过它要守的东西同样是缺陷（同 T-15 的「范围」维度）。

## T-20（评审回合 1）按钮要么做它说的事，要么说清为什么做不到

**权威**：`documentStore.overwriteDisk()`。

**决定**：`saveIssue` 里没有磁盘修订号时（`stale_write` 那条 409 比的是
updatedAt，body 里不带 hash），「覆盖」**去摘要那里补一个真基线**；补不到才
退回删除。

**理由**：不补的话，「覆盖」只是把 `diskRevision` 删掉，而下一次写之前的确认
又会探到一份「我从没读过的文档」→ 原样再弹一次同一个框。用户看到的是一个
点了没反应的按钮（第二次点才成功，因为那时 `saveIssue.disk` 已经换成带
revision 的摘要了）。

**不能改成清空基线**：清空等于此后每一次写都不再校验，按一次「覆盖」把这份
文档的外部修改检测永久关掉。

## T-21（Session 05）判据的主语是「这条路径现在是什么」，不是「那个文件」

**权威**：`engine/project_watch.take_snapshot()` / `_changed_keys()`（ADR 0026 §1–2）。

**决定**：watcher 的判据是**整棵树的快照**（文件集合 + 每个文件的
`(size, mtime_ns)`），不是「按注册表清单逐个 `stat()` 看 mtime 变没变」。

**理由**：老判据问的是「**这个文件**的 mtime 变了没有」，而编辑器的标准保存
法是 `write tmp → fsync → os.replace(tmp, target)`——替换之后「这个文件」已经
是另一个 inode，旧的那个不存在了。判据从一开始就量错了主语，于是"能不能
发现"取决于 `stat()` 恰好落在替换前还是替换后。

同一个错误还有另外四种表现，全部同源：新建（不在清单里）、删除（`OSError`
被 `continue` 吞掉）、重命名（删+增，两头都看不见）、注册表与素材（根本
不是 `.py`）。**换主语一次修好五种**：写判据之前先说清
"谁的、哪个时刻、哪个维度"。

---

## T-22（Session 05）签名的两维各守一半，缺一维会静默漏

**权威**：`project_watch._sig()`。

**决定**：文件签名是 `(size, mtime_ns)` 两维，不是任意一维。

**理由**：只留 `mtime_ns` → FAT32、部分网络盘、老 HFS+ 的时间戳精度只到
1~2 秒，**一秒内的两次保存签名完全相同**；只留 `size` → 改一个数字、换一个
颜色名，长度常常一字节不差。两种漏法的表现都是"保存了没反应"，而且都只在
一部分机器上出现。

**两维各配一条用例**（`test_signature_notices_a_same_mtime_rewrite` /
`..._same_size_rewrite`），砍掉任何一维都会被变异反证打红。「量了主语」不等于「量对了维度」（T-21 是前者，这条是后者）。

## T-23（Session 05）「看不见」不是「不存在」

**权威**：`project_watch.take_snapshot()` 在目录不可用时返回 `None`。

**决定**：项目目录当前不是一个可读目录时，这一轮**什么都不做**，也不动上一
张快照——不返回空快照。

**理由**：空快照与「用户删光了所有文件」在 diff 里**长得一模一样**。照它行事
的后果是一次网盘抖动/外接盘没挂上就打掉整个项目的渲染会话，并触发一次
全量"删除"刷新。快照比的是两个**状态**而不是重放事件流，所以中间漏看几轮
不丢信息：目录回来之后，下一次 diff 仍然会把这段时间里真正发生的变化算出来。

代价是「项目真的被删了」要等到用户下次打开时才报。这是刻意的取舍：误报
删除的代价（作废全部会话 + 一次假的全量 diff）远大于晚报的代价。

## T-24（Session 05）防抖等的是「安静」，而目录可能永远不安静

**权威**：`ProjectWatcher.poll()` 的 `quiet or aged`。

**决定**：防抖窗口（0.5 s）之外**必须有批次年龄上限**（5 s）。

**理由**：防抖的规则是"新变化到达就把批次结束往后推"，而一个正在跑脚本、
正在被 rsync 写入、正在解压的目录会让这个条件**永远不满足**——刷新被无限期
推迟，用户看到的是"改了半天一点反应都没有"。这条属于"等一个可能不会发生的
事件"那一族，解药是给等待本身设上限，而不是把防抖调短。

## T-25（Session 05）不留降级版兼容代理

**权威**：`pool.py` 里的 `start_watcher/stop_watcher/watched_dirs` **删除**
（ADR 0026 §9）。

**决定**：全量迁移调用方（10 个测试夹具 + `desktop.py`），不留代理。

**理由**：`start_watcher(dir, scripts, on_change)` 这个签名表达不了项目
watcher 需要的东西（ctx、刷新回调）。留一个降级版代理的话，任何一条老路径
调它就会**把功能完整的项目 watcher 替换成一个只盯清单的**——两个 watcher

`RefreshSink.watch` 同理删除：它的动作（按新清单重挂 mtime 跟踪）在整棵树的

空门禁比没有门禁更坏（根 `AGENTS.md`）。

## T-26（Session 06）「派生同步不标脏」与「派生同步必须落盘」不是矛盾，是三档

**权威**：`documentStore` 的 `derivedSeq` 与自动保存订阅里的 `derived` 分支。

**决定**：`doc` / `canvases` 的变化有**三种性质**，各有各的处置，
`loadSeq` / `derivedSeq` 两个代次就是订阅认性质的判据：

| 性质 | `dirty` | `saveState` | 撤销历史 | 落盘 |
| --- | --- | --- | --- | --- |
| 载入（`loadSeq` +1） | 由载入方声明 | 由载入方声明 | 清空 | 不排队 |
| 用户编辑 | 置位 | 推成 `dirty` | 进 | 排队 |
| **派生同步（`derivedSeq` +1）** | 置位 | **不动** | **不进** | **排队** |

**理由**：共享规则说「派生数据刷新不得**无故**把文档标成 dirty」，Prompt 06
又要求「必须标记文档需要可靠自动保存」。两句话看着打架，其实说的是两个不同
的东西：

* `script` 是**存进文档的字段**。只改内存不落盘的话，用户下次打开这份文档，
  刚刚原地升级的面板又回到不可编辑——外部改动的效果活不过一次刷新；
* 但一次外部文件改动**不是用户的编辑**。把 `saveState` 推成 `dirty` 会让关闭
  保护弹一句「有未保存的改动」，说的是用户没做过的事；而 `hasUnsavedWork()`
  读的正是 `saveState`。

所以 `dirty`（字面含义就是"有改动还没写进自动保存"）照置、落盘照排队、
**只有用户看得见的那一档不推**。写盘本身仍然走完整的状态机：`saving` /
`save_error` / `conflict` 一个都不吞——"这次写成了没有"是用户必须看得见的。

「无故」那个词落在哪里也说清了：**无差异就一个 `set()` 都不发**。这与后端
统一刷新的「无差异 = 零事件、零写盘」是同一条纪律，也正是"一批事件里的第二条
第三条不会重复置 dirty"的来源——不需要另写去重逻辑。

## T-27（Session 06）图幅不是派生字段

**权威**：`panelSourceSync.derivedPatchOf()` 同步的四个字段
（`script` / `cost` / `fileKind` / `pxW`），**不含** `nativeW` / `nativeH`。

**决定**：`/api/panels` 也报图幅，但同步不碰它。

**理由**：`nativeW/nativeH` 是**几何**——`useEngineSync` 有一个 effect 盯着
它，图幅一变就按新纵横比调 `o.h`。让磁盘上那份文件的原始尺寸去改它，等于让
一条外部事件挪动用户的排版，正是「绝不修改几何」要挡的事。

而且磁盘那份**不是权威**：`size_mm` 本身可以被 override，同一个文件的两个
副本可以有两个不同的图幅。图幅的权威是**这个变体自己**渲染回来的 manifest，
那条路径早就存在（`useEngineSync` 的第二个 effect），不需要第二个来源。

同一条推论下 runtime 面板整个跳过：它的 `fileId` 是 `runtime:` 前缀的不透明
id，磁盘上没有对应文件，也就永远不会出现在 `/api/panels` 里。不跳过的话每一
轮同步都会把它们判成「素材不见了」。

## T-28（Session 06）「文件暂时不见了」与「脚本关系失效了」是两件事

**权威**：`syncObjects()` 里 `if (!info)` 那一支——**只记进 `missing`，
不改对象的任何字段**。

**决定**：素材不在本次清单里时，面板对象原样保留，`script` 也**不抹**。

**理由**：两件事的证据强度完全不同。"清单里没有它"可能是网盘掉线、外接盘
没挂上、后端刚重启还没扫完；而"脚本关系失效"是后端**看得见那个素材、并且
明确说它没有脚本**。把前者当后者处理，一次网盘抖动就会让一批面板永久失去
编辑入口——而恢复它需要用户自己发现并重新触发一次刷新。

缺失素材有它自己的既有语义（`preflight` 的 `missing-asset` 由
`!assets[o.fileId]` 现算 + 重新链接对话框），一个字节都不用新写。

## T-29（Session 06）刷新、事件、重连共用同一条路径

**权威**：`store/liveSync.ts` 的 `refreshAssetsAndSync()`。

**决定**：SSE 事件、素材面板的「刷新项目」按钮、SSE 重连恢复，三个入口
调的是同一个函数；合并与去重都长在它下面（`assetStore.load()` 合并请求，
`syncPanelSourceMetadata()` 无差异零改动）。

**理由**：这是本仓库反复付学费的那一族——「共享判据修一处不算修完」。
三条各写一遍的话，「刷新之后要不要同步文档」就有三份判据，而第三份总会漏掉。
合并做在两层上也不是冗余：请求层挡的是同一批事件的多次调用（它们能并成一个
promise），差异层挡的是并不成一个请求的那些（第二条事件晚到一步）。

**重连恢复刻意不调后端的静态刷新**：那会扫磁盘，而一次网络抖动就扫一遍是拿
用户的磁盘给自己的连接质量买单。只重取素材清单（只读端点）足以恢复"哪张图
现在可编辑"，真正的文件变化由 watcher 在下一轮自己发现。

## T-30（Session 06）降级要把 manifest 一起清掉

**权威**：`applyPanelSync()` 里 `render.reset(fileId)`。

**决定**：面板失去脚本时，除了把 `script` 置 null，还要丢掉它在
`renderStore` 里的**全部变体**（含 manifest / tracked / latest / recent）。

**理由**：`script` 只管住了"双击还能不能进去"这一个入口。留着的 manifest
会让元素树、命中几何、检查器继续按"这张图可参数化"办事——界面上一切正常，
直到用户点下去才发现后面没有东西。这是「修了判据，没扫消费点」的同一形状：
**"可编辑"这件事在前端有不止一个消费者**。

`overrides` 反过来**一条都不删**：那是用户的编辑，源关系恢复之后还要用。
清的是缓存，不是数据。

## T-31（Session 07）状态的主语必须是用户指着的那个东西

**权威**：`engine/readiness.py` 的 `STATUSES` / `REASONS_BY_STATUS`。

**背景**：「这张图能不能进图内编辑」在起始状态下由三处各答一次，而**三处的
主语都不一样**：`/api/panels` 给不给 `script`（按**素材**）、`/api/registry`
的 candidates（按 **stem**）、`probe.script_inventory()` 的 reason（按**脚本**）。
于是同一张图在素材面板里「不可编辑」、在注册表对话框里「有候选脚本」、在
脚本清单里「可试运行」——三句话都对，合起来却没有一句回答了用户的问题。

**决定**：新增一层事实模型，主语固定为 `/api/panels` 的那一个素材 id，输出
**六个互斥状态**（`editable` / `auto_linkable` / `needs_probe` / `conflict` /
`source_missing` / `layout_only`）加一个稳定 `reason_code`。三份原始事实
（注册表 / 静态 AST 报告 / 文件存在性）仍在各自的位置，就绪度只**组合**它们。

**理由**：这是本仓库反复付学费的那一族——[[name-the-subject-of-the-predicate]]
的同一形状。三个主语不同的判据合不出一句话，而界面必须说一句话；不定主语的
话，说那句话的责任就落到了前端，而前端手里只有其中一份事实。

**禁止的替代实现**：在别的 API 或前端里另起同义状态；前端按 `script` 有没有
值自己再猜一遍（Prompt 08 只翻译这份事实，不重新判定）。

## T-32（Session 07）fingerprint 是**报告**的哈希，不是**输入**的哈希

**权威**：`readiness.fingerprint()`。

**决定**：fingerprint = 规范化 JSON（键排序）的 SHA-256 前 32 位，输入是
**这份报告本身**（不含 `generated_at`、不含 `fingerprint` 自己）。

**理由**：需求里那四条（时间戳不能进、无关文件 mtime 不能进、绝对路径不能进、
dict 顺序不能进）如果按"哈希输入"来做，就要逐条去防，而每加一个输入维度就
得重新审一遍这四条。按"哈希输出"做，四条**自动成立**：`generated_at` 不在
body 里所以进不来；素材 mtime、脚本 mtime 这些没有进报告的东西变了它不动；
绝对路径本来就一个都不在报告里。反过来，任何一个会被用户看见的事实变了它必
然变——因为那个事实就在被哈希的字节里。

**代价**：输入变了而输出没变时会白算一遍（缓存键另算，它才是按输入的）。
这正是要的：前端据 fingerprint 判"要不要重画"，白算一遍它不该看见。

## T-33（Session 07）「没测量」不是「测量结果是零」

**权威**：`REASON_SCAN_UNAVAILABLE`、`conflicts: null`、`project.scan_ok`。

**背景**：Session 06 的交接把这条写成了下一阶段的头号陷阱：「`conflicts`
缺席 = 这一轮没跑静态扫描，不是"没有冲突"」。

**决定**：静态扫描失败时**不报** `no_source_candidate`——那是一句错的断言。
状态给 `layout_only`（那是此刻唯一还成立的能力陈述：这张图还能排版），
reason 给 `source_scan_unavailable`，`conflicts` 给 `null` 而不是 `[]`，
项目级 `scan_ok: false` + 一条 issue。**这一份报告不进缓存**——缓存一次失败
等于让一次瞬时的目录读错误把就绪度永久钉死，而用户看到的现象是"我修好了它
还是说不行"。

**同一族的另外两处**：`registry_valid` 的 `null` 是"项目里根本没有注册表
文件"（与"有、但坏了"是两回事，合并的话界面会对着一个新项目喊"你的注册表
损坏了"）；`RefreshState.conflicts` 的 `None`（Session 04 的 T-15）。

## T-34（Session 07）注册表优先于静态报告

**权威**：`readiness._capability()` 的分支顺序（注册表那一支在冲突之上）。

**决定**：一个 stem 在注册表里有映射时，就绪度**不看**静态报告怎么说。
静态冲突照旧出现在项目级 `conflicts` 里，但带上 `resolved_by`。

**理由**：注册表文件就是人工裁决的落处（`src/tavotto/AGENTS.md`：「一脚本多
产物 / 归属有歧义的 stem，裁决结果记在各图库自己的注册表文件里，勿改」）。
让静态报告推翻它，等于每刷新一次就把用户的决定重新掀一遍——而用户能看到的
现象是"我明明指定过了，它每次都又问我一遍"。

**`source_missing` 的候选是这条规则的补充而不是例外**：注册表指着的脚本没了、
另一份此刻正好认领同一个 stem（改名/重构最常见的形状），状态照旧是
`source_missing`（注册表说的还是那个不存在的文件），但候选要给出来——否则
用户手里只有一句"它不见了"。

## T-35（Session 07）就绪度只报告，动作仍归原来的端点

## T-36（Session 07）同一条保证只留一个实现，否则变异永远杀不死它

**权威**：`compute()` 里唯一那处 `sorted(panels, key=…)`。

**背景**：第一版里排序做了两遍——素材清单排一次（`assets.sort()`），报告的
panels 再排一次。两遍各自都足以让「排序稳定」成立，于是**删掉任意一处都还
有另一处兜着**：两条变异全部存活，而用例是绿的。

**决定**：顺序的契约只有 `panels` 那一处；`iter_assets()` 的遍历顺序是它自己
的事，本模块不依赖也不复述。

**理由**：这不是"多一层保险"，是**判据量不到自己**。第二份实现让变异反证在
这一维上恒绿，而恒绿的门禁与没有门禁的区别只是它看起来像有。冗余要留的话，
用例必须能分别打到每一份（Session 05 的签名两维就是那个形状：size 与
mtime_ns 各有一条用例看着，删任意一维都有对应的用例红）。

## T-37（Session 08）就绪度报告带上 `stem`——关联动作的对象是它，不是那张图

## T-38（Session 08）接入中心的开关仍然只有 `uiStore.registryOpen` 一个

## T-39（Session 08）就绪度的刷新挂在 `refreshAssetsAndSync` 一处

**权威**：`web/src/store/liveSync.ts` 的第一行
`void useProjectReadinessStore.getState().load({ force: opts?.force })`。

**背景**：报告会过期的时机与素材清单**完全一样**（它们是后端同一次
`compute()` 的两个投影）：`panel.file_changed` / `assets.changed` /
`registry.changed`、素材面板的刷新按钮、SSE 重连恢复、接入中心里的每一次动作。

**决定**：不在各个事件分支上各调一次，挂在 `refreshAssetsAndSync()` 里。
`force` 与素材那一侧同义——用户刚按过刷新、刚写过盘时不复用在那之前发出的
在途请求。

**理由**：Session 06 定下的不变式是「前端的消费只有 `liveSync` 一份」。报告
另开一条消费路径的话，第三个触发点总会漏掉其中一条——而漏掉的表现是
「素材卡的角标变了，接入中心里还是旧的」，也就是 07 之前那个病换了个位置。
**不 `await`**：诊断端点不该挡住画布上的面板同步。

## T-40（Session 08）「常驻侧栏的偏好」与「此刻开着没开」是两件事

**权威**：`web/src/store/uiStore.ts` 的模块级 `prefOpen`，以及 `persist()` 里
那句 `const snapshot = { ...state, leftOpen: prefOpen.left, rightOpen: prefOpen.right }`。

**背景（真实缺陷）**：`persist()` 原来照抄当前状态，而**响应式让位也写在同一个
`leftOpen` 上**——互斥断点上两侧都开着时自动收左栏、窄屏开机不铺右栏。于是把
窗口拖窄一次，之后**任何一次** persist（改个网格、拖一下宽度）都会把
`leftOpen: false` 当成用户的偏好写进本机；回到大屏、重启之后常驻的左栏再也
回不来，**而用户从没关过它**。

**决定**：偏好单独记一份，只有**用户自己的动作**与**产品规则**写它：

| 写偏好 | 不写偏好 |
| --- | --- |
| `toggleLeft` / `toggleRight` / `railClick` / `setLeftTab` / `setRightTab` 里**他动的那一侧** | 同一次里被互斥顺手收起的**另一侧** |
| `autoShowProperties` 的右栏、以及素材抽屉「挑完让位」那一档（宽屏一样生效 = 产品规则） | `autoShowProperties` 里由 `exclusive()` 触发的那一档 |
| `autoHideProperties` 真的收起时 | `setLayout()` 的挤压、`readPersisted()` 的窄屏裁剪 |

**理由**：窗口宽度不是用户说过的话。判据只求值一次（`autoShowProperties` 的
`assetsYield`）并同时用于「改状态」与「写偏好」——写两遍的话两份迟早分叉，
而分叉的表现是「关掉的抽屉过一会儿自己回来了」。看护：`uiStore.test.ts` 的
「窄窗口的自动让位不许覆盖桌面偏好」四条（变异把 `snapshot` 换回 `state`，红）。

## T-41（Session 08）状态的句子按 `reason_code` 查，不按 `status`

**权威**：`web/src/lib/readinessText.ts` 的 `reasonText()`——它只读
`cap.reason_code`，`statusLabel()` 才读 `status`。

**背景**：素材卡角标、素材说明条、接入中心每一行、属性栏那条提示，四处说的是

**决定**：一份实现（`lib/readinessText.ts`），且**句子按 reason code 查**。

**理由**：同一个状态下不同 code 要说的话完全不同。`auto_linkable` 有四个

## T-42（Session 08）默认值只有一个主人：不知道入口就**不传**

**权威**：`web/src/components/RegistryDialog.tsx` 的 `entryOf()` 返回
`string | undefined`；`web/src/lib/api.ts` 的 `writeRegistryEntry` 里
`entry?: string`；后端 `app.py::api_registry_write` 的
`str(body.get("entry") or "main")`。

**背景**：手工关联要往记录里写一条 `script → stems`，还得带上入口函数名。
前端能从三个地方知道它：已登记的那份 → 这一轮扫出来的候选 → 脚本清单解析出
的 `entry_candidates[0]`。三个都问不出来时怎么办？

**决定**：**不传**。第一版写的是 `?? 'main'`——那是把后端已经有的默认值在前端
再抄一份。抄的那一刻两处相等，但它们此后各改各的，而分叉的表现是
「登记成功了，下次渲染却找不到入口」。

**看护**：四条变异各屏蔽一个出处（含"编一个 `'main'`"），全部被打红。
fixture 里三个出处的入口值**刻意互不相同、且都不是 `main`**——写成一样的话，
屏蔽掉第一个出处，第二个照样返回同一个答案，那条判据就永远量不到自己
（这是 T-36 的形状长在了 fixture 里，本轮真的踩到过）。

## T-43（Session 09）两条工作流共享**同一个对象**，不是两份数据

**权威**：`web/src/store/workspace.ts`（`mode` / `activePanelId` + 四个稳定
动作）；`web/AGENTS.md` 的「两条工作流与原图规格」。

**背景**：Prompt 09 要「单图无需画布即可编辑」，而 overrides / 标注 / 撤销
全都挂在 `CanvasObject` 上。最直觉的做法是给快速编辑一个自己的容器
（一张隐藏画布、或者文档顶层一个 `figures[]`），然后「添加到画布」时把对象
搬/抄过去。

**决定**：**不建第二个容器。** 一张图在文档里只有一个面板对象；快速编辑是
这个对象的另一种**看法**（这一屏只画它，页面纸 / 网格 / 参考线 / 别的对象
让开），画布排版是它在页面上的落位。

理由是抄那一下：两个容器意味着同一张图有两份 `overrides`，而「共享 edits」
就得靠一条同步规则维持。同步规则会在某条路径上漏掉（撤销、跨画布、写回原图
之后的基线继承……），而漏掉的表现是**用户在一边改的东西在另一边不见了**——
那正是这一阶段要消灭的东西，只不过换了个更难查的形态。

顺带得到的三个结论都不需要再写代码：

* 「添加到画布」**不复制失联对象**：根本没有复制这一步；
* 「从画布进图内编辑再返回，位置尺寸不变」：快速编辑**一个字都不写
  x/y/w/h**，而不是"回来时恢复一下"（恢复式实现总有一条路径会漏）；
* 「重复添加不叠对象」：`findFigurePanel()` 找得到就聚焦。

**代价（如实记录）**：打开一张图会**真的在当前画布上放一个面板**（一次
可撤销的文档修改）。用户从没想过画布，但画布里多了一个对象。这是有意的
——那个对象就是他接下来编辑的载体，让它凭空存在于"文档之外"才是幻觉。

**看护**：`store/workspace.test.ts` 19 条；其中「切进切出不动文档」比的是
整份 `doc` 的 JSON 与历史长度，「加入画布之后 overrides 还在同一个对象 id 上」
比的是 id 本身——比字段值的话，一份复制品也能让它绿。

## T-44（Session 09）尺寸的**事实**与「按原图导出」的**决策**分开

**权威**：`src/tavotto/engine/originalspec.py`（事实）、
`web/src/lib/originalSpec.ts`（决策）、`docs/adr/0028-original-output-spec.md`。

**背景**：改造前「这张图有多大」在 `scan_panels()` 里现算，位图那一档是
`ppi = 600 if png else 300` —— 一句注释就是全部依据，猜错了界面上一个字不说。
而「按原图导出」这句话本身没有定义：要不要套用画布缩放？裁剪算不算？

**决定**：后端只报**文件自己说了什么**（逻辑 mm / 像素网格 / 物理密度 /
矢量视口 / 透明度），前端一份服务按固定优先级做**决策**
（渲染 manifest > 文档 > 磁盘 > 明确 fallback）。`native_*_mm` 改成事实层的
**投影**，不是第二次计算。

「按原图导出」的定义写进 ADR：忽略落位、缩放、页面尺寸/背景/边距、页面裁切，
以及面板上的 crop / rotation / flip / opacity；保留图内 edits；**不因为用户
曾把面板缩小就把字号一起缩小**。被忽略的逐项列进 `spec.ignored`，界面照此
说明——忽略而不说等于骗人，说了而不忽略等于套用画布缩放。

**为什么决策在前端**：第 1 档（渲染回来的 `size_mm`）与第 2 档（文档里那份）
后端看不到——图幅的权威是"这个面板此刻那份变体"，而变体是文档状态。

**看护**：`tests/test_original_spec.py` 16 条 + `lib/originalSpec.test.ts`
25 条；变异反证 12 条（含"渲染图幅不再压过文档"、"缩放判据改用页面包围盒"）
全部被打红。

## T-45（Session 09）「不知道」在密度这一维上也是独立一档

**权威**：`engine/originalspec.raster_dpi()`；`DPI_SOURCES` 的四个取值。

**背景**：位图的物理密度有三种情形——文件写了、文件没写、源文件已经不在了
只能反算。最省事的做法是都给一个数。

**决定**：给数的同时给**出处**：`metadata`（文件写的）/ `assumed`（文件没写，
我们按格式假定）/ `derived`（由已知 mm 与像素反算）/ `unknown`（这一维没测量）。
`dpi: null` 与 `dpi: 96` 是两个不同的答案。

**为什么不用 MuPDF 的 `Pixmap.xres`**（实测 PyMuPDF 1.28.2）：**没有 `pHYs`
的 PNG 与真的写着 96 dpi 的 PNG，它一律回 96**。把它当密度来源，就等于把
「不知道」合并进了 96 —— 而这里最需要说出来的恰恰是「这个数是我们假定的」。
所以密度由本模块自己按格式解析（纯标准库，PNG pHYs / JPEG JFIF / Exif）。

`ASSUMED_DPI` 的取值与改造前**逐位相同**：老项目里已经摆好的面板尺寸一个都
不变，变的只是它现在说得出自己是假的。

**看护**：`test_ninety_six_dpi_is_metadata_not_the_absence_of_it` 就是钉着
这条——有人把实现换回 `xres`，它当场红；变异「位图密度一律按假定」同样被打红。

## T-46（Session 10）项目里存的是**规则全文**，不是一个 profile id

改造前 `CanvasData.profile` 只有 `{id, journal?}`，注释写得很明白：

> 规范升级后旧文档自动跟着新规则走，而不是把一份过期的规则冻在布局文件里

那个判断在**规范只会由我们改、而且只会变严**的世界里成立。本阶段把规范交给
用户自己建、自己改之后，它的代价换了一副面孔：

> 改一次全局规范，上个月定稿、已经投出去的图，体检结论换了一套。用户没有
> 任何办法知道结论为什么变了，也没有办法要回原来那一套。

**裁决：默认「项目结果稳定」优先于「规范升级自动生效」。** 文档里存
`snapshot`（规则全文）+ `snapshotVersion`（只给人看）+ `follow`（用户明确
表态才写）。全局那份后来变了，界面提示「有新版可同步」，**由用户点一下**，
那一步进文档历史。

三个字段全部**可选**，磁盘 schema 一个字节没升版——老文档没有它们 = 从没绑过
快照 = 按 id 取全局现值，这正是 Prompt 10 要的「未显式保存的旧默认迁到新规则」。

**代价如实记着**：每张画布的 profile 快照是一整份规则（约 4 KB），多画布项目
里会重复几份。没有做去重——去重意味着引入一层间接（一个 id 指向文档里的某处
共享块），而那正是"改一处影响另一处"的来源，与本条裁决背道而驰。

## T-47（Session 10）「有没有新版」的判据是**内容不等**，不是版本号

第一版打算比 `snapshotVersion` 与全局那份的 `version`。实测之下这条判据有两个
方向都会错：

* 版本号没动而规则改了（用户改自己那份规范时根本没有版本号可改）→ **不提示**，
  而这正是最该提示的那次；
* 版本号跳了而规则一个字没改（改了 `label`、改了 `source` 注释）→ **提示**，
  用户点进去发现什么都没变。

**裁决：判据是规则本身的内容不等**（`sameRules`，键序无关的确定性序列化）。
快照本来就要存全文，比内容是免费的。版本号退成纯展示（「你用的是 1.0.0，
现在是 1.1.0」）。看护用例两条对称，方向相反的都在。

## T-48（Session 10）统一为 8 pt = 删掉更严的那条，**不是**改 8 pt 那条边

`min_effective_font_size_pt: 8.5` 与 `absolute_min_font_size_pt: 8.0` 的差别不是
冗余——它们是两条检查（`font-too-small` / `font-below-absolute-floor`）。
「统一为 8 pt」有两种做法，选错一种会把语义也改掉：

| 做法 | 结果 |
| --- | --- |
| 两档都设成 8.0，**边界语义不动**（`eff <= floor`） | 8.2 pt 通过、正好 8.0 仍然不算过。ADR 0006 的「必须大于 8pt」原样有效 ✅ |
| 两档都设成 8.0，同时把 `<=` 改成 `<` | 8.0 变成通过——**改的是"最小字号是多少"这件事本身**，而 Prompt 只说了统一，没说放宽 ❌ |
| 只留 8.5 | 那正好是要删的那条 ❌ |

**裁决：第一种。** 依据写在规范文件自己的 `source` 里——8.5 是「本项目补充
（原文示例里有 8 pt 图例/刻度，这里从严）」，也就是说**那条规则比它想守护的
规范更严**。删掉它就是回到规范原文。

两条检查**仍然是两条**：默认规范把两档设成同值只是让 `font-too-small` 在这一份
规范里退居幕后；`free-form-v1`（6.0 / 5.0）与任何期刊覆盖照样两条各自出场。
看护用例分成两条，一条量默认规范只有一个数，一条量两条检查还在。

## T-49（Session 10）默认输出 PPI **不进 Style**

Prompt 10 把「可选默认输出 PPI（仅作为偏好）」列进了 StyleProfile。实现时发现
它没有一个不制造第四个出处的落地方式：

* 读它的只能是导出面板，而导出面板的 PPI 来自 `exportDefaults`（一台机器一份
  偏好）。让「应用样式」去写那份偏好 = **把一次临时动作变成用户的长期设置**；
* 不读它 = 一个死字段，界面上能改、改了什么都不发生；
* 而「规范推荐多少 PPI」**已经在 Spec 里**（`preferred_formats.export_dpi_default`）。

**裁决：不做。** Style 里没有这个字段，白名单里也没有它的位置，理由写在
`_STYLE_KEYS` 旁边。这条是本阶段"消掉重复出处"的一部分，不是偷懒。

## T-50（Session 10）规范的身份跟着记录走

从内置复制一份规范时，`data.profile_id` 必须改成新记录的 id。留着源 id 的话
proof report 与 MCP 响应上写的是 `lab-publication-v1`，而实际用的是用户改过的
规则——**「这张图按哪套规矩过的检」就此说不清了**，而留档的全部意义就是这句话。

`reset_profile()`（恢复默认值）同理：内容回到内置那一份，**身份仍然是自己的**。
否则恢复一次就多出第二个 `lab-publication-v1`。

## T-51a（Session 10）`follow` 是项目的姿态，不是某一套规范的属性

换一套规范时 `follow` 跟着走（`bindingFor(entry, {follow: doc.profile?.follow})`）。
反过来的话，用户说过的"以后别问我"会在换规范时被悄悄关掉，而没有任何提示。

它只在明确为 `true` 时写进文档：「没选过」与「选了不跟随」**行为相同**，
所以不给第三档——对比 `dpi_source` 的四档，那里三个取值的行为各不相同
（[[unknown-is-its-own-value]] 说的是"行为不同就别合并"，不是"什么都要分三档"）。

## T-51（Session 10）前后端对「不认识的 id」取舍不同，**且是有意的**

| 侧 | 行为 | 理由 |
| --- | --- | --- |
| 后端 `profilestore.resolve_spec()` | **抛错** | MCP 调用方拿着一个不存在的规范 id 时，"按默认规范放行了"是最坏的答案 |
| 前端 `resolveDocumentSpec()` | 退默认规范 + 报 `globalMissing` | 旧文档里可能存着一个已经删掉的 id，导出对话框不能整个崩掉 |

## T-52（Session 11）聚合项回答「过没过」，逐条命中回答「谁没过」

求值器的 `Sink` 把同一条规则的多次命中聚合成一项。这在「这份图过没过」上是
对的，在「谁没过」上是错的：

```text
聚合项  font-below-absolute-floor  gids=[xticks, yticks, title]  detail={effective_pt: 6}
```

三个元素分别是 6 / 7 / 7.5 pt，而聚合项的 `detail` 属于**最糟的那一次**。
把它摊成三行显示，其中两行的数字就是假的——而**判据修对了不等于它说的话对**，
判据一旦可信，人更会相信那句错的（[[error-messages-are-assertions]]）。

**裁决：`Sink` 额外记一份逐条命中**（`PreflightOccurrence`：objectId / gid /
prop / 它自己那次的 message 与 detail），去重的尺子与聚合项完全一样（带 `worse`
的取最糟那次，不带的第一次说了算）。

三个边界：

* **它不进跨语言合同。** golden vectors 比的仍是聚合投影，Python 侧一个字节
  没改——那边的消费方是 MCP 的聚合清单。
* **看护用例盯着两者一致**：命中的 objectId / gid 并起来必须与聚合项逐字相等。
  两份数据分叉的话，面板列的对象与 proof 留档的对象会对不上。
* **一次 `add()` 可能带来多个命中**：`out-of-page` 一次交上来一串对象 id。
  展开规则固定（有 gid 按 gid 展开，否则按对象 id 展开，都没有就是页面级一条），
  不按调用点各写各的。

## T-53（Session 11）指纹**不含当前值**

`issueId = ruleCode｜canvasId｜objectId｜gid｜propertyPath`。

把当前值放进去看起来更"精确"，代价是：7.5pt 改成 7.6pt 会变成一条**新**问题。
React 拿它当 key，于是每敲一个数字整行都被重建——焦点掉、动效重播、
「技术详情」的展开状态丢。而用户的认知里那始终是同一条问题。

反过来，五个维度**一个都不能少**：少了 `canvasId`，两张画布上同一个对象的
同一条问题会撞成一条（多画布项目里第二张画布上的问题就此消失）；少了
`propertyPath`，同一个元素的 `fontsize` 与 `tick_fontsize` 会互相顶掉。
看护用例逐维反证。

## T-54（Session 11）「还没查」是独立一档，不许压扁成「没问题」

`summarizeIssues(issues, state)` 的 `state` **必须由调用方明说**，没有默认值。

给它默认 `ready: true` 的诱惑很大——绝大多数调用点确实已经查过了。但那一档
默认值会让"还没查"静默变成"查过了、没问题"，而这是这套服务能犯的**最坏的错**：
它长得和好消息一模一样，用户会带着一屏静悄悄的绿去投稿。

配套两个决定：

* **导出对话框打开时当场同步跑一遍**（纯计算、没有请求），于是那 250ms 防抖
  窗口里不会说出一句假话；
* **检查失败保留上一次的结果**（它当时是真话），另说一句「这一次没查成」，
  并把它算进「需要用户点头」的条件——那份清单可能已经过时，不能当成这一版的
  结论。

同一族的既有裁决：T-33（「没测量」不是「测量结果是零」）、T-45（`dpi: null`
与 `dpi: 96` 是两个答案）。

## T-55（Session 11）`safe_auto` 的门槛是「修完真的能过」，不是「写个合理的值」

Prompt 举的例子是「把 7.5 pt 提升到当前 Spec 的 8 pt」。**照做的话根本没修好**
——默认规范统一为 8 pt 之后，绝对下限那条判据是 `eff <= floor`（T-48 明确不动
这条边），写 8.0 仍然不算过。

所以目标值取**大于下限的最小 0.5 档**（默认规范下是 8.5），并且：

* **换算回脚本坐标系**。面板缩到 60% 时 `eff = size × scale`，直接把 `fontsize`
  写成 8.5 的话读者量到 5.1pt——修复反而制造了一条新的违规；
* **取整方向跟着目标走**（提字号往上取、降字号往下取），否则两位小数的舍入会把
  结果推回违规那一侧。

三条门槛缺一不可：目标值唯一、修完真的能过、不动科研数据。第三条排除了字体替换
（装没装都不知道）、色图替换（改的是数据语义）、裁剪与重排。

## T-56（Session 11）Readiness **不进**问题清单

「这张图还没连上脚本」与「这张图字号偏小」都是"问题"，但它们的**下一步完全
不同**：前者要去接入状态里连接源脚本或试运行，后者要改一个属性。混进同一个
清单之后，用户既分不清轻重，也找不到各自的出口——而且就绪度那边已经有一整套
状态、reason code 与措辞（ADR 0027 / T-41）。

**裁决：面板底部只放一条链接**（「项目里还有 N 张图没连上脚本 →」），点进去
是接入状态中心。清单本身只装样式与几何问题。

## T-57（Session 11）「画布还在不在」只判一次

第一版写成两道守卫：先查 `canvases.some(...)`，切完再查 `activeCanvasId` 到没到。
两句话说的是同一件事，于是**把前一句改成恒真也没有任何用例会红**（变异反证里
它活了下来）。

`activateCanvas()` 对不存在的 id 本来就是 no-op（`switchCanvas` 自己查成员），
所以合成一处不放松任何东西。**冗余的保证杀不死，处置是合并，不是造个输入去
覆盖它**——与 T-36 同一条（那次是工作区模式的持久化）。

这已经是本轨道第三次撞见同一个形状。

## T-58（Session 12）原图与画布是**同一个请求的两个 scope**

两条各自独立的导出路径是更直觉的做法（"原图导出"是一件小事，直接把源文件
拷出去就行）。它有两个当场就能看见的代价：

1. **默认值会分叉。** 文件名怎么清洗、扩展名怎么补、覆盖怎么办、报告写不写
   ——每一项都要在两条路上各写一遍，而写两遍的东西迟早不一样。改造前的四份
   载荷构造（对话框 / `api_export` / MCP bridge / 打包）已经演过一遍了。
2. **"这次导出成功了没有"会有两种形状。** 结果结构不同的话，界面要为两条路
   各写一套结果区、一套错误处理、一套进度。

**裁决：一个 `ExportRequest`，`scope` 是它的一个字段。** 分歧收敛在
`produce()` 这一层（画布走合成、原图走整页搬运），而请求、校验、命名、原子
落盘、取消、部分失败、报告全部共用。

代价是 `ExportRequest` 上有两个互斥的可选段（`canvas` / `original`）。这是
**刻意**的：把它们做成一个联合体在 JSON 上没有更强的保证，而两个具名段让
"这个 scope 里没有那几个字段"这句话可以被用例直接断言。

## T-59（Session 12）`scope=original` 的载荷里**没有**布局字段

不是"记得别填"——`OriginalSource`（Python 的 dataclass 与 TS 的类型）上根本
没有 `x_mm` / `y_mm` / `w` / `h` / `page_w_mm` / `crop`。

理由是**这条纪律必须结构化**（与 T-43「快速编辑一个字都不写 x/y/w/h」同一条）。
靠"实现的时候记得别用"维持的话，下一个改这段代码的人（包括半年后的自己）
会在某个看起来很合理的地方接上一句 `w_mm: panel.w`——那一行不会被任何类型
检查挡住，而它的表现是用户把面板缩小过之后，原图导出的字号跟着变小。

现在想让画布缩放漏进原图导出，得先改结构，而改结构会当场撞上两条同名用例
（`tests/test_export_request.py` 与 `web/src/lib/exportRequest.test.ts`）。

**变异反证当场证明了这条用例本身也可能是空的**：第一版夹具里，面板在画布上
的 `w/h` 恰好等于它自己的图幅（都是 80×60），于是"用的是 spec 还是用的是
w/h"这个问题根本量不出来——把实现改成读 `panel.w` 照样绿。改成 40×30 之后
才红。**夹具让判据恒真，是变异存活的第六种成因。**

## T-60（Session 12）PPI 是 `null` 还是 `600`，是两个不同的答案

只出 PDF 时，"分辨率"这一项没有意义。把它压成 `600`（或者任何默认值）看起来
无害，代价是**界面会去显示一个不影响任何东西的设置**，而用户会以为改它有用。

**裁决：`ppi: number | null`，`null` = 这次导出里它没有意义。** 界面据此把
整行藏起来（不是禁用——一个灰着的控件仍然在说"这里有个设置"）。

与 T-49（PPI 不进 Style）、T-54（「还没查」不许压扁）、ADR 0028 的
`dpi_source: unknown` 是同一条：**「不适用」不是某个取值的同义词。**

## T-61（Session 12）时间戳后缀换成**明确的覆盖策略**

改造前每个导出文件都带 `_MMDD_HHMMSS`。它解决了一个真问题（撞名），代价是
用户永远拿不到自己起的那个名字，导出目录里堆着 `Fig1_0831_143512.pdf`。

**裁决：新路径给用户输入的名字 + 闭集覆盖策略**（`ask` / `replace` /
`rename`，默认 `ask`）。`ask` 撞名时**不渲染、不写盘**就回来——先渲染半分钟
再告诉用户"这个名字已经有了"是在浪费他的时间，而静默覆盖上一次的成果是
不可逆的。

**旧路径（`stem`，没有 `filename`）保留时间戳**，一个字节不变：老标签页、
CI 脚本与 `codex-plugin` 从来没要求过名字，给它们换一套命名规则只会制造
一批需要同步改的调用点。这不是"临时兼容层"——它是一条有明确边界的旧契约，
判据就是"载荷里有没有 `filename`"。

## T-62（Session 12）部分失败是**独立一档**

一次请求要 PDF+PNG，PNG 挂了。三种处置：

| 处置 | 问题 |
|---|---|
| 报 `done` | 说谎：用户以为两个文件都在 |
| 报 `failed` + 把 PDF 也删掉 | 也是说谎，方向相反：用户什么都拿不到，而失败的原因只跟一个格式有关 |
| **报 `partial`** | ✓ |

`outputs[]` 里成功与失败**是同一个结构**，失败项带自己的 `error.code`。
界面逐项显示。

同一条纪律延伸到样式检查报告：**它自己的失败只算它自己的**（§七 明写），
但作业仍然进 `partial` 而不是 `done`。

## T-63（Session 12）后台线程必须显式绑定项目

`_request_ctx()` 没有请求上下文时落到**默认项目**。这个兜底是对的——watcher
回调与启动流程确实该落到默认项目。错的是让一个**知道自己在为谁干活**的线程
去走兜底：同时开着两个项目时，为项目 B 起的后台导出会去项目 A 解析面板。

**它不会报错。** 两个项目里都有 `p1.pdf` 的话，作业照常成功——只是成功地
导出了另一个图库的那一张。这类缺陷没有任何技术信号，只有用户在投稿前发现
图不对。

**裁决：`app.bound_project(ctx)`**，请求上下文里取好 ctx 带走。判据用"出来的
是哪张图"而不是"有没有报错"：两个项目里放同名不同尺寸的文件，少了绑定就
当场红（变异反证第一轮它活了下来，因为原来的用例只开了一个项目——
**判据看不见的维度，等于不存在**）。

## T-64（Session 12）「导出期间又被编辑过」量的是载荷，不是计数器

两种实现：

* **自增计数器**（每次 commit +1）：改个画布名、折叠个侧栏、撤销又重做一次
  都会让它变，于是导出完成时冒一句"文档被改过"——而文件里的内容一模一样。
  说了一句真话，但它没有信息。
* **载荷指纹**（把将要送去合成的那份 JSON 哈希一遍）：量的是"现在再导一次
  会不会出来另一个文件"。

**裁决：指纹。** 客户端在开始那一刻取，服务端原样存、原样回传（它看不见前端
的编辑，不去猜），完成时客户端拿**此刻的文档**重算一遍再比。

「此刻的文档」这四个字是判据的一部分：第一版拿 `lastInput.doc` 重算，而那份
是开始时冻住的引用——**比出来永远相等，那条判据于是恒成立、恒不报警**，
而空的 diff 与"没变化"长得一模一样。变异反证把它打红了。

## T-65（Session 12，评审回合）「能不能做」与「做了会怎样」必须是同一个判据

导出面板要回答「原图导出能不能用」。第一版拿 `spec.stale` 判——它看起来正好
是那个意思（"源文件此刻不可用"），实际答的是**另一个问题**：「这份规格是不是
上一次已知的那份」。

一张刚渲染过、manifest 还在手上的图，`stale` 是 **false**，而它的磁盘文件
可能早就没了。于是界面给出一个**按下去必然失败**的按钮，用户等一轮渲染才
拿到 `export_failed`。

真正的判据在后端：`_resolve_panel_source()` 的第一步是 `safe_resolve()`
（文件不在就 404），它**排在**"去注册表找脚本重渲染"之前。所以能不能导 =
素材清单里还有没有它（runtime 素材走 worker，不需要磁盘原件，单独放行）。

**Why**：两个字段的名字都像"源没了"，语义却差一层。判「能不能」时必须去问
**真正会执行的那条路的前提**，不是一个读起来像的字段。

**How to apply**：写"能不能 X"的判据前，先把 X 那条路的**第一个会失败的地方**
找出来，判据就照着那个写。找不到就说明还不知道 X 会怎么失败——那时候写的
任何判据都是猜的。

与 [[name-the-subject-of-the-predicate]]、[[predicate-dimension-not-just-subject]]
同一个家族：那两条是主语与维度，这一条是**判据与被判的那件事之间隔了一层**。

## T-66（Session 12，评审回合）注释是断言，写错的注释比没有更坏

`pdfbackend` 里写死了 `_ORIGINAL_ASSUMED_DPI = 96.0`，上面挂着一句：

> 与 `engine/originalspec.ASSUMED_DPI` 同一个数字不是巧合——那是同一个假设，
> 改一处必须改另一处。

`ASSUMED_DPI` 是 **PNG 600 / 其余 300**。那句话从写下的第一秒起就是假的，
而它比一个裸的 `96.0` 更坏：裸常量会让人去查一下，这句注释让人**不去查**。

后果是一张带 300 dpi 元数据的图被摆进大三倍多的 PDF 页面，而界面上显示的
尺寸来自另一条链（`OriginalOutputSpec`）——文件与界面各说各的，两边都"有
出处"。

**处置不是把 96 改成 600**，那只是换一个错答案：密度的解析全产品只有
`engine/originalspec` 一处，`pdfbackend` 是 PDF 后端的边界层，它连素材的
元数据都不该认识。页面尺寸改成**参数**，由调用方从唯一权威取。

顺带删掉了 `original_png(native_grid=False)` 那条分支：产品里没有任何调用点，
用的又是同一个错常量——**没人执行、又与唯一权威分叉的代码**。

## T-67（Session 12，第三轮评审）确认是**对这一批问题**的，不是对导出这个动作的

导出面板上那个「我已知悉上述问题，仍然导出」的勾，第一版只在**打开对话框**时
撤销。于是：改了格式、编辑了文档、或者已经导出过一次之后，那个勾还在。

后果有两层，第二层更重：

1. 新冒出来的阻断项**不经确认**就被放行；
2. `start()` 把当前那批 error 的规则码写进样式检查报告的 `acknowledged`
   ——**替用户签了一个他没签过的字**。留档的价值全在于它说的是真的。

**裁决：指纹取自"要确认的那批问题"**（`errors` + `notVerifiable` 的 `issueId`
加上「这次没查成」这一档），指纹一变就撤销确认；**每次导出尝试之后也撤销**
——一次点头只对那一次导出有效。

指纹用 `issueId` 而不是计数：三条 error 变成另外三条 error 时计数不变，而它
确实是另一批问题（`issueId` 的定义见 T-53）。

## T-68（Session 12，第三轮评审）同一个属性上的多条修复要**取交集**，不是挨个写

一条修复计划算出的目标值只是"对我这条规则最省事的那个数"。两条规则落在同一个
属性上时，后写的赢——而它可能违反前一条。默认规范上就有现成的一对：

| 规则 | 对 6 pt 图例文字算出的目标 | 它能接受的区间 |
|---|---|---|
| `font-below-absolute-floor` | 8.5 | `> 8.0`（判据是 `eff <= floor`，正好 8.0 过不了） |
| `legend-font-size` | 8.0 | `[8.0, 9.0]` |

批量里 8.0 后写、盖掉 8.5，而 8.0 **仍然过不了绝对下限**：「全部修复」报了
两条修好，问题面板里那条 error 还在。

**裁决：计划带上"这条规则能接受的区间"，合并时取交集再把提议值夹进去。**
由构造保证结果同时满足每一条（交集 ⊆ 每个区间）。给不出区间、或者交集为空
（两条规则互相矛盾）时**整组不修**，并如实计入 `skipped`——报一个"修不了"
比报"修好了"而它没好要诚实。

一般化的形状：**「每条规则各自的最优解」拼不出「所有规则的可行解」。** 要么
带上约束一起合并，要么就别声称同时满足。

## T-69（Session 12，第三轮评审）把纪律写进文档而不写进工具，下一次照样会踩

变异反证脚本的汇总行把「存活」与「锚点找不到」塞进同一个清单。前两轮各撞上
一次，我在 `TEST_MATRIX.md` 里写下了"两者必须分开报，合成一档的话一次重构就
能把整套变异悄悄变成空转"——**然后没有改脚本**。第三轮又撞上一次。

现在两者分列，且**有锚点找不到时脚本以非零码退出**：变异根本没打进去 =
那一条不算跑过。

与 [[make-the-discipline-structural]] 同一条，只是这次踩在**工具**上而不是
产品代码上。教训的形状：写下结论的那一刻感觉像已经处置了，而处置的定义是
"下一次不会再发生"，文档做不到这一点。

## T-70（Session 12，第四轮评审）闸放在咽喉上，不放在按钮上

导出面板的阻断闸原来是主按钮的 `disabled`。而「覆盖 / 另存一份 / 重试」三颗
按钮都**直接调 `start()`**，谁都没经过它——一次已确认的导出撞名之后点「覆盖」，
同一批阻断项就被不经确认地再导一次，`acknowledged` 还是空的。

**这一条是上一轮的修复制造出来的**：上一轮加了「每次导出尝试之后撤销确认」，
于是撞名回来时 `confirmed` 已经是 false，而那三颗按钮不看它。

**裁决：`if (blocked || …) return` 放进 `start()` 本身。** 逐颗按钮加
`disabled` 是治标——判据分散在 N 个调用点上，第 N+1 个照样漏。

一般化：**一个安全判据如果能被"再加一个入口"绕过，它就不在正确的位置上。**
正确的位置是所有入口必经的那一点。与「把纪律做进结构」同一条。

## T-71（Session 12，第四轮评审）广播事件必须有归属判据

`export.progress` 是项目级广播。原来的守卫是"我现在闲着（`!running`）就收下"
——那不是归属，那是**空闲**。于是同一个项目的另一个标签页在导出时，它的进度与
结果会显示成本标签页自己的；`resetExportState()` 之后一个**已经发出去**的轮询
同样能把状态填回去（停轮询停不掉在飞的请求）。

**裁决：`ownedJobId`——只收自己认领过的那个作业的快照。**

判据的形状值得记：**「我能不能收」问的是所有权，不是我现在有没有空。** 同族的
还有 T-63（后台线程要钉住自己在为哪个项目干活）——都是"这件事是谁的"这个维度
在判据里缺席。

## T-72（Session 12，第四轮评审）判据要打在真正会出事的那条路上

第四轮的变异反证第一轮有两条**存活**，成因是同一个：

* 「`start()` 里没有阻断闸」——用例点的是主按钮，而它本来就 `disabled`。
  点了等于没点，**闸有没有都绿**。真正会出事的是「覆盖」那条绕过 `disabled`
  的路；
* 「带 override 的位图仍报源像素网格」——只测了纯函数 `pixelPreview` 的两个
  分支，没测**对话框算不算得对那个标志**。函数是对的，调用方传错照样出事。

两条都不是"判据写弱了"，而是**判据打在了另一条路上**。写用例前先问：这个缺陷
真的发生时，是**哪一次调用**出的错？判据就打在那一次调用上。

与 [[mutation-selector-is-part-of-the-gate]] 相邻：那条说的是选择器缩到看不见
判据，这条说的是判据本身站错了路口。

## T-73（Session 12，第五轮评审）原子性要盖到中间产物，不只是最终产物

导出的落盘纪律是"临时目录 → 全部完成 → 原子 replace"。它盖住了**最终目录**，
却没盖住**中间产物**：带 override 的面板先由 worker 重渲染成一份 PDF，而那份
PDF 落在 `worker.export_dir/<stem>.pdf`——一个按图名共享的路径。

worker 调用本身是串行的，但**锁在调用返回时就放开了**，而调用方还要接着去
打开、栅格化那个文件。两次导出打同一张图（两个标签页、两套 override）时，
后一次的 worker 会在前一次读它的过程中把它覆盖——第一次于是**静默拿到了
别人那套 override 的图**。

**它不报错。** 出来的是一张完整、合法、但内容属于另一次导出的图。

**裁决：中间产物落进作业私有的临时目录**，名字再加一层随机后缀（同一次合成里
同一张图也可能出现两次，各带一套 override）。

一般化：**「这一步是串行的」推不出「这一步的产物是我的」**——锁保护的是那次
调用，不是调用之后你还要读的那个文件。判据要问的是"这个路径除了我还有谁会
写"，不是"这次调用有没有被别人插队"。

## T-74（Session 12，第五轮评审）同一件事写两遍，两遍都对也会分叉

第四轮：主按钮有 `disabled` 闸，`start()` 没有 → 「覆盖 / 重试」绕过去。
处置是把闸放进 `start()`。

第五轮：两边**都有**闸了，但 `start()` 那份**少了一条**（漏了「原图可不可用」）
→ 同样是「覆盖 / 重试」能起一个界面刚说不可用的导出。

两次是同一个缺陷的两种形态，根都在「同一件事写了两遍」。第一次的处置只解决了
"有没有"，没解决"一不一样"。

**裁决：收敛成一个 `canStart`，主按钮的 `disabled` 与咽喉的闸读同一个值。**
一份判断、两个消费点，就没有"少写一条"这回事了。

与 [[fix-the-predicate-sweep-the-consumers]] 相邻但不同：那条说的是"改了判据要
扫一遍消费点"，这条说的是**判据本来就不该有第二份**——能合并就别扫。

## T-75（Session 12，第六轮评审）「先看一眼再动手」的那一眼和那一手必须同锁

本轨道到这一轮为止，同一个形状出现了**三次**：

| 轮次 | 那一眼 | 那一手 | 中间那道缝里发生什么 |
|---|---|---|---|
| 第一轮 | 查撞名 | 预留 | 两个作业都查到"没撞"，都往下走 |
| 第三轮 | 查 `_committed` | 置 `_cancel` | `cancel()` 回 True 而作业照常 `done` |
| 第六轮 | **取名** | 预留 | 两个 `rename` 选中同一个名字，后一个被报成 `conflict` |

三次的处置都是同一个：**合并进一次持锁**。第一次修完之后我以为那件事结束了，
第三次和第六次说明它没有——**每加一件"动手之前先看的事"，就要重新问一遍它在
不在锁里**。

一般化的判据：一段代码如果先读了一个会被别人改的状态、再据此改状态，那两步
之间任何一次让出都是一个窗口。找它的办法不是想象时序，是**列出这个函数读过
的每一个共享状态，逐个问"读完到用之间，谁能改它"**。

## T-76（Session 12，第六轮评审）判据要落在被修的那个性质上

第六轮的变异反证第一轮有一条存活：「取名与预留分开持锁」。我原本写的是一条
**行为用例**（两个 `rename` 各拿各的编号），而它盖不住那个变异——A 持着预留，
B 无论在锁里还是锁外取名都会看到那个预留，两种实现下结果一样。

真正区分两种实现的是**取名那一刻锁在不在手上**。所以判据换成直接量同步性质
（`_LOCK.locked()`）。

**行为用例能覆盖大多数情形，但当修复改的是「两件事原不原子」时，只有量那件事
本身才分得出来。** 靠 sleep 去撞那道缝的用例更糟：红不红取决于机器。

与 [[predicate-dimension-not-just-subject]] 同族——那条说的是量错了维度，
这条说的是**要修的性质根本不在行为的可观测面上**。

## T-77（Session 13）「没设过」是独立一档，不许压成一个默认值

**问题。** 画布文字要加字体族。最省事的做法是给 `TextObject` 加一个必填的
`fontFamily: 'serif'`，迁移时给每一份老文档补上。

**裁决：可选字段，缺席 = 没设过 = 继承默认族。** 生效值经
`effectiveCanvasFamily()` 现算，**回到默认值时删字段**而不是写一个等价的
显式值。

**为什么。** 「没设过」与「设成了正好等于默认的那个」是两个不同的答案，
差别在**以后**：默认族一旦改（换规范、换 Style、产品换默认），前者跟着走、
后者不跟。把它们压成一个的代价还包括：每一份老文档在打开时被改写一次（迁移
就是一次写盘）、导出载荷凭空多一个字段（老后端拿到的字节不再逐字相同）、
`overrideStateOf` 永远回 `all`（每一行都挂着「已修改」的点和一颗按了没反应
的恢复按钮）。

**同族的**：`italic` 缺席、`lineHeight` 缺席、图内的「脚本值 vs override」、
`ppi: null`（T-60）、`dpi_source: unknown`。见 [[unknown-is-its-own-value]]。

## T-78（Session 13）下拉里的每一项都要有一条「这个运行时画得出它」的判据

**问题。** 「标注能设字体」最自然的实现是列出系统字体。但合成跑在**没有
matplotlib 的 Flask 进程**里（`src/tavotto/AGENTS.md` 的进程边界），画字只能
用 PyMuPDF 自带的 base-14。

**裁决：能选的族是闭集（三个通用族），且与后端的 `CANVAS_TEXT_FAMILIES`
严格同源，顺序也比。**

**为什么。** 一个「选得中但画不出」的选项造成的不是报错，是**静默替换**：
用户点了、界面显示成功了、override 记下了、图重绘了，只有字形没变。这与
`manifest._font_installed()` 当年修掉的那条是同一个缺陷
（`fallback_to_default=False` 就是为它加的）。

**推论**：确实存在但**画不出来**的（脚本写死了一个本机没装的字体）不能悄悄
换掉——**保留名字 + 一条 warning**（`options_unavailable`）。换掉再改文档等于
替用户做了一个他不知道的决定，而那个决定会跟着文档去到装了那个字体的机器上。

## T-79（Session 13）报字段名的、挂锚点的、查选择器的，必须读同一张表

**问题。** ADR 0030 的定位链最后一跳靠 `data-prop` 选择器。本轮开始前它是
**断的**：文字工具条把六条属性从平铺列表里摘走了（平铺那一份有 `data-prop`），
却没有把锚点一起带过来。每一条图内排版问题点「定位」都只选中对象，焦点没
落到字段上——**而 `focusField()` 照样回 true**。

**裁决：property path 只有 `propertyPathOf(kind, prop)` 一份**；控件按它挂
锚点；「平铺列表要让出哪几条」（`TEXT_BAR_PROPS`）**从同一张表算出来**，
不手抄。

**为什么。** 这条缺陷的形状是「搬家时只搬了看得见的那一半」。手抄的第二份
会在加一条属性时忘记更新，症状分两种：忘了加 = 同一个属性出两套控件；
忘了减 = 定位落空。两种都不报错。

**顺带**：`focusField()` 的返回值改成 `none` / `focused` / `requested` 三档。
它以前恒回 true，而注释写着「找不到就如实回 false」——判据修对了不等于它说的
话对（T-66 的同一族）。

## T-80（Session 13）判据里不许自己先把被测的那一步做掉

**问题。** 「连续输入合并成一条历史」这条用例第一版是这么写的：

```ts
adapter.beginGesture()
for (const v of [10, 11, 12, 13, 14]) adapter.write('sizePt', v)
adapter.endGesture()
```

变异反证把 `write()` 里「自己开一轮」那句删掉，**它照样绿**。

**裁决：用例要跑真实调用方会跑的那条路。** 数字框只有**拖动**才发
`onScrubStart`（→ `beginGesture`）；**打字**那条路只有 `onChange`。用例先替
被测代码把手势开好，等于把「它会不会自己开」这件事挡在判据外面。

**为什么值得单独记一条。** 这不是「用例写漏了一个场景」，是**判据预设了
自己的结论**——同一个形状在本轨道已经出现过（[[predicate-assumes-its-conclusion]]、
[[fixture-makes-the-predicate-vacuous]]、[[cache-key-tests-need-a-warm-cache]]）。
识别信号是：**准备阶段调用了被测模块自己的东西**。改法是把准备阶段换成
「真实调用方在这一刻会做的事」，不是加一条新用例。

## T-81（Session 14）先量，再做——前提被推翻了一半

**问题。** Prompt 14 的前提是「特殊字符在预览或导出中出现黑色方框」。照着这
句话做，第一反应是「加一层字体回退」。**实测之后前提只成立一半**：

| 路径 | 实测 |
| --- | --- |
| 画布文字 → PDF | **没有方框**——PyMuPDF 自己挑了一张 `Noto Serif Regular` 画出来了 |
| 图内文字 + 默认族 | **没有方框**（DejaVu 盖得住，中日韩除外） |
| 图内文字 + Times New Roman | **有方框**：`⁵` `⁻` `₂` 的暗像素数一模一样（3551）= 同一个 .notdef 框 |

**裁决：真正的缺陷是「没有人知道刚才发生了什么」，不是「渲染器不会回退」。**
画布那条路一直在回退，只是**回退脸与请求的族和字重无关**（六种组合永远回
`Noto Serif Regular`），而没有任何人被告知；图内那条路则连问都没问过，
matplotlib 明确 warn 了是哪个码位缺在哪个字体，Tavotto 把这条信息丢掉了。

**为什么值得记一条。** 按原前提做会做出一个更差的产品：它会在一个本来没坏的
地方（画布回退）加一层新机制，而真正坏的地方（图内没有判据）一行都不碰。
同一形状见 [[measure-dont-trust-the-comment]]、[[simulated-input-shape-lies]]。

## T-82（Session 14）合成上下标是有代价的，代价在 PDF 文本层里

**问题。** 「把 Unicode 上标折成合成上下标」看起来是纯赚：字体统一、基线正确、
不依赖任何回退脸。第一版就是无条件折的。

**实测发现它把 `×10⁵` 的 PDF 文本层变成了 `×105`。** 审稿人复制走的是 105。

**裁决：默认档只救「不然就是方框」的，一律合成变成用户明确选的一档。**

```text
auto（默认）  只有这一串里有字符谁都画不出时才合成 —— 今天画得对的东西
              一个像素不变，文本层也一个字符不变
scientific    认得的一律合成 —— 字体统一，代价写在 tooltip 里
```

**为什么。** 优先级表（`00_SHARED_RULES` §2）里「导出结果正确」排在「视觉
精简」前面，而文本层的语义损坏就是导出结果不正确的一种——它比「上标是另一张
脸画的」严重，因为后者看得见、前者看不见。

**顺带**：`m²` 那种 base-14 自己画得出的**设计好的**上标字形两档都不动——把好
排版换成合成排版是纯亏。而且**整串一起折**：`m⁻²` 里 `⁻` 画不出、`²` 画得出，
逐字符处理会得到一个 62% 的合成减号紧挨着一个全尺寸的设计上标。

## T-83（Session 14）算法可以同源，oracle 可以不同源——但差异要被单独看住

**问题。** 「这个字符导出后是不是方框」必须在**点导出之前**说得出来，而浏览器
里没有字体引擎。判据只能有两份。

**裁决：算法严格同源，oracle 刻意不同源，差异由一道单独的门禁看住。**

```text
算法   glyphplan.py            ↔  glyphPlan.ts          严格同源（golden vectors）
oracle 真字体（has_glyph）      ≠  canvas_coverage.json  刻意不同源
看护   scripts/gen_canvas_coverage.py --check（表 vs 真字体）
```

真正落笔的 `pdfbackend` 永远问真字体，所以导出那一端不会错。表漂了的表现是
「预览说画得出、导出上是个方框」——那正是上面两道门禁盯着的东西。

**预检两侧都读表**，不是「Python 侧问真字体更准所以让它问」：两个求值器要给出
**同一个**答案，让其中一个更准只会在漂移时制造两个互相矛盾的结论，而漂移本身
已经被单独看住了。

**顺带一条差点漏掉的**：覆盖表的裁剪条件必须**逐字复刻「走到那一步的前提」**。
第一版把 `fallback` 层裁成「primary 与 cjk 都没有」，而 `layer_of` 的第 2 步
带着 `cp > CJK_START` 的限制——`₂`（U+2082）因此会被前端判成 `cjk`、后端判成
`fallback`：一个**只在下标字符上发作**的两侧分歧。

## T-85（Session 15）派生显示不进文档

**问题。** 图例示意线要跟着源曲线变。最直接的做法是「源一变就把新值写进
图例项的 override」——每次改颜色多一条历史、文档里多一份复制值，而且一旦
用户在图例项上自己改过，两份值从此失联。

**裁决：跟随是派生显示。** 示意线在每次 `apply()` 尾部从源**重新派生**
（`sync_legends`），不进 `applied`、不进文档、不产生历史；文档里只记用户自己
表过态的东西（示意线样式 override、显式的 binding）。「热态 == 文档重放 == 写回
== 重开」照旧成立，因为派生走的是同一条 `apply()`。

**为什么。** 复制值是噪声，噪声会淹没用户自己的改动；派生值没有身份，撤销
时也不需要为它负责。

## T-86（Session 15）脱开的那一刻，基准是「源此刻」不是「脚本原样」

**问题。** 先把曲线改绿（图例项跟着变绿），再在图例项上改线宽（脱开），再改
列数重建：脱开的项该是什么颜色？

**裁决：绿。** 脱开点 `custom_base` 记的是脱开那一刻**从源派生**出来的样子，
不是脚本原样；重建从它出发再重放 override。而且必须从源**现派生**、不能拿
盒里那份——同一批 patch 里源的改动可能排在前面，而跟随同步要到整轮结束才
跑，盒里那份此刻还是上一轮的。第一版拿盒里那份，用例当场红（一批里
「先改绿再改线宽」得到一条红线）。

## T-87（Session 15）绑错一条比不绑更坏

**问题。** 两条同色同型同名的曲线，图例上两项 label 与指纹都并列。

**裁决：并列时只认 `get_legend_handles_labels()` 的位置对得上的那个**，否则不绑
（显示「未关联」，示意线照常可编辑）。「尽可能建立绑定」的边界是「绝不伪造」：
绑错的表现是改第二条线、第一项跟着变，而且没有任何提示——比一个「未关联」
徽标坏得多。

## T-88（Session 15）「已知缺陷」的成因要重新量

**问题。** `docs/1.0-release-readiness.md` §4.1 记着图例重建「不是幂等的，
`_init_legend_box` 本身复现不出当初那次布局」，附两组实测。

**裁决：喂错了素材，不是布局不可复现。** 把示意线**副本**喂回去会复制两次
（误差棒退化、markerscale 复利、标题字号丢）；从源对象或脚本原样快照派生，
撤销到底逐位回原样，豁免删掉。当年那条「喂回 `get_legend_handles_labels()`
会撑高 21px」在 InvCont 上复现不出（67 → 67）——成因没重新定位，只能写
「现在这条路上没有它」，不能写一个猜出来的理由。

## T-84（Session 14）报一盏没有开关的红灯，比不报更坏

**问题。** 中文轴标题在默认族上是方框。把它报成 `glyph-missing` 很容易；难的
是**用户拿它怎么办**——字体下拉里当时只有 `serif` / `sans-serif` / `monospace`
和 Times / Arial / Helvetica，一个都画不出汉字。

**裁决：新增一条能违反规则的判据时，同时确认「修它的那个动作存在」。**
本轮的处置是把字体下拉的候选名单补上中日韩字体（名字取自出版规范的
`cjk_fallback.accepted`，**按运行时探测过滤**——列出来的必须画得出，T-78）。

**明确没做的：自动挑一个中文字体当回退。** 那会让同一份文档在两台机器上画出
不同的字（macOS 上是 PingFang、Windows 上是雅黑、Linux 上什么都没有）。
拉丁那条尾巴只放 matplotlib 自带的 DejaVu Sans——它在每个平台上都在，回退
结果是确定的。

**为什么。** 一盏没有开关的红灯会训练用户忽略整个问题面板，而那面板里还有
别的、修得动的问题。这与 [[p2-needs-an-exit-not-a-file]] 是同一条：
「已记录」不是关闭理由。

**同一条的另一面（本轮踩到的）**：`glyph-substituted` 第一版把 `cjk` 层也算
进去了，于是**每一条中文标注都挂一条建议**——而中日韩在画布这条路上只有一张
脸，它不随用户的任何选择变化。「说了也改不动」与「报了没有开关」是同一件事的
两种形状：前者用户改不动，后者产品没给开关。判据因此收紧到 `fallback` 层——
那张脸是渲染器**自己挑的**，与请求的族和字重都无关，所以一个符号会让整段文字
里冒出另一种字体，而且用户**改得动**（换 `interpretation`）。

## T-89（Session 16）命中区按视觉语义分带，带宽按屏幕像素定

**问题。** 刻度朝内时短线画在框里，而示意图的刻度命中区写死在框外——用户点
着看得见的那排短线什么都不发生，得去点框外的空白。画布上则根本没有刻度线的
命中（`ticks` 伪元素的框圈的是刻度文字）。

**裁决：每条直角边框分三个带——内侧控向内刻度、外侧控向外刻度、线本身选中
子图；带宽以屏幕像素计（鼠标 2.5 / 10 px，手指 4 / 18 px）。** 边框线端点由引擎
按画出来的那条线下发（含偏出去的边框），命中函数是纯的、不知道 zoom 与旋转：
zoom 由调用方换算成「一个分数单位 = 几个屏幕像素」，旋转由命中层反旋转。
devicePixelRatio 不进判据——指针坐标本来就是 CSS 像素。

**为什么。** 「点哪里」必须与「看见什么」一致；固定像素带在放大时不会宽到吃
掉图内的点击、缩小时不会窄到点不中。高亮条与命中带用同一把尺换算，逐像素
重合——画的与点的是同一个东西。

**优先级。** 文字 / 曲线 / 别的子图 / 刻度文字 / resize 手柄永远在边框命中区之上：
只有 `pickElement` 命中 figure 或那条边所属的子图本身时命中区才生效。角落并列
取更近的边，等距先取此刻画着刻度的边，再按固定次序——同一个点两次点击不能
落到两条边上。

## T-90（Session 16）按边切换映射回「轴的方向 + 边的显隐」，连带要说出来

**问题。** Prompt 的模型是每边各自的 inward / outward；matplotlib 的 `direction`
却是**一条轴**的（上下共用、左右共用，`tick_params` 没有按边分方向的入口），
只有显不显示是边的（`ticks_<side>`）。

**裁决：状态是派生的（`inward = 边可见 && 方向含 in`），切换映射成两个真旋钮；
方向那一步连带到的同轴另一边写进计划的 `effect.coupled`，hover 文字点名、示意图
tooltip 点名、连带的带浅色一起亮。** 不做按 Tick 对象逐个改 marker 的 hack：
刻度对象会在换 locator / 换 scale 时整组重建，那种「支持」下一帧就没了。

**映射规则。** 开着 → 关：另一方向还开着只改方向（inout → 单向），另一方向也没
开就关掉这一边（方向不动）。关着 → 开：这一边隐藏先打开；方向 = 轴上已含另一
方向 ? inout : 这一方向（加一个方向，不拿走另一个）。属性页的「隐藏」是派生态
（两边都不显示），从它选回方向时**删**两边的 override 回到脚本的边，不猜。

**一次点击一次 commit。** 方向落刻度元素、显隐落子图，两条 override 分属两个
gid；拆成两步会渲染出一帧「边开了、方向还是旧的」，撤销栈也多一条。画布命中区、
示意图、刻度卡三处都读同一份模型、走同一份计划函数、同一个 action——「Inspector
与直接操作同源」不是「两边都改对了」，是只有一份。

**顺带修的一条混淆。** `length` / `width` 此前 `which="both"`：改主刻度长度会把
次刻度一起拉长，「主 / 次」的区分在界面上就此消失。改成只动主刻度（与
`tick_params` 默认同口径），次刻度另有 `minor_length` / `minor_width`。这是语义
变化，存量文档里带这两条 override 且开着次刻度的图，次刻度会回到脚本自己的长度
——写进 ADR 0035 §5，不静默。

## T-91（Session 17）浮动栏只发意图，几何在 action 里

**问题。** 多选浮动栏很容易写成「按钮里算新 x/y 再 commit」——它离数据近、看起来
只是几行。

**裁决：浮动栏、属性页、（18 的）右键菜单三个入口都只调 `alignSelectedTo` /
`groupSelected` / `ungroupSelected`；按钮表（图标 / 顺序 / 最少对象数）在
`arrangeButtons.ts` 一份。** 判据不是「两边都改对了」，是只有一份：用例里拿浮动栏
点出来的历史标签与直接调 action 的逐字比。顺带把两条 action 层的缺口补上：对齐
此前会挪锁定对象（拖动不会），也不收开着的手势——这两件事以前只有属性页一个
入口时没人撞见，多一个入口就暴露了。

## T-92（Session 17）参照是 UI 会话状态，只有一份

**问题。** 参照（选区 / 画布 / 主选）原来是 `ArrangeSection` 的模块级变量；第二个
入口要读它就得再抄一份，而两份的表现是「浮动栏按画布对齐、属性页显示着选区」。

**裁决：`store/arrangeStore`。不进文档（它不是文档内容）、不进撤销（换参照不占历史）、
不 persist（是「这一轮想按什么对齐」，不是长期偏好）、切文档不重置（同一次会话手感
连续）；存枚举不存翻译。** 两个入口双向同步有用例钉着。

## T-93（Session 17）活动信号现在就接进 action，但它不是遥测

**问题。** Prompt 21 的 coachmark 要知道「用户已经自己对齐过一次了」。两条路：
onboarding 去 import 核心 action 的结果，或 action 发一声。前者把 onboarding 拖进
核心依赖图。

**裁决：`lib/activity.ts` 的 `tavotto:activity` 本地 CustomEvent，现在就从三个 action
里发。** detail 是闭集 `kind` + 枚举 + 计数，无对象 id / 文字 / 文件名；派发失败被吞，
不影响动作；只在本进程 window 上，不落盘不出网。它**不是** ADR 0016 的诊断事件，
也**不是**遥测——要遥测走 `telemetryStore` 那条经用户同意的路。没有选「先只留锚点」：
三行代码，晚接一轮只是让 21 再来碰一次 `actions.ts`。

## T-94（Session 17）气泡不是控件，连定位外壳一起不吃指针

**问题。** 真浏览器里弹层自动聚焦第一个分段项，它的 tooltip 停在下一排按钮上，点击
落在气泡上什么都不发生。属性页里键盘 Tab 到分段项也是同一件事，只是没人用键盘
走到那里过。

**裁决：Tooltip 内容与 Radix 的 `data-radix-popper-content-wrapper` 外壳一起
`pointer-events: none`（`:has([role='tooltip'])` 只选到气泡的外壳）。** 不改成「不
自动聚焦」——那会让键盘用户进不了弹层。这一条在 jsdom 里量不到，是 Playwright 的
`intercepts pointer events` 抓到的。
