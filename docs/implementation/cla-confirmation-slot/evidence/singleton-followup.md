# Follow-up: singleton-pointer representation

Same base `a4695f830d321ffa03184595afd895d2055db3b3`. Parent is replacing the draft added journal columns with an additive `slot_policy` singleton and a virtual slot projection. This note reviews the representation and execution order, not a finalized implementation: at the source read the workspace still contained the earlier column-based draft and was being rewritten.

The singleton pointer can enforce one global owner without changing copied journal columns, so it avoids broadening the migration tool's strict `send_until=0` added-column whitelist. This is viable subject to the following safeguards:

- `slot_policy` has exactly id 1, immutable protocol/first attempt/created, nullable active-attempt FK. BEFORE INSERT rejects an existing singleton including REPLACE. UPDATE accepts only a fully authorized free-to-new-issued transition or exact negative-witness held-to-NULL transition; DELETE rejects. NULL comparisons use `IS` / `IS NOT`, and complete permissions require `coalesce(predicate,0)=1`.
- The exact `confirmation-slot:<new-id>` marker is inserted by the issued transaction, remains present while all policy guards run, and is consumed by that journal's AFTER INSERT trigger. An existing journal id must abort rather than turn an INSERT OR IGNORE into a committed marker-only no-op. A marker is neither a long-lived reservation nor a substitute for current head/revision/lease guards.
- During AFTER INSERT, the candidate is already visible. Any legacy-unresolved-success query in policy guards must exclude this candidate's id. Initial policy enrollment already assigning active=new-id must not then perform a prohibited held-to-same-id no-op; subsequent assignment should target only active IS NULL. Marker deletion comes last.
- Same-id journal REPLACE must not implicitly delete an active or released-history row. Protect the active owner's original tuple and its known run id, and protect a released row's exact canonical negative observation forever. Reusing `observation` is safe only if generic failure/defer/manual updates cannot erase that history marker after release.
- A baseline binary may set a held row phase to resolved using a plain observation but must leave the pointer occupied. The new binary must still select this owner, even if a later row exists, and must do so when the runtime flag is false. All journal readers used for reconciliation must derive the virtual slot from the pointer; no reliance on an absent optional JS field.
- Clearing the pointer requires a single UPDATE carrying canonical negative evidence and the subsequent trigger, all in the original settlement transaction. SQL verifies exact original identity/proof/expiry/run, observed phase, fresh observation and source, current recovery revision/lease/generation, and no live fence. Current recovery revision may differ from original publication revision. A stale snapshot or zero-row CAS aborts the whole batch, including observation, pointer and progress.
- Holder positive publishing remains explicitly rejected in slot mode until equivalent send-fence/budget coverage exists; negative recovery and personal signing are separate and remain available. The lattice is one-way even after valid release or flag disable.

The current adapter draft's invocation-local private WeakMap, same shared budget, single-use witness, cloned snapshot/context and 10-second negative-GET freshness are appropriate ingredients. They still require implementation-specific negative tests; no successful product test was run or inferred during this review.

Formal tests should adapt the existing plan to inspect the pointer rather than a journal column, verify marker absence after success/no-op/abort, compare every copied source column and rowid after migration, and count the extra outer marker INSERT against the unchanged 20-work / 40-total limits. Database trigger work is not an extra outer metered call but is not a zero-cost platform guarantee.
