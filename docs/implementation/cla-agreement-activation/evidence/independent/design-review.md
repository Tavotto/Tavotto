# Read-only security design review: persisted CLA agreement activation

Base: /workspace/Tavotto-cla-agreement-activation, #1161 head 6d8809f03150b762cfafeacdaf89af6c9c9bbc05. This is a design review before the new implementation exists, not a claim that new runtime tests passed. No implementation/worktree/GitHub edits, HTTP, worker.fetch, publishing, downloads, credentials or real signatures.

The proposed append-only active bundle journal, explicit default-off environment capability, exact new Config pin and atomic evidence revision switch are appropriate. Keep the original registry/evidence immutable and retain existing proof protocols. Below are required boundaries and concrete test subjects.

1. Old binary compatibility needs a registry fence. Old native/store.ts:33-36 knows no new table and only asks count(agreements)=2 plus the two configured tuples. A first anchor for the original two 1.0 tuples would NOT fence an old binary even if new flagoff code rejects it. First successful activation must atomically leave >2 real immutable agreement rows; parent has accepted this restriction. Verify real new bytes/hash/version markers for both proposed documents and reject a source-only first anchor. Never add sentinel agreements. Keep a compatibility test using the old exact readiness predicate after activation; it must return false. Additional immutable history keeps this fence effective thereafter.

2. Three readiness states are separate test subjects. Legacy/no anchor/flagoff retains 1.0 behavior. Any anchor/flagoff must refuse readiness regardless of matching old tuples or JSON activation values. Flagon must require exact LATEST anchor hash, holder ID/name, repository ID/name, reference SHA, canonical pinned policy and two exact current tuples, allowing retained historical rows. Old flagon config must reject after later activation. Test stale hash and unchanged current agreement bytes with a newer metadata activation too. The environment parser must override JSON's enabled=true to false when the env flag is absent or not exactly 'true'. Hash shape and bounded stable numeric versions must be checked without widening the frozen/default validation path.

3. Anchor revision is the activation event's revision, not a permanent equality requirement. At insertion anchor.revision must equal the post-CAS current revision; later signing/hold/revoke increments are normal. Runtime readiness may require state.revision >= latest anchor.revision, never equality. Test current configuration remains ready after one ordinary subsequent revision change while old pre-activation proof/revision is invalid.

4. Activation source and document original source differ. native/store.ts:93-96 preserves the FIRST agreement_documents.source_sha while accepting a later observation of identical bytes. Preserve that old row exactly. A new anchor must either bind the actual retained document source after prepare reads it, or name current observation and retained source separately. Do not INSERT OR IGNORE and then claim a newer source was stored in the old document. Document digest=SHA256(raw UTF-8 bytes) is distinct from source_sha=40-hex Git commit. Do not require the original corporate document's source to equal a later Config.referenceSha just because individual terms changed. Test unchanged corporate bytes with original source A and new approved observation/reference B: original row stays A; anchor's explicit semantics and subsequent readiness must agree. A 40-hex source field plus content hash is a provenance pin supplied to an internal API; absent local Git-object verification it is not independent proof that a commit contains those bytes.

5. Apply must revalidate prepared objects. A returned prepared JS object is mutable. Recompute canonical body hash; reject changed content, tuple, source, generation, predecessor, revision, config or hash. Do not include the activationHash itself in its canonical preimage. Require exact field sets and bounded sizes. Check body against all redundant row columns. Version marker must be exact and unambiguous (one expected marker), and raw bytes must hash exactly. Same kind/version with changed digest must reject, including a non-material-looking change; do not resolve the legal documentation's version/hash policy contradiction in this engineering change.

6. Existing guard/CAS transactions provide rollback. The exact transaction subject is old latest activation identity + expected state revision. Validate old selection before insert, append two agreement/document candidates with immutable conflict checks, CAS revision once, append the exact next anchor, and guard predecessor/order/tuples/content/>2 registry within the same batch. Test forced failure AFTER the agreement/doc inserts and AFTER CAS; registry rows, documents, state revision, journal, head request observations and outbox must all equal their pre-call snapshots. SQL uniqueness/order triggers should reject branches and gaps. New tables/triggers/indexes must be included in nativeSQL namespace handling and source schema/migration tests.

7. Retry semantics need latest identity. Once apply succeeds, retrying the ORIGINAL proposal has its old expectedRevision; do not run old Config.assertReady or fail expectedRevision before the explicitly validated identical-latest no-op branch. Exact duplicate must yield no new revision/row/outbox generation. A prior hash merely found in history after a later anchor must reject as superseded rather than claim it is currently active. Concurrent different proposals: one applies, one rejects. Concurrent identical proposals: one applies and the other is an explicit validated already-applied result, or the rejected contender can be retried for that result; do not relabel an uncertain transaction error without checking the stored exact latest outcome.

8. Final packet and intent guards must check TWO subjects. Readiness establishes that Store.expectedConfig is current. It does not prove that a supplied Packet belongs to that config. In the same existing packet guard, check p.kind/version/digest against the current tuple. In the intent guard check the REAL stored packet's tuple for contributor/holder roles; allow historical packets for role='hold' so migration does not remove an existing party's review path. Test new/current LiveStore + old Packet directly, separately from old Store + old Packet. Keep service.currentPacket checks. Sign and receipt CAS must reject an activation occurring after their pre-read; do not extend/copy old consent.

9. Historical consent and grants retain exact identity. Snapshot all original columns/bytes/rowids for packets, personal signatures, agreement documents, grants/controls/receipts before/after activation. New packet has zero personal signatures and receipts until new consent. Old complete personal packet remains auditable but cannot qualify for new digest. Old grant cannot countersign new terms; no new grant is manufactured. Historical revocation from #1161 must work under the NEW ready config with the stored old key and original registry tuple; its cap-100/identity/key limitations stay explicit. Holds remain subject-wide. No capability flips, holder transfer, cross-version acceptance or legal approval is implied.

10. Whole-invocation SQL budget, not just transaction count. A roughly ten-statement mutation batch can fit, but account for readiness, database clock, revision/latest, existing document/provenance reads and confirmation/no-op readbacks too. Use existing InvocationBudget and meterDatabase to test total SQL <=20 work / <=40 settlement; do not raise ceilings or add a new private unmetered database path. Fold final activation checks into existing packet/intent guards. Existing automatic/verification admission accounting must remain true at their existing contributor boundaries. Returning a bounded anchor body in the existing readiness/revision SELECT can permit JS hash validation without another SQL read.

11. Runtime anchor integrity should have an explicit trust statement. Merely matching the stored hash column to Config.agreementActivationHash does not itself recompute SHA256(body). Preferred: existing readiness/revision SELECT also returns the bounded latest canonical body, and JS validates body/hash/columns without extra SQL. Final mutations can compare the already validated immutable latest identity and tuple in SQL. If runtime relies solely on the invariant that only validated apply can insert immutable rows, document that boundary and do not claim tests prove detection of inconsistent stored body/hash. Apply must reject tampered prepared values either way.

12. Existing in-flight publication handling stays unchanged. Activation revision triggers may invalidate local observations and enqueue existing recovery, but must not clear send fences, issue a second POST, drop an issued/unknown attempt, release manual state or extend an old proof. Use only fixed-time synthetic pre-existing journal rows and local SQL/qualification assertions to test these facts. Do not execute the prohibited dynamic-success-publication-across-expiry scenario, worker.fetch, any HTTP route or remote publication/readback.

13. Legacy bootstrap must explicitly reject anchors in the final same transaction, not only in a pre-read. It should remain fresh/legacy initialization, not a hidden activation writer. Deployment templates and the offline disabled-manifest validator must include the new env flag as exactly false. Existing v1-to-v2 offline snapshot migration must leave anchors empty, preserve every existing column/row unchanged and not assert current eligibility. Old schema lacking the new table should fail closed until explicitly migrated; there is no automatic schema install or live fallback.

Focused falsification suggestions, each on an isolated local copy: omit latest hash from readiness; remove flagoff NOT EXISTS; permit first registry count=2; replace exact tuple with version-only; omit mutation p tuple; drop CAS revision/predecessor check; ignore one proposed document's content hash; overwrite/claim a new source on an existing digest; make anchor revision runtime equality; or classify any historical duplicate as current. Prove the transform landed at the intended function, then record a nonzero targeted test exit. No HTTP or publishing test is necessary.

Remaining decisions are product/legal rather than implementation choices: actual text and version, authority/approval to activate, whether historical consent covers any contribution, simultaneous accepted versions, identity/counterparty changes, and real deployments/credentials. This review approves no such operation. No design-analysis blocker remains after the parent accepted the initial >2 registry fence.
