# CI05 · 用同等覆盖取得提速证据并交接 U00

依赖CI01–03。CI04按实际部署状态交接，不把未部署当通过，也不把它当整项重构的无限前置。

## 实际实施

1. 固定当前policy/coverage与候选SHA，对照改造前后同类工作负载。可使用有限的安全合成改动分别代表Python、UI、跨语言/打包和并发多个PR，不自动推送这些PR；无写权限时交人工执行步骤。
2. 同时比较快速可行动反馈、完整合并资格、总job资源分钟和runner队列。CI样本记录checkoutSHA、依赖锁、image、平台、冷暖及并行槽数；样本不足不计算虚假的百分位。
3. 三种演练：同PR连续push；多个不同PR并行；merge_group与日常lab/夜间同时到达。验证取消与队列保留，确认required判定真实完整，观察哪个资源成为新的瓶颈。
4. 完成当前覆盖迁移检查，尚未实现的FirstOpen/RenderCore不在本次成功分子；既有required失败不可重新标observing。对有意改变的执行时机保留理由和审批。
5. 新增确定负例：一个缺shard、一个坏artifact、一个TypeScript真错误、一个跨任务污染、一个误取消/错事件配置。至少证明相关判据变红，不只说“加了反例”。
6. 作一次可逆route/shard回退演练。失败路径恢复到已验证配置并重跑同SHA，旧报告不复用。安全秘密或真实数据不得参与演练。
7. 写CI_HANDOFF.md与最小统一计划入口更新，正式说明ci_hosted_ready与runner_pool_ready的独立状态。U00从新基线继续，后续U01复用本轮有效接口不新造CI系统。

## 达到何种程度就停止前置优化

关键串行依赖已解除或有测量证明保留的合理性；至少一个长测试族在可用环境里完成受控分片；现有支持的合并前覆盖不缩小；取消/身份/隔离可信；剩余风险和实际耗时明确。不能为了逼近2分钟而继续扩大前置范围。

通过与否基于真实记录，不承诺固定2×。未达到速度目标时可以给出“正确性合格、收益有限，需要不同OS资源/减少特定fixture开销”的事实结论，但不能把未测目标称通过。

## 交付

真实代码改动、workflow/判定测试、覆盖映射、计时和资源原始数据、分片报告、admin待办、CI_HANDOFF、回退方式。是否合并、创建VM、发布仍由用户另行授权；本阶段不碰PyMuPDF产品代码和LICENSE。
