# Runner 容量、机器边界和运维

## 1. 两种拓扑，不把现有lab直接切成PR池

**优先：保留当前可信lab资格VM；从额外资源新建平行CI容量。**
```
原hypervisor / 额外主机（实际容量由管理员核验）
 ├─ 现有lab资格VM：沿用受信main/发行用途与原性能基线
 ├─ 新PR执行槽 fast-01：可销毁VM，一次一个job
 ├─ 新PR执行槽 fast-02：可销毁VM，一次一个job
 └─ 新执行槽 heavy-01：可销毁VM，一次一个job
GitHub-hosted：继续承接默认PR、缺失容量、Windows/macOS/CodeQL与签名渠道
```

每次job从干净模板启动、结束销毁/还原；“fast-01”是容量角色，可不是永久复用同一脏磁盘的运行身份。默认先开1个槽做试点，再2个，再按资源加第3个。

若某个**新的总池**只有16vCPU/32GiB，预算起点可用：
| 用途 | vCPU配额 | 内存 |
|---|---:|---:|
| fast-01 | 3 | 6GiB |
| fast-02 | 3 | 6GiB |
| heavy-01 | 8 | 14GiB |
| 未分配余量 | 2 | 6GiB |

这不是已证足够的配置，不代表独占物理核心，也不包含原lab再并行运行的额外资源。如果heavy峰值超预算，先调整为2个槽或增内存，不用swap硬撑。原建议低配28GiB、高配34GiB；不能按高配在32GiB上同时承诺，更不能忽略宿主其他VM。

16/32若本来只是一个guest，增加同级VM须由原hypervisor调配；不默认在guest里再造嵌套虚拟化。需要记录CPU型号、物理/虚拟核心、超分配、内存硬上限、磁盘IOPS/空间、网络及其他常驻负载。

Windows E2E是已观察样本的长路径之一。单纯增加Linux槽不会让Windows/macOS原生资格更快。新增Windows VM应与实际x64平台和系统使用条件相符；macOS arm64继续在真实对应Mac或GitHub支持目标上测，不用Linux容器假冒。

## 2. 一台runner跑job，不是永久分给一个PR

3个槽不保证3个PR各拿1个：同一PR矩阵可以占满。`strategy.max-parallel`只限制该矩阵，不限制所有workflow总CPU，不创建runner，不解决任务优先级。

初期保留便宜质量检查在hosted；对本地池分别声明fast/heavy可承载类型与并行上限。集成候选不能被无限nightly任务饿死。不得给所有任务相同heavy标签；标签表示可路由能力，不是安全授权。只有一种slowjob也不必硬保留闲置2fast+1heavy，应按实际到达负载调整。

## 3. 三个信任区

**A GitHub-hosted**：保持公开PR的默认安全执行区。不因本计划改用pull_request_target来取得更多权限。

**B 可销毁PR池**：无真实数据、内网权限、发布凭据、长期仓库写密钥。VM不得挂宿主根目录、Docker socket、实验室共享盘；阻断访问敏感内网/云metadata服务，必要出站按管理员规则。一个job一个独立VM和一次性注册；JIT/ephemeral注销并不自动清磁盘，必须由外部控制面保证清洁。[W02/W03]

**C 可信lab与发行**：保留原来严格的信任检查；PR/merge_group不能因为“作者是自己”“同仓分支”“进入合并队列”就被当作已经合入可信main。保护后的tag也要以真实授权政策核验，不因任何人能造同名tag就放行。

现有仓库文档禁止PR触发到常驻lab。若引入B，ADR明确仅新增B，不删除C的限制。通过组织runner group/限定workflow/独立私有infra仓库等**PR不可随意改写的控制**确保PR无法要求`runs-on:tavotto-lab`来接触C。若当前账户能力不能形成该边界，保持PR在hosted，私有池仅承接受信任务，不冒险发布新路由。

runner注册/编排凭据留在管理面，不进入执行VM或模板；模板里不保存已注册runner、token、SSH仓库写密钥。上传失败日志前脱敏。不要把PR构建出的可执行文件或缓存直接交给拥有签名/发布凭据的后续job当可信代码执行。

## 4. 缓存预热与预装

干净镜像可预装固定toolchain、Node/pnpm、Python toolcache、编译器、浏览器运行依赖及批准字体。镜像记录版本和hash，更新受控。预装不意味着永远不跑锁文件安装；仍核验依赖闭包与工具版本。不能把全局pip环境作为所有项目共享可变容器。

Playwright浏览器随所用包版本匹配；预热镜像与每次下载/缓存恢复谁更快应测量，不能先认定缓存必然更快。新生VM从只读或可信内容缓存获取依赖，PR不能污染后续发行使用的共享可执行缓存。

GitHub runner自身需按官方更新要求维护；长久冻结旧runner会无法接单。镜像升级独立于产品科学依赖升级。[W03]

## 5. 网络与原有lab约束

仓库文档记录实验室github.com直连存在限制，并使用不同下载/checkout路线。那是历史记录，不是本次联网实测。试点先验证checkout、actions下载、artifacts、PyPI/npm/crates/浏览器等真实链；若网络更慢，自托管可能得不偿失。[G08]

不关闭TLS验证、不固定不明IP、不把lab的长期SSH凭据复制到PR镜像。不能为CI吞吐删除原发行flock。性能基准若共享物理宿主并发负载，独立VM仍有噪声；需要保留独占测量窗口或明确记录负载，不与安静旧基线机械比较。

## 6. 掉线与容量退出

在创建job前选择已启用的执行路线，默认hosted。`runs-on`标签不是“先等本地几分钟再自动换hosted”的备选列表。尚未部署/离线池不进入强制默认路由。

pilot失败或容量退出时，用已测试的配置回到hosted同等任务；已失败/取消的必需实例仍需重跑相同SHA取得资格。不能因为本地离线就跳过资格。容量状态和路由决定要可见，但不为本轮自研复杂抢占调度系统。
