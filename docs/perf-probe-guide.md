# 拖动卡顿排查：性能探针使用说明

用户说「拖动一卡一卡的」，而开发机上复现不了——卡顿取决于**那台 Mac、那份图**。
性能探针在用户自己的 Tavotto 里量出每一帧时间花在哪，存成一个只含数字的文件；
开发者用 `scripts/perf_report.py` 读它，得到按严重程度排好的卡点、代码位置和改法。
设计与取舍见 [ADR 0075](adr/0075-drag-performance-probe.md)。

## 给测试者（发给他们的就是这一节）

需要含性能探针的 Tavotto 版本：设置 → 诊断里能看到「性能分析」一栏。

1. 打开**你觉得卡的那份项目 / 那张图**，进到平时拖动的界面。
2. 设置 → 诊断 → 性能分析 → **开始**。设置会关掉，画布右上角出现「性能分析」面板。
3. 先别动鼠标，等 2 秒（探针在量这台机器空闲时的基线）。
4. **照常拖动**你觉得卡的东西——标题、图例、坐标轴标签、子图、画布上的整张图都行，
   每样拖几秒。面板上的「已记录拖动」会增加。
5. 点**自动测试**，再点一下要测的对象（选你觉得最卡的那个）。接下来约 7 秒请不要
   动鼠标：Tavotto 会自己拖它两轮，然后取消——**不会改动你的图**，也不进撤销历史。
6. 点**完成并保存**。桌面版会在访达里直接选中这份报告（文件名形如
   `tavotto-perf-20260923-142501.json`，存在 `~/Library/Application Support/Tavotto/perf-reports/`；
   访达没弹出来时点面板上的文件名）。浏览器版另外会下载一份。把它发给开发者即可。

报告里只有数字：帧耗时、次数、节点数、机型 / 内存 / 电源状态。没有文件名、图里的
文字、脚本或路径。可以用任何文本编辑器打开检查。

小提示：想知道「是不是电脑的问题」，可以插电 / 拔电、开 / 关低电量模式各录一份。

## 给开发者

```sh
python scripts/perf_report.py tavotto-perf-*.json                 # 终端摘要
python scripts/perf_report.py a.json b.json c.json --html perf.html   # 多台机器对照 + 逐帧图
python scripts/perf_report.py a.json --json findings.json             # 机器可读结论
```

只用标准库，任何 Python 3.10+ 都能跑。

### 怎么读

每份报告先给一张**体检表**：每一维 A–D 加一句依据，没有数据的写「—」。多份报告时，
顶部是一张按同样维度排的机器对照表。

| 维度 | 看什么 |
|---|---|
| 流畅度 | 超时帧比例（帧间隔 > 1.5 倍刷新周期）、>50ms 的帧、最长连续卡了几帧、帧间隔抖动 |
| 响应 | 鼠标一动到画面跟上的延迟（1.5–2 个刷新周期是正常下限）；按下后前三帧有没有顿一下 |
| 余量 | 主线程每帧实际忙多久 → 估计 CPU 慢几倍的机器开始掉帧。**快机器的报告靠这一维才有用** |
| 松手 | 松手后 0.6 秒内的长帧；图内元素松手到后端重画好的等待；上一次松手 1 秒后触发的自动保存（整份文档序列化）是否落进了下一次拖动、花了多久 |
| 稳定性 | 每个 pointermove 的成本随拖动时长增长的斜率（越拖越慢），带绝对增量门槛防量化噪声 |
| 渲染放大 | 拖动中每个 pointermove 引起几次组件渲染：属性页 / 左栏 / 面板本体动了就是浪费；跟手的读数、选框每帧一次是预期 |
| 机器 | 空转时就掉帧、低电量模式、电池、Rosetta、降频、热警告、高分辨率大窗口 |
| 覆盖 | 这份报告够不够下结论：有没有自动测试、图是不是太简单、是不是旧版探针录的 |

体检表下面是**按严重程度排好的卡点**（严重 / 问题 / 提示）。同一个现象出现在好几段拖动里
只报一条，注明出现在哪几段。每条带证据、代码位置和改法，归因类的结论会给：

- 超时帧的时间拆成**输入处理**（业务代码 + React 同步重渲染）、**渲染**（rAF 脚本 + 浏览器样式 / 布局 / 绘制）、
  **未归因**（GC、别的任务、合成器 / GPU，用 Safari 时间线录一次看）；
- 帧间隔与这几项的**相关系数**：谁和卡顿同涨同落，谁就更可能是元凶；
- 最慢的几帧逐帧拆开（第几秒、各段多少毫秒、这一帧来了几个 move）；
- 跨片段看「图的复杂度 ↔ 渲染耗时」是否相关；
- 自动测试 m1 / m3 两轮只差输入频率：m3 明显更差 = pointermove 没有合并到每帧一次。

WebKit 的计时精度是 1ms，单个小数值没有意义；分析器只用总和 / 次数与逐帧量级。

### 本地模拟慢机器

开发机太快时，可以在浏览器版里用 Chromium 的 CPU 限速复现（`./run.sh` 后用 Chrome
打开，DevTools → Performance → CPU 4×/6× slowdown），同样走「设置 → 诊断 → 性能分析」。
Playwright 里是 `Emulation.setCPUThrottlingRate`。注意这量的是 Chromium 不是 WKWebView，
只能当趋势参考；结论以用户机器上的报告为准。
