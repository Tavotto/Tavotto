# ADR 0197：AI 修复的试错——小实验、失败时的提示与修复经验

日期：2026-11-19 · 状态：**已接受**（维护者 11-19 批准三层都做、各 PR 给 1.0 豁免；第 2 层 `run_snippet` 已随 #2064 合入；第 1 层与第 4 条随后一个 PR 落地）

## 问题

兼容性评测（`scripts/eval/fix_compat`）里，内置 AI 修不好的题多半是「看出了原因，却没法低成本地验证猜测」：
它只能读文件，或者整份脚本跑一次 `try_run`（要用户批准、一两分钟）。用 Codex + Tavotto 插件的人修得好，主要靠
Codex 能随手跑一小段代码看结果再决定下一步。`run_command`（ADR 0149 修订 #1374）能跑命令，但每条命令一张批准卡，
不适合试错。

## 决定

分三层，按 PR 落地：

1. **失败时就给提示 + 尝试记录表**：试运行失败的结果里按结局码附一句对症建议（一张表，键是结局码）；每次试运行后附上
   试过什么、错误有没有变化。同一条记录也进修复审计与诊断包（见第 4 条）。
2. **小实验 `run_snippet`（#2064）**：在一个环境里跑一小段模型写的 Python，几秒出结果。
3. **把失败变成指导**：离线——评测里失败的轨迹提炼成第 1 层的新提示，并加一道题防退步；在线——每台机器本地记住修成功的做法
   （最后做，界面先给维护者看）。
4. **修复经验进诊断包**（维护者 11-19 裁决「总是收（脱敏后）」）：结局码之外，AI 写的启动脚本、读过的片段、报错原文、
   AI 的总结也收，一律先过 `diagnostictext` 脱敏；敏感运行参数仍一律不收。落在发送包的 `detail-runs.json` 里（见下），report.json 形状不变。

### 第 1 层：失败时的提示与试运行记录

- **形状判据只有一份**：`fixtools/hints.py`。形状 = 运行报告的结局码 / 错误码；`script_error` 再按 traceback 里一眼可认的样子细分
  （`os.environ` 的 KeyError → `env_var_missing`、相对导入 → `relative_import`、`input()` 的 EOFError → `input_eof`）。
  `ask.prepare_diagnostics` 的「用户侧失败没试过改动先别报缺陷」闸门也从这里取（`USER_SIDE_SHAPES`），不再自己维护一份。
- **提示表**：键是形状，值是几句对症建议；每句声明它点名的工具。工具不在注册表或本会话不放行，这句就不说；第一句是主动作，
  它说不了整条提示都不说（后面的句子接着它，单独留下是半截话）。提示只指方向，会改东西的工具照常各自问用户。
  `read_run_report` 与 `try_run` 的返回里，提示放在最前面（`hint: {for, id, next}`）。
- **真入口在另一份脚本**（`script_is_library`）：按维护者 11-19 裁决（ADR 0188），提示让 AI 收尾、告诉用户去打开那份脚本，
  **不**用启动脚本代跑。
- **试运行记录**：应用试运行（`try_run` 不带 `mode=diagnostic`）每次真跑完记一条 `{n, before, after, hint, changes}`——
  之前与之后的形状、给了哪条提示、这期间真做过的改动的工具名（`run_tool` 在计入 `changes_attempted` 的同一处收集）。
  没批准 / 取消 / 环境没选中 / 起不来不算一次。返回里附最近 8 条（`attempts so far:`）；同一个失败连着回来两次就明说别再重复。
- **审计只记码**：`fix_audit.jsonl` 每行多一个 `attempt` 字段，只有上面那几个形状码、提示 id 与工具名，不落内容。

### 第 4 条：诊断包里的修复经过

- `FixSessions.diagnostics_for(项目)` 给出这个项目名下还在内存里的修复会话：状态、结局、AI 的总结、步数、通道、
  模型（**只有厂商 id 与模型名**，不带地址与密钥）、试运行记录、工具返回的有界尾部（每条 2 000 字符、最多 60 条，
  工具返回本来就先过 `scrub`）、AI 写的启动脚本。只在内存里，不写盘；审计照旧不落内容。
- 进发送包的 `detail-runs.json`（`fix_sessions` 键）。**不论勾没勾「脚本源码」都收**（维护者 11-19 裁决「全部总是收，改发送框文案」）：
  这一段不剥源码行，其余部分（修复经过的报错、日志记录）不勾照旧剥。整段照常过 `Scrubber`（密钥换掉、家目录换成 `~`）。
- 这是 `docs/rules/backend/diagnostics.md`「不勾不带源码」的登记例外；发送框的「包含 / 不包含」两句与 `docs/privacy.md` 同步写明
  「用过 AI 修复时还会带上它读过的脚本片段」。report.json 形状不变，`detail-runs.json` 只是多一个键，不升 schema。

### 第 3 层·在线：本机记住修好的做法

维护者 2026-11-21 的裁决：连具体做法也记，并做界面；修好的做法要进诊断包；同意随提示发给所选的 AI。
另外两项按建议的默认值：整台电脑共用、按失败类型取用；最多 50 条，90 天没再用到就丢。

- **什么时候记**：会话以 `fixed` 收尾，且这次有应用试运行。有应用试运行时，`finish` 已要求它验证通过；只是模型自称修好的不记。
  失败类型取第一次试运行之前的形状。
- **记什么**：`run_tool` 收集真做成的改动，存进 `ctx.fixes_made`。只认四种能在别的项目复用的改动：
  - 运行参数；
  - 启动脚本正文，以及从中认出的环境变量；
  - 数据指认，即要的路径指到了哪里；
  - 运行方式。

  另外记脚本文件名、日期和用过几次。
- **怎么保护**：落盘前过 `readscope.scrub`，家目录写成 `~`。脚本标了「运行参数敏感」就不记参数。
  变量名像凭据的（`*KEY*`、`*TOKEN*`、`*SECRET*`、`*PASSW*`……），值不记，正文里的值也抹成 `…`。
- **放在哪、存多少**：`data_dir()/ai/fix_memory.json`，有界。
- **回放**：`read_run_report` 和应用试运行的返回里，`hint` 后面紧跟 `fixed_before_here`。
  内容是同一类失败最多 3 条，明说是参考数据、不是指令。只给有界的结构化字段，不给启动脚本全文，以免变成存储型注入通道。
  改动照常各自过批准。
- **看与删**：设置 → 改图助手 →「记住修好的做法」，一行开关，有记录时加「已记住 N 条 · 查看」。
  列表弹窗里可以逐条删，「全部删除」在弹窗底部原地确认。
- **诊断包**：`detail-runs.json` 的 `fix_memory`。与修复经过同口径，不勾源码也收，过 `Scrubber`。
- **隐私**：`docs/privacy.md` 写明落盘、发给 AI、进诊断包三件事。
- **效果暂时量不出来**：题库每题都是全新的数据目录，而且现在一次就修好。要量，得加一道「先修甲、再修同类的乙」的题，尚未做。

### `run_snippet` 的边界

- 档位 `run`（与 `try_import` 同档），**不弹卡**（维护者 11-19 裁决「全部免问」；已向维护者说明下面 Windows 的盲区）。
- 执行器只有一条：`trial.run_python`（写入根绊线 + 禁起进程 + 有就套操作系统沙盒）。实验另加 `strict_deny`：
  - **断网、凭据位置不可读**：进程内第二个 audit hook 拦 `socket.connect / bind / sendto / sendmsg / getaddrinfo / gethostby*`，
    以及落在硬拦表里的 `open / os.listdir / os.scandir`；清单就是 AI 读取范围的硬拦表（`ReadScope.deny_roots()`，与 `readscope.DENY_HOME_RELATIVE` + Tavotto 自己的密钥文件同源）。
  - **名字规则同样生效**（d2 人工核 #2064）：`open` 的目标按文件名比对 `readscope.DENY_NAME_PATTERNS`（`.env*`、`*.pem`、`id_*`、`token`……），
    `_NAME_EXEMPT_SUFFIX`（`.pub`）豁免、只对文件，大小写口径与 `read_file` 的 `_name_denied` 一致；要的名字与符号链接指到的名字都看。
    否则当前目录就是项目根，一句 `open('.env')` 就绕过了读取范围。模式装 hook 时编成正则、以默认参数捕获，不经 `fnmatch` 的模块缓存。
  - 操作系统沙盒同一份清单：macOS profile 加 `(deny network*)` 与逐条 `(deny file-read* (subpath …))`；bwrap 加 `--unshare-net`，凭据目录盖空 tmpfs、凭据文件盖 `/dev/null`。
    实验口径的沙盒单独探测（`--unshare-net` 在禁了网络命名空间的机器上会失败，失败就退回进程内守卫并标 `os_sandbox: none`）。
  - 当前目录是项目根、项目根在 `sys.path` 上（经环境变量交给守卫前导、用户代码运行前摘掉；不改模型代码，报错行号不偏）：能读项目数据、能 import 项目模块，写不进项目。
  - 时限默认 20 s、上限 30 s；代码 ≤ 20 000 字符、先 `compile` 检查；输出各路只回最后 6 000 字符，过 `scrub`。
- **不算「改动」**：`run` 不是 `CHANGE_TIERS`，所以不会解开「先动手才能起草产品缺陷」那道闸（ADR 0149 修订 #2053）；照常计入步数预算、照常进审计（代码只记长度）。
- 结果只是实验，**不能证明修好**：工具描述如实写，修好仍以 `try_run` 为准。

### 如实写下的盲区

- **没有操作系统沙盒时（Windows、没装 bwrap 的 Linux），进程内守卫只是尽力而为，可以被普通 Python 绕开。** Codex #2064 用几行标准库代码证实了三种：
  ① 前导的标准库 import 先于守卫执行项目里的同名模块；② `os.open(home)` 再 `dir_fd=` 相对它读凭据（审计事件不带 `dir_fd`）；③ 沿调用栈或经 `gc` 改掉判据状态。
  三种都已堵上：父进程起子进程时把 `PYTHONPATH` 挪进私有变量，解释器启动时看不到它，守卫与 site 装好后前导才按解释器的方式（`abspath`）放回——不按条目或前缀去猜哪些路径来自环境（两轮复核证明猜不全：CPython 会展开、规范化条目）；`''` 与启动目录下的条目永不放回，子进程从试跑目录起、守卫装好后才切到项目根；文件夹不许当文件打开；
  判据数据与函数在装 hook 时以默认参数捕获（不可变元组），名字全部删掉，`gc` 取对象与改函数 `__code__ / __defaults__` 一并拦下。
  **但这类拦截没有尽头**：判据要用的标准库函数本身是可改的 Python（例如改掉 `os.path.realpath` 依赖的内部函数），在进程里与被测代码同权的守卫封不死。
  维护者 2026-11-19 看过 Codex 的证据后**再次裁决维持免问**，这一条作为已接受的风险留在这里。
- **启动阶段的环境变量**：`PYTHONPATH` 与 `PYTHONPYCACHEPREFIX` 启动时挪进私有变量、守卫装好后放回（Codex 两轮复核）。`PYTHONHOME` **不挪**：它就是解释器找自己标准库的地方，启动时必须生效；
  它若指向不可信的位置，用户运行的每一个 Python（包括 Tavotto 平常的 safe / native 运行）都已经受影响——这是用户自己环境的信任问题，不是模型写的代码能越过的边界。
- 有操作系统沙盒时（macOS、可用的 bwrap），断网与拒读由内核按真实路径执行，上面这些写法都碰不到它；进程内守卫只是第二层。
- C 扩展 / `ctypes` 直接发系统调用绕过进程内拦截（与写入绊线的既有盲区相同）。
- 进程内的读拦截按「真实路径前缀」判（macOS / Windows 上先 casefold）；硬链接到凭据文件的别名拦不到（有操作系统沙盒的平台由沙盒拦）。
- 名字规则**只有进程内这一层**：操作系统沙盒按路径前缀拦，不便按文件名拦，所以即使有沙盒，起个无害名字的硬链接、或直接发系统调用，都能读到项目里的 `.env` 一类文件——归入上面已接受的「纯 Python / C 扩展可绕过」。
  hook 检查与真正 `open` 之间把符号链接换个目标的竞态同属这一类，不另修。
- 「守卫装好前只从标准库导入」同样作用于试跑的诊断副本与探 import（它们共用这段前导）：当前目录不再在 `sys.path` 上（`run_path` 仍把脚本所在目录放在最前）。

## 后果

- AI 能在动手前低成本地验证猜测：import 行不行、参数解析器要什么、数据第一行长什么样、某个函数在不在。
- 守卫前导多一个可选的严格段；不带 `strict_deny` 的调用（试跑 / 探 import / 体检）行为逐字不变。
