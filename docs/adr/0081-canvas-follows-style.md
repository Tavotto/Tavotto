# ADR 0081：画布跟随样式——应用 = 绑定，改样式 = 改图

日期：2026-09-24 · 状态：**Accepted**
修订：[0029 Style / Spec / Export 三层](0029-style-spec-profiles.md)（「应用样式 = 一次性的文档修改」改成「画布绑定一套样式、跟随它」；规范那一侧**一个字不动**）
相关：[0023 文档落盘权威](0023-document-persistence-authority.md)、`docs/rules/frontend/project-document-and-autosave.md`（文档变化的三种性质）、
`docs/rules/frontend/readiness-and-left-shell.md`（左栏样式面板）

## 问题

用户原话：「我希望里面的画布功能能够直接联动当前画布，修改标准后，当前画布会自动修改为当前标准，而不是还需要用户手动去调整。」

改造前，样式是一次性的：在样式对话框（或左栏样式面板）里选一套样式、点「应用」，把一批 override 写进文档，然后样式和
画布就再没有关系了。之后改样式，画布上的图不会变，用户要再点一次应用；而且「应用」有三个入口（样式对话框的四档范围、
设置 › 样式页、左栏面板），三处各有各的范围语义。

用户确认了两点：① 只联动**样式**，规范仍然只检查、从不改图；② 范围是**当前画布**。

## 裁决

### 一、画布绑定一套样式（`FigureDocument.style` / `CanvasData.style`）

```jsonc
"style": {
  "id": "s1",                 // 样式库（<data_dir>/profiles/styles.json）里那一条
  "snapshot": { /* 这张画布最后一次对齐到的样式内容 */ },
  "detached": true            // 可选：撤销过样式修改、已脱离（§十二）
}
```

- **可选字段，schema 不升版。** 老文档没有它 = 没绑定，行为与改造前完全相同。后端 `documents.py` 不认识画布里的
  字段，原样保存。
- 形状照抄规范绑定（ADR 0029 §2）：`id` 加上内容快照；判断「样式变没变」看**内容是否不等**（`specBinding.sameRules`），
  不看版本号。库里那一条找不到（换了台电脑 / 被删了）时，快照照样说了算。
- 用户能选的状态只有「绑了」和「没绑」两种。规范有 `follow` 开关，是因为规范的默认立场是「项目结果稳定」；
  样式绑定的意思本来就是「跟着走」，要不跟随就解绑。「已脱离」（§十二）不是开关：只由撤销落下，
  用户重新选一次就回到「绑了」。

### 二、应用 = 绑定，只有一个实现（`store/styleBinding.ts`）

| 时刻 | 写什么 | 历史标签 |
| --- | --- | --- |
| 选一套样式 | 绑定 + 整份样式对齐当前画布上的所有图 | 按样式「X」排版当前画布 |
| 已绑定时在样式面板里改一个值 | 先存进样式库那一条，存成功后改快照，并只对齐改了的那一项 | 修改样式「X」 |
| 库里那一条在别处被改过（设置里保存、另一张画布上改过） | 快照 + 只对齐变了的那几项 | 按样式「X」更新 |
| 绑定画布上一张图第一次拿到 manifest | 只对齐这一张 | 按样式对齐新图 |
| 不跟随样式 | 只解绑，图保持此刻的样子 | 不再跟随样式 |
| 恢复原样 | 清掉整张画布上样式管得到的 override，并解绑 | 恢复原样并解除样式跟随 |

每一行都是**一次** `commit`：绑定、快照和 override 在同一次 commit 里，⌘Z 会把它们一起撤回。

入口收成一套（「同类控件出现第二套先删第二套」）：

- 左栏样式面板底部的「跟随样式」选择器，里面有「不跟随样式」和库里的每一条。
- 设置 › 样式页的「用于当前画布」：调同一个 `bindCanvasStyle`，然后打开左栏面板让用户看结果。
- 样式对话框只编辑、不应用：原来的四档范围和「应用到…」按钮删掉了。

### 三、改值 = 改样式本身

已绑定时，样式面板里每一格的改动都走 `editBoundStyle`：

1. **先存库**（`profileStore.save`）。存不进去（乐观并发撞车、后端不在）就一个字都不改文档，状态栏说明原因。
   反过来先改文档的话，快照会领先于库，下一次「库里那一条变了」的判断就会把用户的改动拉回去。
2. **内置样式只读**：按 ADR 0029「改内置 = 复制一份」，先复制一份（`derived_from` 记着来源），改在副本上，
   画布改绑到副本，状态栏说一句。内置那一条保持原样。
3. 存成功后，一次 commit 改快照，并只对齐**改了的那一项**（`presetDelta`）。这样用户在属性页里对某一张图
   刻意改过的其它项（字体、颜色）不会被顺手冲掉。

样式里的数字是**页面上**的 pt（ADR 0029 §6a）：同一个 10 pt，页面上缩放比 0.6 的图写 16.67，缩放比 0.5 的图写 20。

### 四、什么时候**不**写：已经合样式的图零 commit

所有写入之前都先过 `effectiveChanges`。每一项的「此刻值」取法是：这个 (gid, prop) 上有 override 就用 override
的值，没有就用 manifest 报的值，与属性页读值同一个口径。数值按两位小数比较，其余按内容比较；与目标一样的项全部
去掉，结果为空就不写。因此打开文档、切画布、重渲染、manifest 回来这些时刻，已经合样式的图不会产生任何一条历史，
文档也不会一打开就变脏。

「新图」怎么认：这张图上**一个样式管得到的 override 都没有**。

- 对齐过的图带着这些 override。
- 用户在属性页里刻意改过的图也带着。
- 两种都不去碰。

同一会话里已经看过的图记在内存里（`seen`，按「文档 · 画布 · 样式」分开记）。撤销「按样式对齐新图」之后，
渲染回来的那一下不会把这张图再对齐一次。

### 五、这些写入属于哪一档

它们是 `project-document-and-autosave.md` 表里的**用户编辑**那一档：进历史、置 dirty、排队落盘。
不走「外部派生同步」（`applyDerivedUpdate`）的理由：

- 那一档**不进撤销历史**，而这里每一条都要能单独撤销（用户明确要求「按样式对齐新图」可以单独撤）。
- 那一档的唯一调用方是 `panelSourceSync`，写的是 `/api/panels` 说了算的派生字段（script / cost / fileKind / pxW）。
  样式写的是 override，是用户看得见的外观。
- 这些写入都有一个用户动作作为源头：选了绑定、改了样式、往绑定画布上加了图。

### 六、撤销「改样式」只退画布

原先的做法（撤销时把样式库那一条推回旧快照）已于 2026-09-25 删除，见 §十二。

### 七、绑定画布上「只带基线」的图也渲染一次

`useEngineSync.renderTargets` 原来只渲染「编辑中 / 有 override / 脚本领先磁盘」的面板，理由是「白跑一次引擎没有意义」。
在绑定画布上，要对齐一张图就得先读到它的 manifest，而用户选绑定的那一刻就是在要这个结果，所以绑定画布上的面板一律进
渲染目标。runtime 面板不变：重开文档绝不自动执行脚本（ADR 0013）。

### 八、缩放不触发联动（用户 2026-09-24 拍板）

已绑定画布上的图被缩放（拖动缩放手柄、改宽高、改缩放百分比）之后，**不重新对齐**，也不产生任何 commit。

- 缩放改的是**图的大小**，不是样式本身。样式联动的触发点只有「绑定 / 改这套样式 / 库里这条被改过 / 新图第一次
  拿到 manifest」这几个，缩放不在其中。
- 用户要的是「按比例一起缩放」：文字相对图的比例保持不变，图缩到 60%，读者量到的字号也跟着变成 60%。
- 缩放后页面上的字号或线宽不再合规时，由样式面板那一格的警告和问题面板指出，用户自己决定怎么修。
  可以点一键修复，也可以在样式面板里改值，改值会再联动整张画布。

机制上不需要额外判据：对齐过的图带着样式管得到的 override，同一会话里也已经记为「看过」，所以缩放之后渲染回来、
甚至重开文档后渲染回来，都不会被当成新图再对齐一次。看护用例是「缩放不触发联动」那一组。

### 九、评审补上的边界（Codex #547）

- **旧样式的数字按原口径读。** 从这个版本起，新建、提取和内置的样式都带 `pt_basis: "page"`，表示数字是页面上的 pt。
  没有这个标记的是旧版存下的样式，数字是当年写进 override 的脚本值，照旧原样写，不做换算。
  否则一份旧的 9 pt 样式套在缩到 60% 的图上，会静默变成 15 pt。
  前后端严格同源：`stylePresets.StyleProfileData.pt_basis` ↔ `profilestore._STYLE_KEYS`。
- **异步存库回来时，发起的画布已经不在了，就不写。**
  - 发起时记下「文档 · 画布 · 绑定」三样，存库返回后逐一比对，任何一样对不上都不写此刻的画布。
  - 库那边已经存了，原来那张画布回到前台时，由「库里那条变了」的判断跟上。
- **没有 manifest 的图不会丢掉这一笔变化。**
  - 绑定或改值那一刻，没有 manifest 的图会记一笔欠账（会话内，`pending`），渲染回来时只补这一笔，单独一条历史。
  - 「库里那条变了」这条路径则**先不前进快照**，等画布上的图都渲染出来再一起跟上，这样重开文档时也看得出欠账。
    渲染失败的图和 runtime 面板不参与等待。
- **被挡下的触发会补回来。** 事务或指针交互进行中到达的触发会被挡下，事务收尾、交互结束时补看一次。
- **恢复原样要等 manifest。** 某张带 override 的图还没有 manifest 时，认不出它身上哪些 override 是样式写的。
  这时恢复原样先不做，按钮置灰并说明原因。
- **标注和序号标签逐个属性算变化量。** 样式里只改了字号，就不会把颜色、字体一起重新套一遍。
- **「画布标注」那一行不含子图序号标签。** 序号标签在样式里是另一项（`subLabel`）。
- **设置里的草稿没保存时，「用于当前画布」置灰并说明原因。**
- **复制内置样式的副本存失败时，删掉那份副本。**

### 十、旧样式第一次被编辑时升级成按页面 pt 记（2026-09-24 拍板）

旧样式（没有 `pt_basis`）的数字按脚本值套用，而样式面板显示和交出的是页面值。两者直接相加是错的：缩放比 0.6 的图，
在面板里输入 9，脚本字号会变成 9，读者量到的是 5.4。所以旧样式**第一次被编辑**时，要先升级再写。
样式面板、设置 › 样式页、样式对话框三个入口都走同一个 `stylePresets.withPageBasis`。

- **已有的数字原样保留，只补上 `pt_basis: "page"`。** 这等于把旧数字按缩放比 1 解读：旧样式是按原生尺寸从图里提取的，
  原尺寸摆放的图上页面值就等于脚本值。所以缩放比 1 的图，除了被编辑的那一项，一个数字都不变；
  被编辑的那一项写成用户输入的页面值。
- **升级和这次编辑合成一次 commit、一次撤销。** 在样式面板里编辑时，当前画布上的图按新语义**整张**重新对齐
  （`presetDelta(null, …)`），状态栏说明「这套样式是旧版本存的，已改为按页面上的实际大小计」。
- **撤销只退画布**（§十二）：画布回到旧快照（含 `pt_basis` 缺省的旧口径）并标成已脱离，库保留升级后的那一份。
- **其它绑定了同一份旧样式的画布，下次打开时按「库里那条变了」跟上。** 这是预期行为：它们跟随的就是这一条，
  它已经换成了页面口径。
- **内置样式不受影响。** 内置样式本来就带 `pt_basis: "page"`；从内置复制出来的副本带着同样的标记。

### 十一、结构：对样式库的写入只有一条队列，写文档前统一比代次（2026-09-25）

§九那一轮之后，评审又在「异步存库 · 撤销推回 · 欠账 · busy 计数」的交错处挑出一串问题（推回那部分已随 §十二 删除）：

- 重载同一份文档后，旧编辑写进了新载入的那一份；
- 换绑定之后，旧绑定的欠账还会写下去；
- 保存结果用错了 manifest 的变体；
- busy 期间被挡下的触发丢了。

每一条都能单独打补丁，但它们是同一个结构问题：**多个异步写库的动作各自在发起那一刻读现场、各自用一个共享计数挡别人。**
所以这一轮改的是结构，不再逐条补：

1. **一条队列。** 改值时的存库、复制内置、排在它们后面的绑定，全部经 `enqueue` 串起来跑，一次只跑一个。每个任务**轮到自己时**
   才读现场（绑的是哪一条、库里现在是什么）。排在后面的改动天然基于前一笔的结果，不会有两个写入同时在飞。
2. **代次。** `generation()` = 项目 · 文档 · `loadSeq` · 画布。任务开始和写文档之前都要比一次，对不上就不写此刻的文档。
   `loadSeq` 在每一次整份替换文档时都会前进，即使 id 全都一样，所以「同一份文档被重载」也拦得住。
   库已经存了的，原来那张画布回到前台时由 `followLibrary` 按内容不等跟上。
3. **队列非空时同步器不动手，排空的那一刻补跑一次。** 这取代了 `busy` 计数，期间被挡下的触发不会丢。
   事务收尾、交互结束两处仍各补跑一次。
4. ~~撤销推回：最新的赢，失败时画布是真相~~。2026-09-25 删除，见 §十二。
5. **会话记账按「代次 · 绑定」分本。** 「看过的图」和「欠账」都换成这把键：不绑着那一条时，它的账没有人
   结算。明确地绑上一条时，只作废**这一条**的欠账（绑定会整份重新对齐、以库为准）；解绑 / 改绑 / 恢复原样时
   **离开的那一条不清**——记账不进历史，撤销把旧绑定带回来时，它那几张还没对齐的图仍然要补。
6. **只认当前变体的 manifest**（`exactPanelManifest`）。`panelRender` 会退回旧渲染或别的变体，拿那份去映射 gid，
   会写到已经不存在的 gid 上。拿不到当前变体的 manifest，就当作「还没有 manifest」，走欠账那条路。
7. **停在历史上时不自动写**（2026-09-25，跟上 #543 定稿）：撤销之后还有可重做的 future 时，自动写入
   （跟随库、对齐新图）一律推迟。自动写入是一条新 commit，会把 future 清掉，用户按 ⌘⇧Z 就回不去了。
   这与 #543「撤销 / 重做后派生同步不清 future」是同一条纪律。用户下一次编辑清空 future 时补跑一次。
   用户自己点的绑定和改值本来就是新编辑，不受这条限制。
   另外，「按样式对齐新图」只改 override、不改对象尺寸，所以不会触发布局组的自动重排（有用例钉住）。
8. **渲染不了的图不挡快照，但记欠账**（2026-09-25）。「库里那条变了」时，渲染出错的图、拿不到精确 manifest 的
   runtime 面板不参与等待，否则一张坏图就会让整张画布永远跟不上库。它们欠着这一笔，按 `owe` 记下，
   等哪天渲染成功时补上。三条写入路径（绑定 / 改值 / 跟随库）现在都记欠账。
9. ~~「库落后」按发起推回的那一处记~~。2026-09-25 删除，见 §十二。
10. **变化量只有一个算法：`deltaFrom(画布快照, 新内容)`**（2026-09-25）。
    - 起点永远是画布的快照，即它此刻真正长成的样子，不是库里的现值。如果库里有一笔被挡下、还没落到画布上的更新，
      面板里改值时它会一起落下去，而不是被当成已同步。
    - 口径从旧（脚本值）变成页面 pt 时算整份，包括旧样式在设置或样式对话框里被存成 page 口径的情况。
    - 写入器拿到的也只是变化量：标注只改了字号时，不会把颜色、字体一起重新套一遍。
11. **`_STYLE_KEYS` ↔ `StyleProfileData` 登记为严格同源对**，由 `tests/test_style_schema_pair.py` 看护：
    它读 TS 源码里接口的字段，与后端白名单比集合，再比 `pt_basis` 唯一的取值 `"page"`。
12. **排队的改值只属于发起时绑的那一条**（2026-09-25）。
    - 代次里不含绑定，所以绑定单独在两处各比一次：任务开始时一次，存库回来后一次。
    - 排在前面的、我们自己的任务把内置样式复制成副本并改绑时，会记一条转发（`redirects`），
      后面发起时绑着内置样式的改动就顺着它落到副本上。转发在队列排空时作废，用户之后自己绑回内置不会被转走。
    - 输入的值恰好等于库里那笔被挡下的更新时，不当成无事可做：不存库，但照样把「快照 → 库」的变化量落到画布上。
13. **所有「按那一处」的会话状态都带上发起时的位置**（2026-09-25）。
    - 转发（`redirects`）按代次记，而且只在改绑真的 commit 进发起那张画布之后才记。
      复制出来、却没落进任何画布的副本会被删掉。
    - 同步器起来时、换进一份绑定的文档时，各拉一次样式库清单（`ensureLibrary`）。否则不打开样式面板或设置的话，
      绑定的文档会一直停在快照上。
14. **没绑样式时，样式面板的直接写入也只认当前变体**（2026-09-25）。面板的 gid 取自显示用的 manifest，
    这一版还没渲染回来时，那份 manifest 是上一版的。所以控件先置灰并说明原因；绑定时写的是样式本身，不锁。
    样式写入原地改值、只追加真正新的 override（`upsertOverrides`），override 顺序不变，不因为顺序变化
    换一个渲染变体键。「按快照新建一条样式」那条路径也记转发。
    同源对看护改为结构性地读 TS 接口（`tests/support/tsconst.exported_interface_members`），
    注释掉的成员声明不算。
    原处放弃一次复制时，只有在这份项目里没有任何画布绑着那个副本时才删掉它：副本在 `duplicate()` 返回那一刻就进了
    共享清单，等存库的这段时间里，别的画布可能已经绑上了它。
    已知盲区：另一个标签页或另一份文档里的绑定，这里看不见。
15. **补账前先对着此刻的样式核一遍**（2026-09-25）：欠账补之前按此刻的样式核一遍（`pruneToStyle`），后来从样式里
    删掉的项不写，还在的项取最新值。（这一条原先还有推回的换代与 409 重推，已随 §十二 删除。）
16. **明确的绑定也进库写队列**（2026-09-25，取代「换代 + 纠正写入」）。
    - 绑定的意思是「以库里此刻那一份为准」。如果有写入还在飞（改值存库、复制内置），绑定排到它们后面，
      读到的是前面所有写入都落定之后的库，所以从结构上不存在「在飞时改绑、之后库被改写、画布与库分叉」。
    - 队列空着时当场绑，界面上立刻看到结果。
    - 排队中的绑定要绑的样式 id 记在 `queuedBinds`，前面的任务放弃复制时，不会把它当成没人要的副本删掉。
    - 已经绑着同一条、快照与库相同、图也都合样式时，再点一次绑定不写任何东西，不产生历史、不标脏。
    - 排队中的绑定执行时，发起的画布已经不在前台（切了画布、文档或项目），就不绑，并在状态栏说明，不静默丢掉。
17. **「对不上的图」在 commit 之前量**（2026-09-25）。commit 改了 override，每一张被写过的图的渲染变体键都会变，
    commit 之后它们都暂时拿不到精确 manifest。所以欠账（`owe`）和「看过的图」（`markSeen`）都用 commit 前量到的集合，
    不给已经写好的图记假账。
18. **绑定之后新加的标注、序号标签也对齐一次**，单独一条「按样式对齐新标注」。绑定前就有的文字，在换进画布或绑定的
    那一刻就记为「看过了」，重开文档时不会被重排。**只带着素材烘焙基线的新图不算手改**：`addPanel` 会把
    `baked_overrides` 原样抄进来，这时照样对齐，与「先加图再绑定」得到同一个结果。

19. **写之前发出的清单请求不许盖过写操作**（2026-09-25）。`profileStore` 的请求序号里，成功的写操作也占一个号：
    比它早发出的 `load()` 回来的是写之前的那一份，照样发布的话跟随会把画布换回旧值。被盖过的那一次如果仍是最近
    一次请求，就重拉一次（等它的人拿到的是新的）。
20. **会话记账按「面板 + 素材」认图；新图欠整份**（2026-09-25，Codex #547 最后两轮）。
    - `seen` 与欠账的键是 `面板 id @ 素材`：替换素材保留面板 id，只按 id 记的话换进来的新图被当成看过了、永远不对齐。
    - 没 manifest 的图记欠账时，**新图**（一个 override 都没有，或只有抄来的烘焙基线）欠的是整份样式：存库在飞时
      加进来的图只欠这一笔变化量的话，补完就记成看过了，样式的其余部分永远落不上去。带着别的 override 的图仍只欠
      变化量，不冲掉手改。
    - 「只有抄来的烘焙基线」只比内容、不看 `baked_current`（`bakedBaseline.isCopiedBakedBaseline`）：文件被外部改过，
      机械抄进来的基线也不是用户的手改。

### 十二、撤销不推回样式库（用户 2026-09-25 拍板）

撤销（或重做）「修改样式「X」」「按样式「X」更新」这两类改了快照的步骤，**只退当前画布**，不再把样式库推回。

- **样式库保留新值。** 别的绑同一套样式的画布照样跟上新值。
- **撤销之后这张画布「已脱离样式」**（`FigureDocument.style.detached`）：不跟随库、不对齐新图，底部选择器显示
  「已脱离「X」」，提示行换成脱离那一句。用户再明确选一次绑定（选回 X 或别的）才恢复跟随，这一次按库里此刻的内容
  整份对齐，是一条普通的绑定历史。
- **重做回到那一步时恢复成绑定状态**，但以库里**此刻**的内容为准：与重做放回来的快照不一致，就按「库里那条变了」
  照常跟上，进历史（仍守 §十一第 7 条：future 非空时推迟）。
- **实现：标记在历史里，不在会话里。** 这两类写入 commit 时带 `undoAlso`（`documentStore.commit` 的选项）：
  撤销这一条时，除了回到操作之前，再落下 `style.detached = true`；重做先撤掉标记、再重放操作。标记随文档保存，
  重开之后仍是脱离的；撤销 / 重做 / 再撤销都一致，不需要任何订阅方在撤销那一刻补写（补写要么是一条新 commit、
  清掉 future，要么走不进历史的派生档，两条路都不对）。
- **删掉的机制**：撤销推回（`pushSnapshotBack` / `schedulePush`）、「最新的赢」（`wantPush`）、推回失败的「库落后」
  （`libraryBehind` / `placeOf`）、推回的 409 重推（`adoptConflict`）、切回画布时的重试，以及它们的用例。

理由：全局、异步的样式库与撤销叠在一起，表面积失控。推回本身是一次会失败、会与别处的写入交错、会跨画布跨文档的
异步写入；为了让「撤销」这个本来同步、局部的动作在它上面成立，前后补了「最新的赢」「库落后」「按那一处记」「换代
纠正」「409 重推」「在飞时改绑排队」「离开的绑定保留保护」一整套机制，Codex 评审每一轮都能在它们的交错处挑出新的
P1。撤销只退画布之后，撤销回到它本来的样子：同步、只动这份文档、进历史。

代价：

- 撤销之后库里仍是新值，其它绑同一套样式的画布照样跟上——撤销不是「把这套样式改回去」。要改回去，在样式面板里
  把值改回来（那是一次对样式本身的修改）。
- 这张画布要重新选一次才继续跟随；在此之前，库里那条之后的修改不会落到它上面。
