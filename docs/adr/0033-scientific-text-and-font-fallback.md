# ADR 0033：科学文本与字形回退 —— 「那个方框」必须说得出是哪几个字

状态：**Accepted**
日期：2026-09-01
相关：[0032 属性能力层](0032-typography-capability-layer.md)（`interpretation` 是它的第十条属性）、
[0030 统一检查与问题定位](0030-validation-and-problem-navigation.md)（缺字形是两条新规则）、
[0031 统一导出管线](0031-unified-export-pipeline.md)（载荷在导出那一刻现取，本轮只多一个可选字段），
本轨道文档 [`docs/implementation/product-ux-reliability/`](../implementation/product-ux-reliability/STATUS.md)。

## 裁决摘要

| 问题 | 裁决 |
|---|---|
| 「这个字由哪张脸画出来」 | **一份计划，四层**：`primary` / `cjk` / `fallback` / `missing`。落笔、量宽、预检、预览读同一份 |
| 分段判据 | **字形覆盖**，不是码位。`ord(ch) > 0x2E80` 只保留为**排版分段**（换行单元），不再当覆盖判据用 |
| 两侧怎么不分叉 | 算法严格同源（`glyphplan.py` ↔ `glyphPlan.ts`），**oracle 刻意不同源**：Python 问真字体，浏览器读生成的覆盖表 |
| 覆盖表 | 生成物 `src/tavotto/pdfbackend/canvas_coverage.json`，唯一产生者 `scripts/gen_canvas_coverage.py`，`--check` 看住漂移 |
| raw text | **一个字符都不改**。解释只生成渲染表示，`parse_runs` ↔ `serialize_runs` 那一对不受影响 |
| Unicode 上下标 | 两档：`auto`（默认，只救「不然就是方框」的）/ `scientific`（一律合成）。`m²` 那种设计字形两档都不动 |
| 为什么默认不合成 | 合成会把 PDF 文本层里的 `⁵` 变成 `5`（实测 `×10⁵` 抽回来是 `×105`）——**复制走的人拿到错的数**比字体不一致严重 |
| 缺字形 | 进问题系统：`glyph-missing`（lab 档 error）。**逐字列出是哪几个** |
| 换脸画出来的 | 另一条 `glyph-substituted`（suggestion）。与「画不出来」**分成两句话** |
| 图内文字的判据 | `manifest._glyph_scan()` 走 matplotlib 自己的解析链量覆盖，产生者只有这一处，两个求值器读同一份 manifest |
| 图内文字的回退 | 设族时带一条尾巴（`FONT_FALLBACK_TAIL = ("DejaVu Sans",)`），matplotlib 逐字形退过去 |
| 中日韩 | 尾巴治不了。字体下拉按运行时探测补上装得到的中文字体——**报一盏没有开关的红灯比不报更坏** |
| 字体来源 | **本仓库不分发任何字体**。三条来源：PyMuPDF 自带、matplotlib 自带、用户机器上装的。看护 `tests/test_font_provenance.py` |

---

## 1. 背景：先量，再改

Prompt 14 的前提是「特殊字符在预览或导出中出现黑色方框」。**这一轮先把它量了
一遍，结果推翻了一半前提**：

| 路径 | `×10⁵` `μm` `≤` `H₂O` 的实测结果 |
|---|---|
| 画布文字 → PDF（PyMuPDF 1.28.2） | **没有方框**。PyMuPDF 在 `TextWriter.append` 里自己挑了一张 `Noto Serif Regular` 把 base-14 缺的字形画了出来 |
| 图内文字 → PNG/PDF（matplotlib，默认族） | **没有方框**。DejaVu 盖得住这一批（中日韩除外） |
| 图内文字 → PNG/PDF（Times New Roman） | **有方框**。`⁵` `⁻` `₂` 三个字符画出来的暗像素数**一模一样**（3551）——那就是同一个 .notdef 空心框 |
| 图内文字，任何族 + 中文 | **有方框** |

所以真正的缺陷有两个，而且都不是「渲染器不会回退」：

1. **图内文字那条路根本没问过覆盖**。matplotlib 明确 warn 了是哪个码位缺在哪个
   字体（`Glyph 8309 (\N{SUPERSCRIPT FIVE}) missing from font(s) Times New Roman.`），
   Tavotto 把这条信息丢掉了。链路全通、渲染成功、界面一句话都不说。
2. **画布那条路的回退是隐式的，没有人知道它发生过**。实测那张回退脸
   **与请求的族和字重无关**（三个族 × 粗/常规六种组合，回退脸永远是
   `Noto Serif Regular`）——于是 sans-serif 粗体标签里的那个下标是衬线常规的
   字形，而没有任何人被告知。

顺带量到第三件事：画布的分段判据 `ord(ch) > 0x2E80` **量的是码位，不是覆盖**。
两个方向都会错——`₂`（U+2082）在 CJK 脸里有、码位却在 CJK 段之外；`━`（U+2501）
拉丁段里只有 CJK 脸画得出，而现行路由不会去问它，结果是一个**本可以画出来的
方框**（这一类共 87 个码位）。

## 2. 字形归属计划：四层，顺序不可交换

```text
primary   请求的那个族的 base-14 脸自己画得出
cjk       中日韩脸画得出（只有码位在 CJK 段、或前两层都没有时才轮到它）
fallback  前两层都没有，但 PyMuPDF 自己挑得出一张脸（实测 Noto Serif Regular）
missing   谁都画不出——导出上就是一个方框，必须进问题系统
```

第 2 步里那句「只有码位在 CJK 段」是刻意的：去掉它，`₂` 会从隐式回退的衬线脸
改判到中日韩脸（Droid Sans Fallback），**既有文档的像素会变**。本分层与改造前
逐字符等价，只多救回第 4 步那 87 个码位。

**落笔、量宽读同一份计划**。改造前它们各自按 `ord` 切一遍——结果相同，判据却
是两份；判据一旦有两份，换行位置迟早和画出来的字对不上。

## 3. 两侧怎么不分叉：算法同源，oracle 不同源

浏览器里没有字体引擎，而「这几个字导出后会是方框」必须在**点导出之前**说出来。
所以判据要有两份。做法与 preflight / patchspec 一样是「同一份向量，两边各跑一
遍」，但多一层：

```text
算法   glyphplan.py            ↔  glyphPlan.ts          严格同源
oracle 真字体（has_glyph）      ≠  canvas_coverage.json  **刻意不同源**
看护   gen_canvas_coverage.py --check（表 vs 真字体）
       glyph_plan_vectors.json（pytest 与 vitest 各跑一遍）
```

真正落笔的 `pdfbackend` 永远问真字体，所以导出那一端不会错。表漂了的表现会是
「预览说画得出、导出上是个方框」，而那正是上面两道门禁盯着的东西。

预检**两侧都读表**：它们要给出同一个答案，Python 侧偷偷问真字体只会让两边在
漂移时给出不同的结论，而漂移本身已经被单独看住了。

## 4. 受控科学文本解释：默认档为什么这么保守

合成上下标看起来是纯赚——字体统一了、基线正确了、不依赖任何回退脸。**实测之后
发现它有代价**：合成之后 PDF 文本层里那个字符就是基础字符，`×10⁵` 抽回来是
`×105`。审稿人复制走的是 105。

这是语义损坏，比「上标是另一张脸画的」严重。所以：

* `auto`（默认）：只有这一串里**有字符谁都画不出**时才合成。今天画得对的东西
  一个像素不变，文本层也一个字符不变；
* `scientific`：认得的一律合成。字体统一，代价写在 tooltip 里。

两档都还要求折出来的基础字符正文脸全画得出（否则白折一场），而且**整串一起
折**——`m⁻²` 里两个字符处境不同，逐字符处理会得到一个 62% 的合成减号紧挨着一个
全尺寸的设计上标，比原样还难看。

`math` 这一档**不做**：画布文字不经 matplotlib，摆一个不存在的模式等于一句
做不到的承诺（图内文字那侧的 `$…$` 才是 engine mathtext）。

## 5. 缺字形进问题系统

两条规则，各自一句话：

| 规则 | 说的是 | 等级（lab / free-form） |
|---|---|---|
| `glyph-missing` | 这几个字**画不出来**，导出上是方框 | error / warn |
| `glyph-substituted` | 这几个字画出来了，但**不是用它自己的字体** | suggestion / suggestion |

压成一句的话，用户看到红灯却发现图上好好的，下一次就不看这盏灯了。

**判据的主语必须说清楚**：画布那条量的是**渲染表示**（行内标记已拆掉、该合成的
已合成），量原文会报出一批不会发生的方框——假红比假绿隐蔽，它让人去修不存在的
问题。

与既有的 `font-family-substituted` / `cjk-fallback-missing` 是**两个问题**：那两条
问的是「族名在不在规范的白名单里」（规范范围），新的两条问的是「这套字体画不画
得出这些字」（能力）。白名单里的字体没装上时前者不响；装了一个不在白名单里、却
画得出中文的字体时前者误报。

## 6. 字体来源：这个仓库不分发任何字体

回退很容易滑向「把一个覆盖全的字体塞进包里」。那条路的代价是许可证：字体是独立
作品，AGPL 的仓库照样不能随手带一份别人的 `.ttf` 出门。三条来源：

* PyMuPDF 自带的 base-14 / CJK / 隐式回退；
* matplotlib 自带的 DejaVu（图内文字的回退尾巴只有它一个）；
* 用户自己机器上装的字体（下拉里列的都先探测过画不画得出）。

看护 `tests/test_font_provenance.py`：版本库里没有字体文件、前端不下载也不内嵌
字体、后端没有 `fontfile=` / `fontbuffer=` 这两个入口、依赖里没有字体包。

## 7. 明确没做的

1. **中日韩的自动回退。** 尾巴里不放平台相关的中文字体：同一份文档在两台机器上
   会画出不同的字，比一条说得清楚的问题项更坏。用户在下拉里选（选项按运行时探测
   给出，候选名单取自出版规范的 `cjk_fallback.accepted`）。
2. **PDF 字体子集嵌入的细节**由 PyMuPDF 自己管；本轮没有改它，也没有新增任何
   嵌入路径。
3. **外部 LaTeX** 一行没有新增（Prompt 14 §七的硬约束）。
4. **图内文字的 `interpretation`**：那边的上下标是 matplotlib 的 `$…$`，不是我们
   的合成管线。能力表里它是 `figureText` 不支持的一条。
