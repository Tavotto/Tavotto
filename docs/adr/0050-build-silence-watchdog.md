# ADR 0050：build 的静默看门狗——用输出把「卡死」和「慢」分开，不问用户

日期：2026-09-07 · 状态：**Accepted**（取代 ADR 0048 的机制，保留它的问题陈述）

## 背景

ADR 0048 把冷启动 build 的超时从一刀切的 900 秒改成按注册表 `cost` 分档，解决了
「本来就要跑很久的脚本被当成死循环杀掉」。但它把分类这件事交给了用户：注册表里
`cost` **从来不是测出来的**——`discover.py` 的注释直说「cost 无法静态判断，草稿一律
medium」，试运行探测虽然真跑了一遍脚本，也没拿计时做任何事。于是用户要手填一个
系统刚刚量过的值，而且填错的代价是渲染被杀。

用户的原话是「这个需要人手动标 heavy 吗，会不会增加用户的认知成本」。会。

## 决策

**超时问的不再是「跑了多久」，而是「它还在动吗」。**

worker 的 stderr 直接落进 `worker.log`，而用户脚本的 stdout 被 worker 重定向到
stderr（`worker.py` 的 `redirect_stdout`）——所以**日志文件长大了就是脚本还在往前
跑**。卡死的脚本不会再有任何输出；慢脚本会持续打进度（那九个 ovito 分析每 50 帧
一行）。两者用这一条就分得开，不需要任何人先把脚本归类。

* `BUILD_IDLE_TIMEOUT = 1200s`——**连着这么久一个字节都没多出来**才判死。
  只要有输出，静默计时清零，等待继续。
* `BUILD_HARD_TIMEOUT = 4h`——兜底。`while True: print(i)` 这种一直有输出的死循环
  永远等不到静默，不能没有头。
* 判据每 2 秒 `stat` 一次日志（几十微秒）。

**两条控制面同一条判据**：Python 池在 `_readline` 里分片等 + `_log_size`；workerd
把子进程 stderr 直接重定向进同一个文件，所以它 `stat` 的是同一份东西
（`session.rs` 的 `log_size` / `await_response`）。Flask 通过新的
`idle_timeout_ms` 把阈值下发给 workerd，语义与 Python 侧逐字相同。

**措辞跟着判据走**：看门狗判死时说的是「连着 N 分钟没有任何输出」，并告诉用户
下一步——展开输出看它停在哪；本来就要静默算很久的，在那一段里打一行进度输出。
兜底上限判死时说的是「一直有输出，多半是循环停不下来」。两句话指向完全不同的
排查方向，不能合成一句。

## 与 ADR 0048 的关系

**机制被取代，问题陈述保留**。`BUILD_TIMEOUT_FACTORS` / `build_timeout_for` /
`script_cost` 一并删掉——同一个问题留两套判据，其中一套迟早无人维护而且没人知道
哪套在生效。注册表的 `cost` 保留，但只剩它原本那个消费者：渲染前那句「冷启动可能
需要几分钟」的**预测**（第一次跑之前确实无从测量）。它不再影响任何超时，填不填
都不改变行为。

**诚实记录一处退化**：ADR 0048 下被显式标成 `heavy` 的脚本，若**完全静默**地跑
超过 20 分钟，现在会被判死（那时它有 1 小时）。取舍理由：`heavy` 落地不足一天、
无人使用；而「静默 20 分钟」这一档已经比它取代的那个平坦 900 秒更宽，对**所有**
脚本都是净改善。真出现这种脚本，正解是让它打一行进度，而不是回到手工分类。

## 不做的事

* 不把 `override` / `export` / 预览改成看门狗：它们不跑用户脚本，平坦上限是对的。
* 不动 native 会话与 barrier 的 `BUILD_TIMEOUT`（那是用户自己的进程，ADR 0021）。
* 不做「按历史实测自动定档」（评估时的另一条路）：看门狗第一次跑就对，而实测
  分档要等第二次。两者不冲突，将来若要给那句预测文案更好的数，再单独做。
