# ADR 0213：用户提交期刊线索——用户给证据，流水线核实入库，回信闭环

日期：2026-11-27 · 状态：**Proposed（草案；产品负责人 2026-11-27 拍板四项：「都按推荐来」，见「决定」第零节）**
**1.0 收敛纪律：新增产品能力。维护者 2026-11-27 给豁免，登记在 `docs/1.0-release-readiness.md` §1.8；入口跟期刊库开关与「联系作者」开关走，不另设开关。**
相关：[0155 内置期刊标准库](0155-journal-catalog.md)（目录结构、出处、签名、`catalog_rev`、远程协议全部沿用）、
[0145 联系作者](0145-contact-the-maker.md)（发信、附件直传、回信、「我的来信」全部沿用）、
[0205 Agent 发外部审阅](0205-agent-review-share.md)（Agent 工具「先问用户」的 `explicit_confirm` 纪律）、
规则 `docs/rules/backend/profiles-and-preflight.md`「内置期刊标准库」。

## 问题

期刊目录（v1 rev19、v2 rev17，近千本刊、两万多条）全靠我们自己采集和巡检。目录会因为三件事变旧：出版社改了投稿须知、我们抄错了、用户投的刊根本没收。
最先发现问题的是用户：预检说线宽要 0.5 pt，编辑部退稿信里写的却是 0.25 pt。可现在用户发现了也没处说，只能自己绕开，下一位用户会再撞一次。

我们要的是**用户顺手指出问题，目录就越用越准**。同时 ADR 0155 的三条底线一条都不能松：
1. 每个数值都能回到原文，`quote` 逐字一致；
2. 目录带 Ed25519 签名，`catalog_rev` 只增不减；
3. 期刊没写的项不补。

## 决定

### 零、拍板记录（2026-11-27，产品负责人「都按推荐来」）

1. **给 1.0 豁免。**
2. **用户上传的原文 PDF、截图只用来取证，不对外分发**；该条结案（入库或不采纳）后 90 天在服务端删除。
3. **自动入库分两步走**：一期全部人工处理；二期按第四节的门槛自动产出**候选**，候选再过与其他条目同一套盲判复核才算「已复核」，随维护者当面签发的下一版上线，其余照旧人工（2026-11-27 修订，见第四节）。
4. **署名做成可选、默认关**（三期）；**不做物质激励**（「现有功能永久免费」不动，也不拿高级版天数换线索）。
5. **编辑部原话入口放在左侧「问题」侧边页底部**（2026-11-27 追加，同日由「需要你确认」分组底部改定）；三期依次做。

### 一、总原则：用户给线索和证据，不直接写目录

- 用户提交的是**线索**：哪本刊、哪一条、证据在哪（原文链接、PDF、截图，或编辑部原话）。用户**不填数值**，界面上也没有可以改数值的输入框。
- 写进目录的只有一条路：采集流水线取原文 → 抽取 → 逐字核对 `quote` → 签名发版。和今天自己采集的数据**同一条流水线、同一套校验**（`journals.validate_catalog`、v2 校验），不另写一份判据。
- 一条提交**永远改不了已复核的条目**，除非它带来的原文引文过得了第四节的逐字核对；推翻已复核条目一律人工。
- **编辑部原话不进目录。** 那是私人通信，不是公开出处。它只用来触发复核：去找出版社的公开原文。公开原文里找不到依据，就不改目录，回信如实说明。

### 二、入口（按价值排；都不撑大原有卡片）

| 入口 | 位置 | 用户做什么 | 自动带上（都是目录数据，不是用户数据） |
| --- | --- | --- | --- |
| **这条不对** | 预检出处卡（`SourceButton` 卡片）底栏，和「打开原文」「存档」同一行的一个文字链接 | 打开独立的「期刊规范反馈」表单（不是「联系作者」窗）：只读列出条目 / 目录现值 / 当前出处，可选问题类型，贴期刊原文、链接或附截图 / PDF | 期刊 id、规则键、当前值、出处 id、v1 / v2 `catalog_rev` |
| **没有这本刊** | 期刊选择器搜不到时那一行（`noMatch` 的 `EmptyLine`），句尾接一个链接 | 同一个表单的「申请收录期刊」形态：期刊名称（预填搜索词）、投稿须知网址或附 PDF | 搜索框里的字（≤120 字） |
| **编辑部要求改图**（二期） | 左侧「问题」侧边页底部常驻（2026-11-27 改定：原定「需要你确认」分组底部，但该分组只在期刊有带条件的要求时才出现，入口常常看不到），与出处卡同样的一行文字链接 | 粘贴编辑部原话，可附截图 | 当前绑定的期刊 id |
| **Agent 提交**（三期） | MCP 新工具 `tavotto_report_journal_issue` | Agent 发现投稿须知和目录不一致时，**先问用户** | 同第一行 |

- 点开是「联系作者」对话框（ADR 0145）的同一个外壳，标题下方预填一行灰字（例：「关于 *Nature* · 线宽下限」），正文框下面多一个「原文链接」输入框，附件和「发送」都沿用原样。
  一句话、一个主按钮，说明放 `title`；**文案与截图先过 agy 审，再给用户看浅 / 深两套截图，确认后才开实现 PR**。
- 不新增提醒形态：发出后的状态、回信都在「我的来信」里，有回信时亮已有的小圆点和通知轨胶囊。

### 三、传输：复用「联系作者」，加一种信件类型

不另开端点，也不另写出站代码。发送走 `engine/contactsend.py` 现有的 init → COS 直传附件 → complete；回信走 `GET /v1/messages/{id}/replies`；本机记录走 `contactinbox`。
线路白名单、`tlstrust`、不跟随重定向、秘密不落地、幂等重放，全部原样沿用。

- **记录类型多一种**：`kind` 从 `"letter" | "report"` 扩成 `"letter" | "report" | "journal"`；旧记录缺省仍是 `letter`。
- **结构化头**（`kind=journal` 必带，闭集、逐项限长，服务端不认的字段回 422）：
  `journal: {type: "wrong"|"missing"|"editor", journal_id?, query?, rule_key?, current?, source_id?, url?, catalog: {v1?, v2?}}`。
  `url` 只收 `https://`、≤2000 字、不带凭据；`current` 是目录里那一条的序列化值（≤200 字）；`rule_key` 必须是 `journal-base-v1` 的字段路径或 v2 事实键（客户端发前校验，不合规就不带）。
- **主题自动生成**（「期刊线索：<刊名>」），用户不用写。正文、附件、回信邮箱照 0145 的口径，都由用户自己决定写不写。
- **不带任何项目内容**：脚本、数据、路径、图都不会自动附上，用户自己拖进来的附件除外，和「联系作者」一样。
- **不经期刊目录的设备令牌**：回音靠 `reply_token`（0145 已有）。这样期刊读取记录和来信**不会关联**到一起，隐私面不变大。
- **保存期**：本机记录与服务端来信同「联系作者」，365 天；**附件在该条结案后 90 天删**（零节第 2 条），服务端记录结案时间。
- **部署顺序**：先部署服务端（infra 的 diagnostics-api `/v1/messages/*` 接受 `kind=journal` 和结构化头，管理工具新增按 kind 导出），再发客户端。
  旧服务端回 422 时，客户端按现有 `client_error` 文案处理，不崩溃、不丢草稿。

### 四、服务端到入库：triage 队列与流水线（在 journal-data 与 infra，不在本仓库）

**一期（全部人工）**

1. 每天一次用 `diag-admin msg export --kind journal`（新增子命令；`msg download` / `msg reply` 已有）把新来信导出到 `journal-data/triage/reports/<TVM-…>/`（`report.json` + 附件 + 对 URL 的取页副本 html/txt/meta + sha）。
2. **去重**：`wrong` / `editor` 按（期刊 id，规则键）合并，`missing` 按归一化后的刊名 / ISSN / URL 主机合并；报的人越多，排得越靠前。
3. **分类（闭集）**：`new_journal` 新刊 / `value_changed` 原文改了 / `our_error` 我们抄错了 / `link_rot` 链接失效 / `misread` 用户理解有偏差（should 与 must、投稿阶段与录用阶段等；不改数据，可能要改出处卡说法） / `no_public_source` 只有编辑部原话 / `duplicate` / `not_actionable`。
4. 维护者按现有采集规范（`tools/COLLECT_SPEC.md`）处理，改动走现有的 `build.py`、签名、发版。
5. **回信**：结案时用 `diag-admin msg reply` 发一封短信，模板三种（文字过 agy、用户定）：
   - 「已更新」：写明版本号；用这本刊的项目打开时会自动更新（ADR 0155 修订：旧项目自动更新）。
   - 「没有采纳」：一句原因，例如「出版社原文写的是建议，不是必须」。
   - 「还差一点」：请对方发原文链接。

**二期（达到门槛的自动成为候选，复核通过才入库）**

> 2026-11-27 修订（维护者拍板）：原稿写「三条门槛全部满足才自动进下一个 rev，标『已复核』」。改为下面的做法，理由两条：
> 两个模型**抽取一致**只说明读法相同，不等于读对，而目录里「已复核」一直指**两位独立盲判都判对**；
> 每一版目录上线都要维护者当面签发，不存在「自动进 rev」，只能「自动进候选」。

先查域名再取原文：原文 URL（含跳转后的最终主机）必须在该出版社已登记的域名里（目录里已有的 `sources` 主机集合），不在的不自动抓、直接进人工；新出版社一律人工。
自动取原文（抓不到就用 ego 取页，人机验证交给维护者）→ 双模型独立抽取（只看我们自己抓的公开原文与目录侧字段，**不看用户正文、邮箱、附件**）→ 候选补丁（完整事实、原文与 sha、两次抽取记录、门槛结果）。
三条门槛全部满足的候选进与其他条目**同一套盲判复核包**（两位独立判官都判对才标 `verified`），通过后随下一版签发上线；任何一条不满足进人工队列：

1. **引文逐字命中**：候选 `quote` 经 NFKC 与空白归一后，是**我们自己抓下来**的原文 txt 的子串（不拿用户上传的 PDF / 截图做核对）；PDF 还要页码对得上。
2. **两个模型一致**：规则键、值、语气（建议 / 必须）三项都一样。
3. **不推翻已复核条目**：新刊或新增条目可以自动；凡是碰到已复核事实（改值、改语气、改适用条件）一律人工，且按「撤回旧事实、换新 id 发新形式」处理，不原地改。

自抓原文证实目录现值没变的，不出候选，只出「保持原样」回信草稿。
v1 条目的线索在二期仍全部人工。

结案回信在二期由 triage 结果生成草稿，维护者批量过目后发送，不做全自动发信；要写版本号的回信等那一版签发上线后再发。

**三期**

- **署名**（2026-11-28 修订，产品负责人「按推荐来」）：名字挂在**因这条线索新增或改动的 v2 事实**上，只写一个人，默认不写。
  - 表单：只在 `wrong` / `missing` 两种表单里出现一个默认不勾的复选框「在引用条目标注我的名字」+ 弱灰「（所有人可见）」（文案产品负责人 2026-11-28 定），勾了才出称呼框；`editor`（编辑部原话）不进目录，不出这个框。Agent 工具（`tavotto_report_journal_issue`）不收、也不发称呼。确切文案随界面评审定，但必须一句话说清「所有用户可见」。
  - 线缆：`journal.credit`（API 1.8.0，见附录）。称呼是第一段要展示给别的用户看的用户自填文字，三处各校验一次：服务端（入站）、journal-data 工具（入库）、客户端（渲染前）。规则相同：NFKC + 去首尾空白后 1–32 字；单行；不含控制字符、Unicode 格式字符（含双向控制符）与 `@`；不含 `://` 或 `www.`。
  - 入库：`tips.py ingest` 把称呼留在本机 `intake/`，进 git 的工单只记 `credit: true`。称呼要上目录，必须由维护者在结案时**显式确认**（`close … --credit`），不自动带过去；只有 `accepted` 且确实新增或改动了 v2 事实的线索才能确认。`kept` / 被拒 / 重复 / 只修链接（`link_fix`，值没变）都不写名字。
  - 「第一个」：同一去重组里、勾了署名且被采纳的线索中 `created_at` 最早的那一位；同一条事实只写一个人，之后再被改动换新 id 时，名字跟着**新 id**（写促成那次改动的人，没人勾就不写），旧 id 随撤回一起消失。不给已经入库的旧事实补名字。
  - 发布：**不放进 v2 刊包**。0.21.x 起已发布的客户端对刊包、索引都做严格校验（未知字段整包拒收），刊包字节又由签名索引按哈希钉死，往事实里加 `thanks` 会让所有老客户端丢掉这本刊的 v2 事实。改为签发时在索引旁另出一个同一把钥匙签名的 `thanks.signed.json`（信封与索引相同），载荷 `{"schema": 1, "kind": "journal_facts_thanks", "catalog_rev": N, "thanks": {<journal_id>: {<fact id>: <称呼>}}}`。老客户端从不请求它；新客户端在同步索引后取，`catalog_rev` 与本机索引不一致、取不到、验签失败或称呼过不了上面的校验，一律**不显示、不报错**。称呼台账在 journal-data `triage/tips/thanks.json`，形状 `{<journal_id>: {<fact id>: {"name", "message_id", "tip", "credited_at"}}}`，由 `tips.py close … --credit` 写入。
    `publish_facts_v2.py --thanks <台账>` 出 `v2/thanks.signed.json`：用同一把签名钥匙，写完后回读验签。只保留这一版刊包里真实存在的 (journal_id, fact id)，对不上的逐条列出、不悄悄丢；称呼在签发时再校验一遍，不合格就拒签整个文件。这一步由期刊数据负责人改并签发。
  - 上线顺序：`/v2/thanks.signed.json` 目前在三层路由白名单之外，都要放开：主仓库 `services/journal_catalog/core.py`、infra `deploy/caddy/jc-public-on.caddy`、官网 `src/journalCatalog/proxy.ts`；顺带定边缘缓存。三层上线、会读它的客户端发版之后，签发才开始带这个文件；在那之前不出。infra 与官网部署照例当面问。
  - 显示：v2 事实的出处卡显示一行灰字「感谢 <称呼> 勘误」；v1 条目不显示（v1 线索仍全人工，且 v1 包同样严格校验）。
  - 撤销：用户回信或另发一封「联系作者」说要撤，维护者从台账删掉，下一版签发后消失。`docs/privacy.md`「Contacting the maker」一节补一句：勾了署名，称呼会在目录里对所有用户可见。
- **Agent 工具** `tavotto_report_journal_issue`：两步调用，与 0205 同一套 `explicit_confirm`。第一次只回将要发送的内容 + `next = ask_user(...)`，用户明确同意后才发。
  只在期刊库开关（`JOURNAL_CATALOG_AGENTS`）与「联系作者」都开着时进 `tools/list`；不进 `usage.TOOLS` 遥测闭集，走 `other`。
  **已实现（2026-11-27）**：第二次调用要带 `explicit_confirm=true` 和第一次回包里的 `send_token`（净化后的内容摘要；不叫 confirm_token，那个名字留给 ADR 0127 只能由用户点击产生的运行确认，内容变了令牌失效）；
  `current` 与 `catalog` 版本由工具读本机目录，不收数值；`TAVOTTO_NO_JOURNAL_SYNC=1` 时同样不出现。细则 `docs/rules/plugin/journal-report.md`。
- **原文巡检常态化**：定期重抓已收录出处，sha 变了就进同一个 triage 队列（分类 `value_changed`），和用户线索一起排。用户线索是补充，不是主力。

### 五、开关与兜底

- 入口只在**期刊库入口常量 `JOURNAL_CATALOG_UI` 开着**并且**「联系作者」可用**时出现；`TAVOTTO_NO_CONTACT=1` 或 `TAVOTTO_NO_JOURNAL_SYNC=1` 时都不出现（后者表示用户不想让期刊功能联网）。
- 发送失败（离线、被拒、额度）沿用 0145 的失败码闭集和文案：草稿留着，联网后可以再发。**预检、选择器、出处卡照常工作**，一律不报错卡住。
- 用户不写任何话、只点「发送」也算有效线索（带着规则键和当前值就够我们复核）；连链接都没有就归 `not_actionable` 之外的「待查」，由我们自己去找原文。

### 六、不做的事

- **不让用户直接编辑目录**，也不做「社区投票改值」：数值由原文决定，不由票数决定。
- **不统计搜不到的词**：搜索框是自由文本，按遥测白名单的结构性防线发不出去；需求排序靠用户主动发的「没有这本刊」和已有的读取记录（ADR 0155 §10）。
- **不做物质激励**（零节第 4 条）。
- **不把编辑部原话、用户上传的 PDF 放进目录或对外分发。**

## 后果

- 目录多了一条持续的线索来源，而且来自真正投稿的人；每条线索都有回音，用户能看到自己的报告起了作用。
- 产品侧改动面小：一个信件类型、一组结构化头、三个文字链接、一个 Agent 工具；出站、附件、回信、本机记录都不写第二份。
- 工作量主要落在 journal-data 的 triage 和流水线上，一期全人工；量起来以后靠二期门槛分流。
- `docs/privacy.md` 的「Contacting the maker」一节要补一段：期刊线索会发送哪些目录数据、附件结案后 90 天删除、不和期刊设备令牌关联。

## 附：一期线缆契约（diagnostics-api `/v1/messages/*`，API 1.6.0 → 1.7.0，加法）

`POST /v1/messages/init` 多一个可选字段 `journal`（对象）。有它，这封信就是期刊线索（服务端 `origin='journal'`）；它和 `report_id` 互斥，两个都带回 422 `bad_request`。

| 字段 | 必填 | 形状 |
| --- | --- | --- |
| `type` | 是 | `"wrong"` \| `"missing"` \| `"editor"` |
| `issue` | 否，只随 `wrong` | `"wrong_value"`（数值不对）\| `"updated"`（期刊已更新）\| `"link_broken"`（出处打不开）\| `"other"` |
| `journal_id` | `wrong` / `editor` 必填 | `^[a-z0-9][a-z0-9._-]{0,79}$` |
| `journal_label` | 否 | 单行，≤200 字（目录里的刊名，用来生成主题） |
| `query` | 否 | 单行，≤120 字（选择器搜索框里的字） |
| `rule_key` | 否 | `^[A-Za-z0-9_][A-Za-z0-9_.-]{0,119}$` |
| `current` | 否 | 单行，≤200 字 |
| `source_id` | 否 | `^(?:v2:)?[A-Za-z0-9_][A-Za-z0-9_.-]{0,79}$`（v2 出处原样带 `v2:` 前缀） |
| `url` | 否 | `https://` 开头，≤2000 字，不含空白、控制字符与 `user:pass@` |
| `catalog` | 否 | `{"v1"?: 1–999999 的整数, "v2"?: 同}` |

- 带 `journal` 时 `body` 可以为空（只点「发送」也是有效线索，第五节）；不带时照旧必填。
- `issue` 是用户在表单里选的问题类型，只给分拣用，可不选；随非 `wrong` 类型带上回 422 `bad_request`。
- `missing` 至少要有 `query`、`url`、附件三者之一，否则 422 `bad_request`。未知字段 422（与现有字段同一处置）。
- 主题：客户端可以留空；服务端在 `subject` 为空时按 `期刊线索：<journal_label 或 query 或 journal_id>` 生成（英文界面 `Journal tip: …`）。
- 幂等指纹把 `journal` 一并算进去：同一个 `client_message_id` 带不同的 `journal` 回 409（与改了正文同一处置）。
- 保存期：信件本身与普通来信相同（365 天）；`origin='journal'` 的附件在维护者结案（`closed_at`）后 90 天删除，信件正文与结构化头保留到 365 天。
- 通知（企业微信 / 邮件）标题前缀「期刊线索」，正文带 `type`、刊名、规则键，**不带 `url` 以外的用户正文全文**（与现有来信通知同口径截断）。
- 管理工具新增：`diag-admin msg export --kind journal --out <目录> [--all]`（默认只导出没导出过的，写 `exported_at`；每封一个子目录：`report.json` + 附件原文件）；
  `diag-admin msg close <message_id> --outcome accepted|rejected|duplicate|not_actionable`（写 `closed_at` 与 `outcome`；对非 `journal` 来信报错）。
- 客户端本机记录 `contactinbox` 的 `kind` 增加 `"journal"`；保存期与 `letter` 相同。

## 附：三期署名线缆契约（API 1.7.0 → 1.8.0，加法）

`journal` 多一个可选字段：

| 字段 | 必填 | 形状 |
| --- | --- | --- |
| `credit` | 否，只随 `wrong` / `missing` | 用户勾了「写上我的称呼」才带；NFKC + 去首尾空白后 1–32 字，单行，不含控制字符、Unicode 格式字符（含双向控制符）、`@`、`://`、`www.` |

- 随 `editor` 带上、或形状不合法，回 422 `bad_request`（与 `issue` 同一处置）。服务端存 NFKC + 去空白后的值；幂等指纹照旧包含整个 `journal`。
- `diag-admin msg export` 的 `report.json` 原样带上 `journal.credit`；通知正文不带称呼。
- 1.7.0 的服务端对未知字段回 422，所以**服务端 1.8.0 先部署**（部署要产品负责人当面同意），带 `credit` 的客户端改动才合入；客户端不做版本探测。
