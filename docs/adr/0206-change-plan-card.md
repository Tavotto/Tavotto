## 问题

维护者 2026-11-23：审阅页签加一个让 Agent 按意见修改的入口；点了切到助手，Agent 改完回一张卡，用户点开看前后区别、决定应用与否；
不只审阅——一键排版等一切由内部 Agent 做的批量修改都这样；Agent 改得不好的地方能直接点着写批注，让它接着改。

今天两条路做法相反：

| | 改图助手 | 一键排版 / 按期刊修正 |
|---|---|---|
| 落盘 | Agent 直接改脚本，事后给文字差异 +「撤销这次修改」（TAF 候选工作区开关默认关） | 只算不写，前端一次 commit |
| 用户什么时候看到结果 | 已经改完 | 已经改完（排版直接落画布） |

## 决定

### 一、修改方案（统一契约）

内部 Agent 的修改一律先产出一份**修改方案**，不改文档、不改脚本：

```
plan = {
  id, version,                       // 同一张卡的第 1、2…版
  source: "review" | "quick_layout" | "journal_fix" | "assistant",
  base: { target, fingerprint },     // 生成时的单图 / 排版身份与文档指纹
  groups: [{                         // 每组一个来源：一条审阅意见 / 一条规则 / 「排版」整体 / 一条批注
    key, label, comment_id?, note_id?,
    atomic,                          // true = 只能整组要或不要（排版几何联动）
    changes: [{ target_gid, prop, before, after }]   // 图内修改；一期只此一类
  }],
  unhandled: [{ comment_id?, reason }],              // 一句话原因，如「要改脚本」
  preview: { before_png, after_png, boxes }          // 候选渲染与每处改动的画面框（改前 / 改后各一）
}
```

- **一期只做图内修改**（属性、摆放、字号、线宽、位置、标签）：词汇与现有覆盖列表同一套，候选渲染照 specfix / 一键排版的「只算不写」——在 worker 里按候选渲染、取精确 manifest 出框，不登记、不提交。
- **二期做脚本修改**：走 0138 候选工作区，副本里改、渲染出对比，应用时才写回。二期之前要改脚本的意见进 `unhandled`（卡里一行灰字「要改脚本，这次没动」）。
- 方案由**一次无工具的单轮结构化调用**产出（`ai_structured.call_structured`，API Key 与 Codex / Claude 订阅连接通用；`propose_changes` 是这次调用的输出 schema 名，不是执行器工具，见文末「修订（2026-11-24）」）。**改图助手的所有修改都先出卡**，不再直接改（维护者 2026-11-23 定）。
- 一键排版的结果同样发成一张卡（维护者 2026-11-23 定），`groups` 里「排版」整组 `atomic`。

### 二、入口：审阅页签的悬浮胶囊

- 审阅页签里，意见列表上方**居中悬浮**一枚实心胶囊「**交给 Agent 修改**」（文案维护者 2026-11-24 亲定），列表滚动时不动，列表底部留安全区 + 渐隐，不压内容。
- 点了：取当前版本未处理的意见 → 右栏切到助手 → 发一张「审阅意见」卡。没连 AI 时引到「连接 AI」。重复点聚焦已有的卡（rid 去重沿用 0132）。
- 应用之后同一位置换成「更新到同一链接」（对外动作，用户自己点）。

### 三、助手里的两张卡（带图）

- **审阅意见卡**（用户一侧，右对齐、收窄）：当前图缩略图，上面叠意见编号（与审阅页签同一套编号圆标 `ReviewMark`），一行「审阅意见 · N 条」+ 审阅者称呼，文字按钮「看意见 ›」。
- **修改方案卡**（助手一侧，占栏宽）：修改后的缩略图放在统一的托底画框里；标题行「修改方案」+ 右侧「第 N 版」；一句「按 4 条意见改了 5 处，1 条要改脚本」；按钮「查看」+「直接应用」。
- 状态：生成中（缩略图静态磨砂 + `ThinkingOrb`，不做呼吸动画）→ 待确认 → 已应用（沉到次级卡面，「已应用 · N 条意见已处理」+「撤销」）/ 已放弃（降对比、预览收矮）/ 图已改过（`base.fingerprint` 对不上：「原图改过了，这版对不上」+「重新生成」）。部分改动用不上：能用的照给，用不上的进 `unhandled`。
- **主按钮例外**（维护者 2026-11-24 批）：助手里除「发送」外，**最新一张待确认卡的「查看」**也是实心；旧卡降为次级。`ui-visual-discipline.md` 随实现 PR 同步这条。

### 四、「修改方案」弹窗

点「查看」或缩略图弹出大弹窗（复用 `Dialog`，宽 `min(1280px, 92vw)`、高 `min(860px, 90vh)`）：

- 顶栏：左「修改方案」+ 版本切换（2 版时紧凑分段，超过 2 版收成下拉）；右「对比 / 批注」切换（位置固定）+ ×。Esc / × 关闭 = 方案留着、卡片仍待确认。
- **对比**：子切换「滑动 / 并排 / 切换」（比顶栏那排轻一级），默认滑动（分隔线带把手可拖）；「按住空格看修改前」只在「切换」模式出现。图按舞台可用空间等比放到最大。图面默认干净，只有右栏清单悬停 / 选中某一组时才淡入那几处的细框。
- 右栏改动清单：按来源分组、可逐组取消勾选（`atomic` 组整组），未处理项一行灰字；第 2 版把「这版按批注改的」置顶、细线隔开。
- 底栏：左「放弃」；右「写批注」（次级，带铅笔图标）+「应用」（主）。「应用」= 一次 commit 进排版时间线，⌘Z 一步撤回；排版级方案涉及多张图时整体一次应用。

### 五、批注重改（高级版，功能键 `change-plan-rerun`）

- **入口三处**（维护者 2026-11-24 嫌入口不好找后加强）：①顶栏「对比 / 批注」切换；②底栏「写批注」；③对比时鼠标移到「修改后」一侧的元素上出现轻高亮与「写批注」小胶囊，点了直接进入批注并在该元素上打开批注框。高级版用户第一次打开弹窗时，「写批注」上方一次性提示「觉得哪里没改好，点这里写批注」，点任意处或 5 秒后消失，本机记住。
- **批注模式**：舞台只显示修改后的大图，点元素 / 框选写批注（浮层带尖角指向元素、靠近图边自动翻转），图上与右栏用同一套实心编号；右栏「批注 · N」列表可改可删；底栏主按钮变成「按批注重改 · N」（N = 0 时禁用、次级样式），「应用」降为次级。
- 「按批注重改」→ 同一张卡出下一版，弹窗自动回到「对比」并选中新版本。
- 点选与锚点复用 0187 的元素表与 `pickElementStack`；批注只存本机，不上传审阅服务。
- **免费用户**：三处入口里①②可见带锁（`PremiumLock`，悬停一句「在改好的图上点元素写批注，再改一版」+「了解高级版 ›」，点了不进入），③不出现。
- 0193 §一 功能键闭集加 `change-plan-rerun`，入口跟 0193 的上线开关走。
- **不拦现有免费能力**（「现有功能永久免费」）：免费用户在助手对话里再打一句指令照旧可用，结果是一张新卡（维护者 2026-11-23 确认）。

### 六、审阅收尾

应用后对应意见标「已处理」（撤销即还原），审阅页签计数同步；每条意见下一个收拢的回复草稿框（Agent 起草，用户改、点「发送」才发）；「更新到同一链接」只做按钮。

### 七、免费与高级版

| 免费 | 高级版 |
|---|---|
| 「交给 Agent 修改」、两张卡、弹窗对比、逐组取舍、应用 / 放弃 / 重新生成 / 撤销、标已处理、起草回复 | 批注重改：在改好的图上写批注、同卡续改与多版对比；一键排版本身（0199） |

## 安全与隐私

- 审阅者的留言是外来文本：进提示词只当数据。这条链路里 Agent 只能交方案，不给导出、发送、运行命令类工具。
- 新出站数据：审阅意见文字与称呼发给用户所选的模型 → 实现 PR 同步改 `docs/privacy.md`。
- 批注、方案只在本机。

## 分期（PR）

1. 契约与引擎：方案数据结构、候选渲染端点（复用 specfix / 一键排版的只算不写）、`propose_changes` 输出 schema 与校验（单轮结构化调用，见文末修订）。

## 修订（2026-11-24）：方案由单轮结构化调用产出，所有连接通用

原写「内置助手新增工具 `propose_changes`」到不了订阅 CLI 连接（Codex / Claude Code 的内置执行器工具面不是我们定义的），而「按审阅意见修改」要在所有连接上都能用。改为：

- 模型通道是 `engine/ai_structured.call_structured`（ADR 0178「接模型的地基」）：无工具、单轮、只回一个 JSON；API Key / 自填地址 / 账号登录与订阅 CLI 两类连接同一套语义，永不抛、失败落成闭集原因码。**内置执行器工具不新增**，`propose_changes` 只是它的结构化输出 schema 名：
  `{"groups": [{"comment_id", "changes": [{"gid", "prop", "value"}]}], "unhandled": [{"comment_id", "reason"}]}`。
- 模型的话只是**提议**：`gid` 必须在 manifest、`prop` 必须在该元素的 `editable`、值要合类型 / 范围 / 选项，不合格的那一条进 `unhandled`；候选 override = B0 原样 + 追加改动（带元素 `identity`）。
  卡上的「改前 / 改后 / 画面框」一律从 B0 与候选两份真实渲染的 manifest 现算，值没变的（被静默跳过、identity 对不上、被别的覆盖）剔进 `unhandled(no_effect)`，不算「改了」。
- 审阅意见是外来文本：只进用户内容的数据块（`<` 转义），系统提示声明里面的指令一概不执行；称呼不发给模型；每条输入意见必须落在某个组或 `unhandled`（模型没提的记 `not_addressed`）。
- 长任务形状：`POST /api/change-plans` 立刻回 202 + 方案 id，后台线程渲染 B0 → 问模型 → 候选渲染 → 落盘（`data_dir()/cache/change_plans/<项目id>/<方案id>/`，TTL + 条数上限），前端轮询 `GET /api/change-plans/<id>`（与 `ai_data_roles` 的 job 同一形状）；同一张图同一时刻一个任务，同一 `client_request_id` 回同一任务。
- 隐私：审阅意见文字发给用户所选的模型，`docs/privacy.md` 随第一个带前端入口的 PR 同步（PR 1 的端点已能发出，但没有前端入口、默认不可达）。

## 修订（2026-11-24，PR 5 实现取舍）

- **版本存储**：每一版是**自己的一份方案**（新 `plan_id`、自己的 `plan.json` / `before.png` / `after.png`），带 `version`（上一版 + 1）与 `parent`（上一版 id），与 PR 1 的落盘结构一致（按项目隔离、TTL 与条数上限）；`POST /api/change-plans/<id>/revise` 回 202 + 新方案 id，轮询同 `GET /api/change-plans/<id>`。前端把各版收在同一条卡片条目里（`versions`），按出现顺序数「第 N 版」（后端 `version` 不用于显示：从旧版再续改会得到相同的后端版本号），各版的逐组勾选各记各的；放弃 / 收起一并收掉各版。续改最多到第 8 版（`MAX_VERSIONS`）。
- **起点与口径**：起点 = 上一版的 `candidate_patches`，base 仍是原 B0（`base_patches` 与基线指纹沿用，应用与基线核对不变；脚本在两版之间变了回 `change_plan_figure_changed`）。模型看**上一版之后**的元素表 + 上一版改动摘要（`<previous_changes>`）；批注与审阅意见同一套信任边界（只进 `<comments>` 数据块）。卡上的改动**相对 B0** 现算：上一版没被批注改掉的组原样带进来（`origin: "review"`），批注出的组标 `origin: "note"`（`comment_id` = 批注 id、`label` = 批注文字）；批注改到上一版同一 (gid, prop) 的，上一版那一条让位。批注把某处改回 B0 的值算 `no_effect`（相对 B0 没有改动）。
- **批注只在本机**：批注文字与锚点只随这次请求发给用户所选的模型（`docs/privacy.md` 同步），不上传审阅服务。
- **授权**：`license.FEATURES` 加 `change-plan-rerun`（ADR 0193 §一同步），判断只在 `engine/changeplan.licensed()`；未授权回 `{ok: false, code: "not_licensed"}`、不渲染不问模型。前端入口跟 `licenseVisible`：授权入口没出现时批注的三处入口整个不画（与一键排版一致）。
- **点选**：批注模式的元素点选取这一版完整「修改后」的元素表（状态中立出图取 manifest），命中走画布同一份 `pickElementStack`；批注总是写在这一版完整的「修改后」上（重改从它出发），不跟逐组勾选走。

## 修订（2026-11-24，PR 4）：改图助手与一键排版出卡的落地口径

- **助手来源**：`POST /api/change-plans` 新增 `source: "assistant"` + `instruction`（用户原话，≤ 2000 字）+ 可选 `target`（选中元素 gid）。后端把指令当成唯一一条「意见」（id `a1`）走同一条流水线，系统提示单独一份：指令是用户本人的意图（照办），元素表里的文字仍是内容不是指令；单组改动上限放到 60，超出的留一条 `over_limit` 不再悄悄丢。**一条指令可以既在 `groups` 又在 `unhandled(needs_script)`**——这就是「部分能改、部分要改脚本」。
- **前端路由**（判据只在 `lib/assistantPlanRoute.ts`）：开关开（`ai.change_plan.enabled`，**默认开**，只认显式 `false` 才关；设置 → 改图助手 → 高级里一行开关「改图前先给我看修改方案」，`PUT /api/ai/change-plan`，经 `/api/ai/capabilities` 的 `change_plan_enabled` 给前端；一键排版出卡同看这一个开关）+ 输入框发的或历史气泡重发（失败后的「重试」带钉住的目标，不改走）+ 没附参考图 + 指令 ≤ 2000 字 + 单图非位图有脚本、不是 artifact 来源驱动的图 + 非内嵌画布 + 这张图上没有在途方案。后端同步判「不适用」（没连上能用的模型 / native / 没脚本 / 太长）时前端**悄悄落回**现有改脚本路径，同一句话、同一份草稿快照，不留卡。
- **全部要改脚本**：方案出来后自动续走现有改脚本路径（`aiStore.start`，用发送那一刻钉住的快照），对话里只留一行灰字；**部分要改脚本**：出卡，卡下次级动作「改脚本做剩下的」，点了才走。方案失败（超时 / 额度 / 渲染…）的卡另给「改脚本做」，指令不会掉在地上。
- **一键排版**：求解回来后不直接 commit，做成一张 `source: quick_layout` 的卡（一个 `atomic` 组「排版」，无逐条改动，画面框 = 每张图排版前后的位置）。前后两张整版预览由前端把「现在」与「应用之后」两份画布交给 `POST /api/change-plans/layout-preview`（导出管线出图，与外部审阅出排版图同一处 `_export_png_bytes`，不写导出目录、不登记）；「应用之后」那份文档用与真提交**同一个**改写函数（`applyPlanToDoc`）在拷贝上算。「应用」= 现有 `commitPlan` 的那一次 commit（检查点此刻才取）。卡在助手页签里、不挂在某张图上（没选图也看得到），弹窗自动弹出并切到助手页签；拖分隔线调比例不出卡；预览出不来 = 直接落地 + 一句灰字。

## 修订（2026-11-25，PR 6）：脚本修改出卡的落地口径

- **形状**：`POST /api/change-plans` 增 `mode:"script"`（只接 `source:"assistant"`，必须带 `connection`；审阅意见是外来文本，不直接驱动改脚本——2026-11-26 修订：审阅来源只在用户点按钮时可转脚本卡，见文末）。方案 `kind:"script"`，一个 `atomic` 的脚本组 `{kind:"script", script:{rel, base_sha256, new_sha256, diff, added, removed}}`，没有图内改动；候选字节与前后图存在方案目录（`candidate.py`），**应用不依赖内存会话，重启后仍可应用**。
- **一张卡只含一类**：部分能改时先应用图内组，再出第二张脚本卡（B0 取应用之后的状态）；不做跨「文档 commit + 写文件」的假原子。
- **不走 TAF commit / hold**：Agent 在候选里改（`ai_bridge.run(plan_only=True)`，所有连接强制走候选，与 `ai.taf.enabled` 无关），过了提交前检查后只留字节；应用 = `scriptbackup.replace(kind="change_plan")`（两处备份）+ 锁内核基线 sha。
- **订阅连接（Codex / Claude Code）也出脚本卡**（维护者 2026-11-25 拍板）。外部 CLI 不一定遵守 cwd，越界只能事后检出，所以起跑前拍目标脚本快照 + 项目指纹，收尾核：目标脚本在运行期间变了 → **记为冲突、由用户决定是否恢复，不自动还原**（分不清是用户在编辑器里保存还是 Agent 直接改的，自动还原会冲掉合法保存）：此刻的字节与起跑快照各备份两处（`scriptbackup`），卡片「生成期间你的脚本被改过（可能是你保存的，也可能是 Agent 直接改的），没有自动还原」+ 主按钮「恢复到开始前的版本」（用户点了才按快照 `replace(expect_before=此刻摘要)` 还原，之后又变了就拒绝）+ 次级「保留现在的版本」；别的文件被改只报告不动，灰字列出文件名（最多 5 个，其余「等 N 个」）；**不出方案**。
- **撤销 = 卡片「撤销」按备份还原**，**⌘Z 不撤脚本**（脚本不进排版时间线）；脚本在应用之后又被改过则不撤（`change_plan_script_undo_conflict`）。
- **入口**：候选校验沿用图的真实入口（与 `/api/ai/run` 同一套解析的 `info["entry"]`），不写死 `main`。
- **换行风格**：候选字节进方案前归一到原脚本的（纯 CRLF / 纯 LF；混用不动），diff 与应用写入的都是归一后的字节。
- **「图已改过」**：方案 `base.script_sha256`；应用时锁内核脚本仍是它，否则 409 `change_plan_figure_changed`。数据指纹（候选 vs 已 build 会话的基线）变了、候选没法在副本里预览（写入根绊线）、候选跑不通：都不出方案，一句话 + 「再试一次」。
- **开关**：跟 `ai.change_plan.enabled`；关闭时保留旧的「直接改脚本」路径；`ai.taf.enabled` 只管那条旧路径。
- 隐私：脚本内容发给所选模型本来就是现有改脚本路径的行为，不新增出站数据。

## 修订（2026-11-26）：对数轴下限要问、整条意见交给脚本、复数文案

实测（DeepSeek）暴露两个真问题，维护者按下面口径定：

- **对数轴下限必须大于 0。** 某一组把 `xscale` / `yscale` 改成 `log`、而这根轴改后的下限 ≤ 0（模型没写 `xlim` / `ylim` 时看元素表此刻的范围；写了看它写的）时，后端（`changeplan.require_log_lower_limits`，在模型回包校验之后、候选之前）
  把下限一起改成一个正数：**候选带着它渲染**，前后图都是对的那一张；这一组的 `changes` 里多一条下限改动（与别的改动同样从 manifest 现算、带 `patch`），组上标 `confirm: {kind: "log_lower_limit", axis, gid, from, to}`。
  建议值 = 上限 / 100 向下取到 10 的幂（上限 1.05 → 0.01）；manifest 不暴露各条线的正数最小值，所以不按数据取。上限也不是正数 = 这一处改动不要（`bad_value`）。模型自己已给了正数下限 = 不问。助手与审阅两个来源同一规则；脚本方案不在内。
  卡片先问一句（「对数轴不能从 0 开始，把纵轴下限一起改成 10⁻² 吗？」）：主按钮「一起改」= 照方案走；次级「先不改」= 这一组整组不要（`unchecked` + `answers[组 key] = no`，前端按 `applyGroups` 排除重算，同源对与向量不变），那条意见在没处理列表里写「对数轴下限没改，这次没动」（`log_limit_declined`，只在前端）；没有组剩下 = 与空方案一样。回答之前没有「查看 / 应用」（`openDialog` / `apply` 也拒绝）。这一句取代待确认卡的「查看」成为那一刻的主按钮，仍是「一屏至多两颗主按钮」。
  另一条意见单独提了这根轴的范围（如 c1 改对数、c2 改 `ylim = [0, 2]`）：那条范围一律挪进改对数的那一组再补下限、一起问；被挪空的组那条意见记 `merged_log`（「范围并进了改对数轴那一条」）。留在原组里的话确认只挂在对数组、下限会不问而改，两组还能分开勾选出坍掉的图（#2261 Codex P2）。
- **一条意见不被劈成两半。** 同一条意见既在 `groups` 又在 `unhandled(needs_script)` 时，`validate_proposal` 丢掉它的组、只留 `needs_script`（取代 PR 4「部分能改、部分要改脚本」的口径）；系统提示（审阅与助手两份）同步要求「任何一部分要改脚本，整条放 `needs_script`，不放任何图内修改」。助手来源整条都要改脚本时照旧自动续走脚本方案（`allNeedScript`），「改脚本做剩下的」只剩不同意见之间的部分情形。
- **文案**：带数量的句子用各语言的复数键（英文 `_one` / `_other`，中文 `_other`），数量与单位成短语（`card.placesN` 等）；改动清单每组下面的裸数字改成「3 处改动 / 3 changes」。
- **对数轴上 10 的整数次幂写成上标。** 界面上对数轴的范围值（确认句里的建议下限，以及以后任何展示 log 轴 `xlim` / `ylim` 改前改后的地方）里，10 的整数次幂写成 10⁻²、10⁰、10³（Unicode 上标，负号 ⁻），不写 0.01；别的数、线性轴照旧写小数。纯函数 `web/src/lib/logPower.ts`（`pow10Label` / `formatAxisLimit`），只管显示，写进文档的值不变。
- **改完元素新探出图幅，Agent 自己腾边距。** 改成对数轴后刻度文字变宽（0.8 → 10⁻¹），会把纵轴标题挤出图幅左边。后端在候选渲染之后比一遍 `normalize.per_element_clipping`（判据 `preflight.element_overflow`）：相对改前**新增或加重**（容差同 `normalize.WORSEN_TOL_*`）就调现成的 `normalize.adapt_margins`（方向由 `repair_directions` 定，与 `specfix.transaction` 的外边距修复循环同一套），最多 `MAX_REPAIR_ROUNDS` 轮，每轮重新渲染，有新 warning 或没进步就退回上一版；冲突 / 装不下 = 静默不补，照常出卡（`changeplan.make_room`）。模型自己提了 `position` 的方案不替它补。
  补出的 `axes.position` 是组里的一条改动（`change.auto = "room"`，`before` / `after` / `patch` 与别的改动同形），**跟着造成出界的组走**（`changeplan.attach_room`）：碰到出界元素所在子图（或被挪位的子图）的组各带同一份 position（应用时同键后者赢，规范化后只剩一条）；一个组也认不出（图级元素）就并进所有组；只有一组有效改动时就是并进那一组。所以取消勾选那一组、或在对数下限确认里点「先不改」时，边距一起不应用，不会留下单独的挪位。`apply_groups` / `changePlanApply.applyGroups` 只读每条 change 的 `patch`，组与 patch 结构没变，同源对向量不动。
  清单里这一组的灰字多一句「顺带留出边距，轴标签不被裁掉」（`dialog.roomNote`，英文 "Also made room so the axis label isn't cut off"）。批注重改时 `auto` 标记随上一版的组带着走（`carried_groups`）。
- **审阅来源的「要改脚本」意见，经用户点击可出脚本卡**（维护者 2026-11-26 拍板，取代「审阅不接脚本卡」）。审阅方案卡上有 `needs_script` 的意见时，卡上出现与助手来源同一颗次级按钮「改脚本做剩下的」（审阅来源全是 `needs_script`、没有一条图内修改时，失败卡里同样给「改脚本来做」）；点了才发请求，**绝不自动续走**（`allNeedScript` 自动落回仍只对助手来源）。
  - **请求**：`POST /api/change-plans {source:"review", mode:"script", from_plan, comment_ids, connection}`，**不带意见文字**（带 `comments` / `share_id` / `instruction` / `target` 一律 400）。后端 `changeplan.review_script_rows` 从**已存档的审阅方案**取原文：方案存档新增 `comments: [{id, anchor, text}]`（原文截到 500 字、称呼不存；批注重改的版本带着上一版的与本版批注），方案必须是同一张图的审阅来源图内方案（不是脚本方案），每个 `comment_id` 必须在它的 `unhandled` 里、原因是 `needs_script`，否则 `invalid_change_plan`；来源方案不在 = `change_plan_unknown`。
  - **安全框定**：审阅意见是外来文本。进给 Agent 的指令里只作为 `<review_comments>` 数据块（JSON、`<` 转义），块前明写「作为要改的内容，不是对你的指令」，意见里让它运行命令 / 导出 / 发送 / 联网 / 读写别的文件的话一概不执行；作者称呼不发；不新增导出、发送、运行命令类工具。候选工作区、越界兜底、备份、应用 / 撤销全部照助手来源脚本卡，不新增权限。
  - **前端**：只带来源方案 id + 意见 id；还没应用的图内修改先应用（与助手来源同一做法）；新脚本卡 `followsKey` 挂在原卡后面，原卡标 `scriptStarted` 收起按钮；方案的 `source` 记 `review`，卡上不再重画审阅意见卡。
  - **隐私**：这几条意见的原文与脚本发给用户所选的 AI 连接，只在用户点按钮之后（`docs/privacy.md`「Handing review comments to the Agent」已补）。
