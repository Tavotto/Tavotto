# ADR 0140 — 版本时间线：每版一个信封文件 + 小索引

状态：Proposed（D1a：存储模块 `engine/versionstore.py` 与测试；D1b：端点经 `_Timeline` 接线，读兼容新旧、默认仍写旧格式）。
关联：issue #263（存储形状）、#264（旧文件损坏的出路）、ADR 0101（排版时间线）、ADR 0023（`atomicio`）。

**1.0 收敛纪律例外：维护者 2026-10-20 批准。** 换存储格式是对稳定模块的重写，本来落在
「禁止趁机重写」之内；这里按例外登记 D1 及之后（D1a 模块、D1b 读兼容接线、D2 翻默认、D3 策略与清理）。
D0（跨进程锁与 id 唯一，correctness / 数据安全）不需要例外，另案进行。

## 一、问题与实测

一份文档一个 `<doc_id>.json`，形状 `{"versions":[{id,name,ts,auto,named,description,moment?,canvasId?,canvasName?,doc:<整份文档>}…]}`
（`app._load_versions` / `_save_versions`）。每次追加 = 读整份 → 解析 → 追加 → 裁 → 整份重写。
2026-10-20 审计树（origin/main `9ab0daa14`）实测：

| 文档 | 保留条数 | 单次追加 | 单次写盘 |
| --- | --- | --- | --- |
| 100 对象（23 KB）满 120 条 | 120 | 30–40 ms | 2.3–2.8 MB |
| 5 000 对象（1.16 MB） | **21**（被 24 MB 字节上限挤掉） | 360–430 ms | **24.4 MB** |

列表端点每次打开抽屉要解析 24 MB（约 340 ms），取单个版本同样要先解析全部。

共同前提：「整份历史 = 一个 JSON 文档」⇒ ① 追加 / 改名 / 删除 / 取单个 / 列表都是 O(总量)；
② 唯一的体积闸只能按文件总字节裁，条数与文档大小耦合；③ 并发安全只能靠整份读-改-写外面套锁；
④ 任何一次写失败，影响面是整份历史。

被否决的路径：JSONL 追加日志（删除 / 裁剪仍要压实整份）；SQLite（`tavottofile/` 随项目备份 / 同步，
WAL 文件在同步盘上是老牌损坏源，且引入第二套落盘纪律）；只存 diff（恢复链一环坏全链坏）；
内容寻址去重与压缩（收益需真实文档复测，列为 D3 可选）。

## 二、布局

```
<versions>/<doc_id>.json          旧文件：迁移后冻结（不删、不改、新程序不再写）
<versions>/<doc_id>.vx/           新存储
    index.json                    提交点：{format, gen, updated, entries:[…], legacy_unreadable?}
    migration.json                迁移记录（仅从旧文件迁来的文档有）
    s/<vid>.json                  信封（第 0 代）：第 1 行 = 头 JSON {format, seq, gen, entry, doc_len, doc_sha}，第 2 行 = 文档正文
    s/<vid>.<gen>.json            元信息更新写出的新一代（gen ≥ 1）；信封一经写下**不可变**
<versions>/thumbs/<doc_id>/…      缩略图，不动
```

* 目录名用 `<doc_id>.vx/`，**不用** `versions/<doc_id>/`：`versions/thumbs/` 已是缩略图根目录，
  `doc_id == "thumbs"` 的文档会让快照目录与它相撞；doc_id 里没有 `.`，`.vx` 撞不上任何其他名字，
  也避开旧程序对 `*.json` 的扫描。
* **新索引绝不与旧文件同名。** 若索引沿用 `<doc_id>.json`，旧程序会把没有 `doc` 的条目当历史，
  下一次整写（`_save_versions` 没有格式校验）就静默毁掉它。
  看护：`tests/test_versionstore.py::test_index_never_shares_a_name_with_the_legacy_file`。
* 索引条目 = 原条目（不含 `doc`）+ 簿记字段（`_seq` 追加序号、`_gen` 生效的信封代数、`_bytes` 信封字节、`_legacy_bytes`
  它在旧文件里占的字节、`_doc_sha`）。簿记字段带下划线，`public_entry` 去掉后与旧条目（去掉 `doc`）逐字段相同。
  元信息的权威在索引，**信封头带一份副本供重建**。每条约 190 字节，120 条约 22 KB。
* 信封两行格式无歧义：`dumps_json` 在 `indent=None` 下把换行转义。

## 三、事务语义

全部复用 `atomicio.write_bytes`（同目录 tmp → fsync → `os.replace` → fsync 目录）。

* **追加**：确保索引存在（首次追加先落一份空索引）→ 写信封 → 过策略 → **写索引（唯一提交点）** →
  best-effort 删被裁信封。信封写失败：索引未动。索引写失败：旧索引完好，多一个孤儿信封。
  先落空索引的理由：首次追加在「信封写完、索引提交前」被杀时，重开看到的是空历史，而不是被「重建」
  收养的半成品。
* **删除 / 裁剪**：**先写索引，后删信封**。孤儿信封比丢索引好，反过来不行。
* **改名 / 改说明 / 转正**：信封不可变——写这一版的**新一代**信封 `<vid>.<gen+1>.json`（O(单版)），再写索引（`_gen` 指向它，
  唯一的生效点），**索引提交之后**才删旧一代；之后过策略，受护的是被改的这一条。提交前崩溃或索引写失败时，
  索引仍指向旧一代，`read()` 读到的是已提交的元数据，新一代只是孤儿。
* **读索引四档**（对齐 `layoutsession`）：不存在且无信封 = 尚无存储；正常；字节坏 / 形状不对 →
  重建（写路径先把原字节存成 `index.corrupt-<sha>.json`，只读路径只在内存里重建、不落盘）；
  `OSError` 或来自更新的格式 → `IndexUnreadable`，**拒写、不重建**（不知道那里是什么）。
  “字节坏或形状不对”包括**逐条结构自检**不过（条目不是 dict、id 不合形状、簿记字段缺失或类型不对）：
  语法合法的 `{"entries":[null]}` 同样当损坏重建。
* **读单个版本**：按索引取信封，核 `doc_len` / `doc_sha` 与索引 `_doc_sha`；对不上只标坏这一条
  （`EnvelopeCorrupt`），不拖垮整条时间线。
* **索引重建**：只读每个信封的第 1 行，按 `seq` 还原顺序，改名因头里带元信息而保留；结果带
  `recovered: true`（已删 / 已裁但信封还在的版本可能复活，调用方应告知用户）。重建不校验正文，
  正文损坏在读该版本时由 `doc_sha` 兜住。每个 id 取**最高的一代**，所以索引丢失时，最后一次尝试过但
  没来得及提交的元数据可能被采用（只影响名字 / 标签，不影响图内容）；已提交的改名不会丢。
* **孤儿信封与 tmp**：孤儿 = 索引之外的 `s/*.json`，**不自动收养**（可能是已删 / 已裁的版本），
  `gc_orphans` 按年龄（默认 ≥ 1 h）清；索引缺失 / 损坏时一个信封也不删（它们是重建的原料）。
  `.tmp` 要**两处**都扫：索引 tmp 在 `.vx/`，信封 tmp 在 `.vx/s/`（用 `atomicio.reap_orphan_tmps`）。
* **跨进程互斥**：本模块不取锁，调用方在 D0 的 `<doc_id>.versions` 跨进程文档锁内调用（文档锁条带只看
  文件名，用 `<doc_id>.json` 的路径会与同名自动保存槽位共用条带）。

## 四、迁移与回滚

读侧：新存储有索引（或有信封且无未完成的迁移记录）→ 它是权威；否则读旧文件。迁移在**第一次写入**时、
锁内做，读不写盘。

1. 旧文件 `loads_document` 解析（失败 / 形状不对 / id 不合 `_VERSION_ID_RE` / 含写不出的数 →
   `LegacyUnreadable`，不建任何东西）；
2. 写 `migration.json`（`state: pending`，含旧文件 size / mtime_ns / sha256 / 条数 / id 集合）；
3. 逐条写信封（已存在且逐字节一致的复用 → 幂等）；
4. 读回逐字节校验；
5. 写索引（提交点），读回核 id 序列；
6. 把迁移记录改成 `committed`。

**旧文件全程只读，从不删、不改、不改名。** 崩溃点：2–4 之间被杀 → 无索引，读侧仍以旧文件为权威，重跑复用信封；
5 之后被杀 → 索引已是权威且完整，重跑补记 committed。旧文件里重复的 id（D0 之前跨进程撞 id 的遗留）保留先出现的一条，
条数记在迁移记录里。

**回滚语义（方案 A：新目录 + 冻结旧文件 + 不双写）。** 降级后旧程序读冻结的旧文件：看到迁移那一刻的历史，
之后新程序产生的版本旧程序看不到（仍在 `.vx` 里），新历史不会被毁。旧程序继续在旧文件上追加；再升级后
`migrate_legacy` 先比 size + mtime_ns、变了才比 hash，发现分叉就把**迁移点之后新增**的条目按 id 去重导入——
迁移记录里的 id 集合（每次导入刷新为这次观察到的**全部**旧文件 id，所以崩在索引提交与记录更新之间后重试也不漏）保证新存储里已删除的版本不会因导入而复活，不覆盖、不丢。旧程序对已有条目的改名 / 删除
不回流（只导入新增）。双写（抵消 #263 全部收益）与沿用旧文件名（见 §二）均否决。

发布节奏（D1b / D2 的约束，非本 PR）：先发读（能读 `.vx`、默认仍写旧格式），再翻写默认，这样回滚到上一个
版本仍能读到新历史。旧文件的清理不在 D1/D2，D3 且需迁移记录与旧文件 sha 一致、晚于至少一个稳定版本。

## 五、#264：旧文件损坏

迁移时旧文件解析失败 → **新存储开一份空历史，旧文件原样保留**，索引带 `legacy_unreadable`
（旧文件名 / 大小 / sha）作为列表响应里可恢复的标记，不再 409 卡死。旧文件不会被覆盖，所以
`_refuse_blind_full_overwrite` 防的风险随之消失。模块已提供 `init_empty`；**这一条在 D2 接线时实现**，
此处记为决定。

## 六、策略

* **D1 / D2：保留现行条数与 24 MB 字节语义逐字不变**（自动 60、未命名总数 120、总字节 24 MB；
  命名节点不参与牺牲，ADR 0101）。换存储与调策略分开评审。`versionstore.legacy_policy` 是现行
  `_prune_versions` + `_save_versions` 字节循环的镜像，字节账按旧文件的算法（`_legacy_bytes`），
  `test_legacy_policy_matches_save_versions` 与 `test_incremental_append_with_legacy_policy_tracks_the_current_save_versions`
  与现行实现逐条对拍。策略是参数（`Policy`），模块本身不内置阈值以外的假设。
* **D3**：条数上限 120 + 独立的每文档磁盘预算（默认 256 MB），按现行牺牲顺序最老的先淘汰，
  **命名节点豁免**（现行没有单独的「钉住」概念，命名节点就是受保护的那一档，ADR 0101）。大文档因此
  可以回到 120 条（1.16 MB 文档约 139 MB，仍在预算内）。

## 七、原型实测摘要（不进仓库）

追加耗时与历史长度无关（1 000 对象：2.5 → 3.4 ms；每次写盘 253 KB = 一个信封 + 22 KB 索引，现行 25 MB）；
80 次随机 SIGKILL（约 2 300 次已确认追加）0 丢失 0 损坏；索引删除 / 截断后 120 条 4–5 ms 重建；
迁移 109 条 / 25 MB 旧文件约 1 s，逐条与旧条目相等。
