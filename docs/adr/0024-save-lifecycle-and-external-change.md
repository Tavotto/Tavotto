# ADR 0024：保存生命周期、外部修改检测与检查点的画布身份

状态：**Accepted**
日期：2026-08-29
相关：[0023 文档落盘的唯一权威](0023-document-persistence-authority.md)（修订号在那里产生）、
[0001 项目/画布/标签/对象层级](0001-project-canvas-tab-object.md)（检查点的画布身份是这个层级的一维）、
本轨道文档 [`docs/implementation/product-ux-reliability/`](../implementation/product-ux-reliability/STATUS.md)。

## 裁决摘要

| 问题 | 裁决 |
|---|---|
| 保存状态放哪 | `documentStore.saveState`，六个值的**文档字段**；不是 `window` 事件 |
| `recovery_available` / `read_only` | **不进那个枚举**，走正交的 `docNotice`（见 §2） |
| 外部修改基线 | 内容 hash（`base_revision`），强于 updatedAt（`base`）；带了就以它为准 |
| 「磁盘上应该没有这份文件」 | 哨兵 `base_revision=absent`，**判据两条边都钉住** |
| 基线缺席时 | 写之前先 GET 确认一次，**没有例外** |
| 冲突未决时 | 只写本机副本，一次都不再撞磁盘；出口 = 重新加载 / 明确覆盖 / 另存为 |
| 崩溃恢复 | 主文档照常打开，本机副本挪进 `tavotto.recovery.<id>` 等裁决 |
| `⌘S` | **真的保存**（等到写完）；`⇧⌘S` 才是「另存为画布文件」 |
| 关闭保护 | 只在 `dirty` / `saving` / `save_error` / `conflict` 时拦 |
| 版本检查点 | 记 `canvasId` + `canvasName`；恢复落到**它自己那张画布** |
| 排队中的写入属于哪个项目 | **排队那一刻**的 pj，跟着载荷走 |

---

## 1. 背景：改造前「保存」没有状态

`819ca2f` 上，用户能看到的保存信息只有顶栏一行字，它从两个布尔现推：

```ts
{dirty || !lastPersisted ? t('topbar.saving') : t('topbar.savedAt', …)}
```

于是「保存中…」同时表示三件事（有未保存修改 / 正在写盘 / 刚打开还没存过），
而写盘失败之后这行字照样显示「已自动保存 14:03」——`flushAutosave()` 在
**排队那一刻**就把 `dirty` 清掉了，失败只派了一个 `CustomEvent`，由 App.tsx
弹一句 4.5 秒后自动消失的状态条。用户回到界面时什么都看不到，而磁盘上那份
还停在 13:58。

三条 P1（`STATUS.md` 的 R-03 / R-06 / R-08）都是这个形状的变体：**一个持续
存在的事实被当成一次事件报告掉了**。

## 2. 保存状态是文档的字段，但不是一个大枚举

Prompt 03 §二 列了八个状态并列：`clean` / `dirty` / `saving` / `saved` /
`save_error` / `conflict` / `recovery_available` / `read_only`。

我们只把前六个做成 `SaveState`，后两个走 `docNotice`，因为它们与保存进度
**是两根互不相干的轴**：

- 「本机还留着一份没人裁决的副本」与「当前这次编辑存到哪一步了」可以同时
  成立。塞进同一个枚举，两者就会互相顶掉——恢复副本还在本机躺着，一次成功
  的自动保存把状态推成 `saved`，横幅没了，而那份副本一直到下次启动才再被
  想起来。这个 bug 在实现过程中真的出现过一次（`openRecentDocument` 里
  `switchDocument` 的落盘回调把刚设上的 `recovery_available` 覆盖掉）。
- `read_only` 更明显：schema 太新的那份文档**根本没有打开**。当前文档是一份
  崭新的空白文档，能存能改。把它说成「当前文档只读」是错的；真正的事实是
  「磁盘上的**另一份**读不了，而它一个字节都没被动过」。

`docNotice` 因此是一个 sum type，同一时刻至多一件：
`{kind:'recovery', docId, summary}` | `{kind:'schema_too_new', docId, schema}`。

**这条与 Prompt 的字面不同，是有意的**：Prompt 的退出条件是行为（恢复可预览
可恢复、只读不伪装可保存），不是枚举里必须有那两个字面量。

## 3. 外部修改检测：两个基线，两个维度

改造前只有跨标签页的乐观并发：`?base=<updatedAt>`。它看不见编辑器外的改动
——脚本、同步盘、另一个编辑器改完 `tavottofile/*.json`，往往一个字节的
`updatedAt` 都不动，甚至写回一个更小的值。那种改动 `base` 一律放行。

新增 `?base_revision=<内容 hash>`（hash 来自 ADR 0023 的 `content_revision`）。
它**强于** `base`：谁改都瞒不过字节。带了 `base_revision` 就以它为准，
`base` 只服务不发修订号的调用方。

### 3a. 判据的两条边

`_revision_conflict(base_revision, current)` **故意不对称**：

| 基线 | 磁盘 | 判定 | 理由 |
|---|---|---|---|
| `absent` | 有文件 | **冲突** | 那份内容不是我的，整份 PUT 就是把它删掉 |
| `absent` | 无文件 | 放行 | 首次写 |
| hash | 另一个 hash | **冲突** | 有人动过 |
| hash | 无文件 | 放行 | 挡的是「覆盖别人的内容」，不是「重建一个被删掉的文件」 |

`absent` 哨兵不是锦上添花：少了它，两个标签页同时新建同一份文档时双方都
拿不出 hash，后端一律放行，后写的那个整份盖掉先写的——**而这正是这条判据
要挡的事**。判据只钉一条边，就会从另一条边漏。

### 3b. 基线缺席 = 写之前先确认，没有例外

`diskRevision` 里没有这个 id 的条目 = 本会话从没确认过它的磁盘状况。此时
`ensureDiskKnown()` 先 GET 一次：磁盘上真有一份我从没读过的内容，那就是
冲突，不是「首次写」。

落在这条上的有四种情况：新建文档、载入画布文件、读盘那次抛了异常、应用
启动时那份还没被切换过的初始文档。写一条「只有读盘失败时才确认」的规则更
省一次 GET，但那三种一样是两个基线都拿不出来。**判据留了例外就会从例外
那一侧漏**，代价只是每份文档第一次落盘前多一个 GET。

### 3c. 冲突未决时不再碰磁盘

进入 `conflict` 后，防抖自动保存**只写本机副本**。继续往磁盘上撞只会继续
409，而每撞一次就多一条「保存失败」，用户以为自己遇到了四个问题。内容一个
字节都没丢——它在 `tavotto.autosave.<id>` 里等裁决。

三个出口：**重新加载**（加载前把当前内存版本挪进恢复槽位，所以它不是一个会
丢东西的按钮）、**明确覆盖**（拿 409 里回的 hash 当基线，**不是清空基线**：
清空等于用户按一次「覆盖」就把这份文档的外部修改检测永久关掉了）、**另存为**。

## 4. 崩溃恢复：不再静默取胜

稳态下 localStorage 里没有文档主体（写盘成功就删）。所以启动时还留着一份
副本，含义只有一个：上次写盘没成。

改造前 `readAutosaveDoc` 按 `updatedAt` 挑一个赢家并把赢的那份**立刻推回
磁盘**——用户从没被问过，而被推上去的可能正是他不想要的那份。这正是 Prompt
§五 明令禁止的「启动时自动覆盖主文档」。

现在：主文档照常打开；本机那份**挪**进 `tavotto.recovery.<id>` 等裁决。
挪而不是拷，因为原槽位是「在途的兜底副本」，下一次 flush 就会按当前内存内容
把它覆盖掉。恢复动作只进内存并置 `dirty`——**用户确认保存后才覆盖主文档**。
本机副本不比磁盘新时直接删掉，不打扰用户（「旧 autosave 不提示」）。

## 5. 检查点的画布身份（R-03）

版本检查点存的是**激活画布**的内容（`state.doc`），却按 `documentId`
（整个项目）归档。改造前恢复一律写进「恰好激活的那张」：在画布 B 上产生的
检查点，在画布 A 上按一下恢复，A 的内容和名字当场被 B 盖掉——而界面上没有
任何地方说过这一版来自 B。

裁决：检查点记 `canvasId` + `canvasName`，落点判据在
`web/src/lib/versionTarget.ts` 一处，四条分支：

| 分支 | 落点 | 是否要点头 |
|---|---|---|
| `same` | 当前画布 | 否（最常见的路不该多一次点击） |
| `other` | 切到原画布再写，当前画布不动 | 是（说清会切过去） |
| `missing` | 原画布已删 → 写进当前画布 | 是，**danger** |
| `unknown` | 旧检查点没有身份 → 写进当前画布 | 是，**danger** |

**缺席就是缺席**：旧检查点没有 `canvasId`，读到的地方不补默认值——补出来的
身份恰好总是「允许直接覆盖」。自动检查点的去重判据也加上画布身份：复制一张
画布之后两张内容逐字节相同，只比 `doc` 会把第二张画布的检查点判成重复而跳过。

## 6. `⌘S` 真的保存

改造前 `⌘S` 打开的是「保存为画布文件」对话框，而 `ShortcutHelp` 里写的也是
「保存为画布文件」——两边一致，但用户按 `⌘S` 想要的从来不是「另存一份」。

现在 `⌘S` = 保存当前文档（目标已知，直接写，**等到磁盘真的写完**才回话），
`⇧⌘S` = 另存为一份命名的画布文件。`⌘S` 在输入框和对话框里**也拦**——那才是
用户最想按它的时刻，不拦的话浏览器弹出「保存网页」，用户以为存了文档，存下来
的是一张 HTML。

## 7. 关闭保护：先读状态再冲刷

`beforeunload` 只在 `hasUnsavedWork()` 为真时拦。顺序很要紧：**先读状态再
冲刷**——反过来的话 `flushAutosave()` 把状态推成 `saving`，而 `saving` 属于
「有未落盘的工作」，于是一份干干净净的文档每次刷新都弹一次「确定离开吗」，
用户学会的是无脑点确定，那时候真该拦的那一次也拦不住了。

## 8. 排队中的写入属于哪个项目

一次写入属于**排队那一刻**的项目，不属于「socket 打开那一刻碰巧是哪个」。
`dropProject()` 是先冲刷再忘掉 pj，而冲刷排出去的那次 PUT 要过几个 await
才真的发出（§3b 的确认）——读全局的话它就落进了后端的默认项目，在原项目里
表现为「没保存」。所以 `pj` 跟着载荷一起排队
（`session.apiUrlFor` / `withProjectFor`）。

## 9. 不在本条范围内

- **autosave 仍在数据目录**（`LAYOUT_DIR/_autosave`）而不是项目内（R-07）。
  搬家会改变「项目拷到另一台电脑带不带工作副本」的语义，单独处置。
- **没有 index.json**：`/api/layouts` 仍靠 `glob` 现算。引入 index 就多一份
  可能与磁盘不一致的真相，得先说清它坏了怎么重建。
- **编辑历史面板的形态**：现有版本抽屉已经区分 undo 栈 / 检查点 / 恢复，
  但它的入口仍在文档菜单里。左上区域的独立入口留给 Prompt 08 的左栏改造，
  免得同一块区域两个 Session 各摆一次。
