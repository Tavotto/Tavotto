# ADR 0129：异常退出标记——引擎意外退出的检测 / 重启，与「上次没有正常退出」的下次启动提示

日期：2026-10-14 · 状态：**Proposed**（随 PR B 评审）
相关：[0118 发送问题反馈](0118-diagnostics-send-report.md)（本 ADR 论证自己**不违背**其「状态只在内存」的本意）、[0002 Tauri 桌面壳](0002-tauri-desktop-shell.md)、
[0108 稳定 origin](0108-desktop-stable-origin-and-backend-session-state.md)、[0105 远程实例窗口](0105-desktop-remote-instance-window.md)；
规则全文 `docs/rules/frontend/frontend-diagnostics.md`「退出相关入口」、`src-tauri/AGENTS.md`。

## 问题

1. 引擎（sidecar）在会话中死掉时，页面只会表现为一连串请求失败，准备卡还写着「连接断了，正在重连…」——**没有任何东西在重连**。用户没有办法自救，也不知道该找谁。
2. 壳自己崩溃 / 被杀 / 断电之后，下次启动一切如常，而那恰恰是最需要「要不要把诊断发给维护者」的时刻（崩溃时页面已不在，没人能点任何东西）。

## 决策

### 一、引擎意外退出：检测 + 一键重启（修复卡，不受发送开关控制）

- `sidecar.rs` 的 `Sidecar::poll_exit()`：对 child `try_wait`。`shutdown()` 会 `take` 掉 child，所以 take 之后 `poll_exit` 回 `None`——**None = 还在跑或已被正常关闭，不是崩溃**；已退出则回收子进程并回闭集类型 `signal`（被信号杀）/ `nonzero` / `zero`（退出码 0 但壳没让它退）。不带 status 文本与日志。
- 握手成功后挂**监视线程**（约 1 s 一次）。线程带代次：重启引擎、`shutdown` 取走句柄后旧线程自行退出。发现意外退出：写退出标记（见三）、`AppState` 记下、向**主窗口**发 `tavotto:engine-exited {kind}`；另提供 `current_engine_exit` 回读（事件可能早于前端监听）。
- 新命令 `restart_engine`：关旧句柄 → 重新 `Sidecar::start`（端口记忆，ADR 0108）→ **新 nonce** → 导航。导航与首次启动共用同一个 `boot_engine`，没有第二份；`AppState.port` 因此不再是 `OnceLock`（新引擎可能换端口，导航守卫读最新的）。引擎并未退出 / 正在重启时直接返回 `false`（幂等）。重启时不再重放首启交接（`--open`）。
- 前端通知轨一张修复卡：一句话「渲染服务意外退出了」+ 主按钮「重新启动」，折叠的一句「重启后可以发送问题反馈」。**不受 `diagSendStore.capability` 控制**（引擎没了谁都需要这颗按钮），也**不含发送入口**。引擎确认已退出时，准备卡的「连接断了，正在重连…」换成「渲染服务已停止」（`PrepContext.engineExited`）；网络暂断等其它原因的重连提示不变。
- 重启成功、页面换成新引擎的之后，`take_previous_exit` 会拿到 `engine_exited`（壳在退出时把它记进内存），于是出现三所述的「发送问题反馈」提示——这就是「先重启再发」。

### 二、三条新命令的权限

`restart_engine` / `take_previous_exit` / `current_engine_exit` 三处同步（`build.rs`、`capabilities/main.json`、`generate_handler` + `permissions/autogenerated`）。**远程实例窗口一条都没有**（ADR 0105：它的引擎不是壳拉起的）；命令体里也先核窗口 label 为 `main`。

### 三、退出标记 `session-state.json`

`app_config_dir()/session-state.json`，原子写（tmp + rename，与 `desktop-port` 同写法）。内容**只有**：

```json
{"v":1,"state":"running"|"clean","started_at":<unix 秒>,"app":"<版本>","engine_exit":"signal"|"nonzero"|"zero"}
```

（`engine_exit` 仅在引擎意外退出后出现，且**粘住直到下次启动被取走**：`clean` 也带着它。）不含项目、路径、脚本名、用户标识、错误文本。时序：`setup` 里（单实例插件之后，第二个实例到不了这里）读旧文件 → 纯函数判定 `previous`（无文件 / 损坏 / 版本未知 → 无提示并覆盖；`running` → `app_unclean`；`running` + 合法 `engine_exit` → `engine_exited`；`clean` + 合法 `engine_exit` → `engine_exited`，即引擎崩了、用户没重启就正常退出 App 也会提示；`clean` 无 `engine_exit` → 无提示）存进内存 → 立刻写 `running` → `RunEvent::Exit`（`shutdown_sidecar` 之后）写 `clean`。写入后 `clean` 即封口，监视线程迟到的写入不会把 `running` 写回去。

**绕过 `RunEvent::Exit` 的退出路径必须先写 `clean`**，否则每次升级后都会误报。逐一核过的清单：

| 路径 | 是否经 `RunEvent::Exit` | 处理 |
| --- | --- | --- |
| 关窗 / ⌘Q / 系统注销 | 是 | `Exit` 里写 clean |
| 前端「重启到新版本」（`relaunch()` → `process:allow-restart`，在非主线程调 `restart()`） | 是（Tauri 2.11 的 `restart()` 在非主线程会 `request_exit` 并走 `Exit`） | 同上 |
| Windows 更新器装包前 `std::process::exit(0)` | **否** | 所有 `UpdaterBuilder` 经 `updater_builder()` 取得，挂 `on_before_exit` → `mark_clean` |
| e2e 更新口 `process::exit(40/41/42)`、`handle.restart()` | **否** / 视线程 | `e2e_exit()` / `mark_clean_exit()` 先写 clean |
| 崩溃 / 被 kill / 断电 | 否 | 标记停在 `running`——这正是要被检出的情形 |

`main.rs` 的结构测试逐条钉住：生产代码里不许出现裸 `process::exit` / `.updater_builder()` / 额外的 `restart()`，`Exit` 里 clean 在 sidecar 收掉之后写。

### 四、下次启动提示

App 启动时 `diagSendStore.load()` **之后**才 `takePreviousExit()`；`capability === null` 时**不取**（取走即清空，白吞一次提示）。取到才登记一张通知轨卡：一句话「上次 Tavotto 没有正常退出」+ 主按钮「发送问题反馈」+ ×。点主按钮只 `diagSendStore.setOpen(true)`——**点之前不 prepare、不 start**。

## 为什么这不违背 ADR 0118「状态只在内存」

0118 禁的是：自动补发、跨启动的待发队列、记住用户的选择、记录用户活动。本标记逐条不是这些：

- **不自动补发**：标记只决定下次启动「要不要出现一张提示卡」；是否备包、是否发送，仍是用户在确认框里逐次决定；
- **没有待发队列**：不存任何待上传的东西（连「有一份包」都不存），备包在点开确认框时才现采；
- **不记用户活动**：内容是版本、启动时刻、`running`/`clean`、退出类型三值闭集；没有项目、路径、脚本名，也没有错误文本；
- **不上传**：文件只在本机，从不进诊断包的任何类别，也不进 telemetry；
- **一次性读取**：启动读一次、立刻覆盖成新一轮；`take_previous_exit` 取走即清空，页面重载不重复提示。

它是「进程是否走完了退出流程」这一个事实，不是用户数据。用户可以删掉这个文件（删了只是少一次提示）。

## 后果

- 每次启动多一次几十字节的原子写；退出多一次。写失败静默（只意味着少一次提示）。
- 开发态 / 无配置目录时标记为空操作。
- 监视线程的 1 s 轮询在引擎被杀后最多 1 s 才发现；期间的请求失败仍是普通网络错误。
- 引擎「挂住但没退出」不在本 ADR 范围（没有心跳）。
