## 结论先行

用户报的三个缺陷全部实锤，且根因比表面症状更深：（1）"直线掰不斜"不是交互不顺手，而是
`ShapeObject` 这个类型从数据模型层面就没有 `start/end` 端点字段，`resizeRect` 对竖直位移
无条件丢弃，纯属功能缺失，不是 bug；（2）"点箭头点不中/点图点成线"的根因是命中区精确等于对象
未旋转包围盒高度 `h`，而水平箭头/直线的 `h` 被钳到 0.01mm（≈0.038 屏幕像素，放大到 App 上限
800% 也只有 0.3 像素），用真实 Chromium 点击复现了 100% 点不中；（3）"复制的箭头会消失"实际是
`duplicateSelected()` 对 Immer 草稿对象调用 `structuredClone()`，**100% 抛 `DataCloneError`，
复制从未发生过**——不是"出现又消失"，是"从来没出现"，且这个 bug 对全部对象类型无差别必现，
只是用户恰好用箭头试出来的。三条根因互不相关，但都指向同一类问题：交互层的"应该能做"和数据
模型/实现之间出现了断层。

本轮额外主动审计发现 **17 条**问题，其中 **1 条 critical**（旋转对象缩放手柄全面错位，
与用户报的问题 2 同源但覆盖面更广：任意角度旋转 + 任意对象类型）、**4 条 high**（worker
卡死后无法被 kill 会留僵尸进程；拖拽中途 ⌘Z 留下撤不掉的残留位移；自动保存磁盘队列单槽变量
导致跨文档/跨标签页互相覆盖丢数据；窄框长英文单词画布强制换行但导出整词溢出边框）。
主动发现绝大多数经过第二人对抗验证（跑真实命令复核，部分用真实 Chromium 补测了原作者未验证的部分）。

**主审复核（在两轮 agent 之后另做的第三道抽查）的修正**：抽查了 5 条最具体的断言，

# Part 1　用户报告的三个缺陷

## 缺陷 1：直线标注没有端点手柄，竖直方向位移被无条件丢弃

**现象**：选中一条"直线"标注后看到的是贴着线的矩形外框和左右两个方块手柄；抓着手柄往上下拖，
线的角度纹丝不动（只会改变长度）；某些情况下拖一下手柄后线外面会凭空多出一个明显的矩形框。

**复现步骤**：
1. 画布左侧工具栏选"直线"标注工具（不是"箭头"工具）
2. 从左上往右下斜着拖一段（如 45°）
3. 松手后线是水平的，不是拖出的斜线
4. 选中该线，只能看到左右两个方块手柄
5. 抓右边手柄往下拖，线角度不变，只会变短/变长
6. 松手后线外面多出一圈可见的矩形选择框

**根因**：

`web/src/types/document.ts:151-164` 的 `ShapeObject` 根本没有 `start`/`end` 字段——只有
`ArrowObject`（document.ts:128-140）才有：

```ts
export interface ArrowObject extends ObjectBase {
  type: 'arrow'
  start: { rx: number; ry: number }
  end: { rx: number; ry: number }
  ...
}

export interface ShapeObject extends ObjectBase {
  type: 'shape'
  shape: ShapeKind
  strokePt: number
  color: string
  fill: string | null
  cornerRadius?: number
  sides?: number
  fillOpacity?: number
  dash?: DashStyle
  // 没有 start/end
}
```

`ShapeView.tsx:64-73` 把 `shape.kind==='line'` 永远画成局部坐标系里 `(0,h/2)→(w,h/2)` 的
水平线，方向完全不受 w/h 影响，唯一能让它变斜的是 `rotationDeg`（只能在
`TransformSection.tsx:86-106` 里输入数字，15° 步进，无拖拽入口）。

`OverlaySvg.tsx:45-50` 的 `dirsFor()` 实测确认：

```ts
function dirsFor(obj: CanvasObject): ResizeDir[] {
  if (obj.type === 'text') return ['w', 'e']
  if (obj.type === 'shape' && obj.shape === 'line') return ['w', 'e']  // 侧边缩放柄
  if (obj.type === 'arrow') return []   // 箭头走端点手柄，不走缩放柄
  return ALL_DIRS
}
```

`OverlaySvg.tsx:216` 只对 `type==='arrow'` 渲染 `ArrowEndpoints`（端点圆圈手柄），条件写死：

```ts
{single?.type === 'arrow' && !single.locked && <ArrowEndpoints obj={single} t={t} />}
```

shape-line 没有被这个条件覆盖，只能走 `dirsFor` 给的 `['w','e']` 侧边缩放柄。用 `w`/`e` 手柄拖动
走 `startResizeDrag → resizeRect`（`geometry.ts:195-230`），该函数对 `dir='w'/'e'` 只吃
east/west 分支：`h = orig.h + (south?dy:north?-dy:0)` 在 south/north 均为 false 时恒等于
`orig.h`——竖直方向的鼠标位移被直接丢弃，不管往上拖还是往下拖，线永远还是水平线。

更隐蔽的是 `geometry.ts:212` `h = Math.max(minH, h)` 是**无条件执行**的，`minH` 默认是 2；
直线创建时 `h` 恒为 0.01mm（`interactions.ts:485`，硬编码，不看拖拽产生的真实高度）。用户
只要拖一下这两个手柄中的任意一个，`h` 就会从几乎不可见的 0.01mm 被强行拉到 2mm——原本贴着线
看不出来的选择框，交互后突然变成一个 2mm 高、把线整个包起来的"外框"，与线本身的真实外观
（依旧水平）完全对不上，正是用户描述的现象。

**修复方案**：

1. **数据模型**：给 `ShapeObject`（document.ts:151-164）新增可选字段
   `start?/end?: {rx:number; ry:number}`，仅 `shape==='line'` 时使用其它 shape 忽略；
   兼容旧文档时缺失按 `(0,0.5)→(1,0.5)` 兜底。不需要升 schema 版本（ObjectBase 允许新增可选字段）。

2. **渲染**：`ShapeView.tsx:64-73` 的 `shape==='line'` 分支改成用真实端点算线段：
   ```tsx
   {obj.shape === 'line' && (() => {
     const s = obj.start ?? { rx: 0, ry: 0.5 }
     const e = obj.end ?? { rx: 1, ry: 0.5 }
     return <line x1={s.rx*w} y1={s.ry*h} x2={e.rx*w} y2={e.ry*h} strokeLinecap="round" {...stroke} />
   })()}
   ```

3. **创建**：`interactions.ts:477-491` 的 `startDraw` 对 `tool==='line'` 复用 arrow 分支
   （interactions.ts:453-476）同款算法，把 `sy/ey` 的真实竖直分量算进 `start/end.ry`，
   不再无条件塞 `h:0.01`。

4. **手柄**：`OverlaySvg.tsx:216` 的条件扩展为
   `single?.type === 'arrow' || (single?.type==='shape' && single.shape==='line')`；
   `dirsFor()` 里 shape-line 分支改成返回 `[]`（不再给 w/e 手柄）；
   `ArrowEndpoints`/`startEndpointDrag`（OverlaySvg.tsx:282-312、interactions.ts:265-338）
   泛化成同时接受 `ArrowObject` 和 `ShapeObject`（此时两者 start/end 字段结构一致）。

5. **后端**：`src/magplot/pdfbackend/pymupdf_backend.py` 的 `_draw_shape` 中 `kind==='line'`
   分支（"line 为包围盒水平中线"那句注释附近）必须同步改成读 `start/end`，与 `_draw_arrow`
   的 `ax,ay/bx,by` 算法一致——否则前端能画斜线、导出又变回水平线，破坏"前后端几何公式同源"约定。

**风险与回归测试**：

这个改动会破坏 CLAUDE.md "前后端几何公式同源" 约定的**形式**（shapeGeometry.ts ↔
pymupdf_backend.py 同名注释对），但精神上是延续——必须同步改 `_draw_shape` 的 line 分支，
且要在 `tests/test_compose_text.py` 或专门的形状测试里补一条 `get_drawings()` 几何断言，
否则会重现 CLAUDE.md 强调过的"改一边不同步另一边"的老坑。旧文档里已存在的 shape-line（没有
start/end 字段）要给出兜底默认值，否则历史图库里的直线会"消失"或变成一个点。不涉及 schema
版本号变更。

**工作量**：M　**置信度**：high

**验证方式**：临时用例 `web/src/__audit__/endpoints.test.ts`（已删除），实跑
`cd web && NODE_OPTIONS=--no-experimental-webstorage pnpm exec vitest run src/__audit__/endpoints.test.ts`，
6/6 通过；本次复核额外用 `grep`/`sed -n` 直接读取 `document.ts:145-170`、
`OverlaySvg.tsx:40-55`、`OverlaySvg.tsx:210-220`，确认 `ShapeObject` 无 start/end、
`dirsFor` 对 shape-line 返回 `['w','e']`、`ArrowEndpoints` 门槛写死 `type==='arrow'`——
与素材描述完全一致。

**盲区**：手柄错位/缺失在真实浏览器指针事件下的可操作性体验（用户能否勉强蒙对方向）未用
agent-browser 实测；rect/ellipse/triangle 等其它 shape 类型是否有独立于本条的问题未逐一验证
（理论上不受影响，因为本条只涉及 line 这一种 shape kind）。

## 缺陷 2：旋转对象的选择框/手柄与真实渲染脱节 + 命中区过小导致点不中/误选

用户报的第二个现象实际由两个独立根因叠加，审计中分别坐实，此处合并陈述（详见 Part 2 里
"旋转对象缩放手柄错位"的 critical 级别姊妹发现——那条覆盖面更广，任意角度、任意对象类型）。

### 2a. 命中区精确等于对象未旋转包围盒高度 h，水平箭头/直线的 h 恒为 0.01mm

**现象**：画一条接近水平（或垂直）的箭头/直线后，鼠标怎么点都点不中它，最终点到了它下面的
面板；反过来，画一条斜箭头后，在包围盒里离线段本身很远的空白处点击，却选中了箭头——两种体验
交替出现。

**复现步骤**：
1. 工具栏选"箭头"，从左向右水平拖出一条箭头（或按住 Shift 拖拽让它 15° 吸附到水平）
2. 用鼠标精确瞄准箭头视觉上的那条线点击——绝大多数情况下什么都选不中，或选中了下面的面板
3. 反过来画一条斜箭头，点击矩形包围盒内明显偏离线段的空白角落——箭头被选中
4. 对 shape 工具里的"直线"重复步骤 1-2，现象相同

**根因**：

`ObjectView.tsx:87-98` 每个对象只有一个 `<div data-object-id>` 承担全部命中职责：
`style.width/height = mmToWorld(obj.w)/mmToWorld(obj.h)`，`pointerEvents` 只在
`obj.locked` 时才置 `'none'`，其余情况恒为默认 `auto`——命中区严格等于未旋转包围盒。
`ArrowView.tsx:65`/`ShapeView.tsx:37` 内部真正画线的 `<svg>` 整体 `pointer-events-none`，
可见的墨迹压根不参与命中判定。

`obj.h` 在两条路径上都被钳到 0.01mm 下限：`interactions.ts:461-462`（拖拽画箭头）、
`interactions.ts:485`（画 line 形状，恒为 0.01mm）、`interactions.ts:319-320`（拖端点收尾）。
Shift 吸附水平（interactions.ts:288-296，画"指向峰值"这类示意箭头的常见操作）恰恰是触发
`h→0.01mm` 的典型场景。

用真实 Chromium（Playwright）逐字复刻 `ObjectView`+`ArrowView` 的 CSS/DOM 结构实测：

```
DEBUG GEOMETRY: { arrowRect: { top:150, bottom:150.03125, height:0.03125 }, svgPointerEvents:'none' }
click results by y: {"149":"panel","150":"arrow","151":"panel","150.02":"arrow","150.04":"panel"}
```

只有落在 `[150, 150.03125]` 这条比 1 个物理像素还窄得多的亚像素窗口内的点击才会命中箭头；
真实鼠标点击在 1x 屏幕下只能落在整数 CSS px 上，`y=149/151`（视觉描边范围内最自然的落点）
全部落到 panel 上。

反方向：斜箭头因为命中区=完整矩形包围盒（非几何命中），包围盒内任何一点（哪怕离线段几毫米远）
都会命中，抢走本该落在下层对象上的点击。层级完全由 DOM 顺序决定（`CanvasStage.tsx:203-206`
+ `store/actions.ts:241-266` 的 `changeZOrder` 直接操作数组，无 z-index），箭头默认排在
数组末尾也就是最上层，放大了误选概率。

**修复方案**（方案 A，推荐，改 3 个文件）：

`ArrowView.tsx` 在真实描边线旁加一条透明命中线：

```tsx
const HIT_PX = 8
const hitWidth = Math.max(sw, HIT_PX / zoom, headHalf * 2)
<line
  x1={a.x - ux*extStart} y1={a.y - uy*extStart}
  x2={b.x + ux*extEnd} y2={b.y + uy*extEnd}
  stroke="transparent" strokeWidth={hitWidth} strokeLinecap="round"
  style={{ pointerEvents: obj.locked ? 'none' : 'stroke' }}
/>
```

`ShapeView.tsx` 的 `shape==='line'` 分支同理加一条透明命中线。`ObjectView.tsx` 让外层 div
对这两类对象让位：

```tsx
const isThinLinear = obj.type === 'arrow' || (obj.type === 'shape' && obj.shape === 'line')
style={{ pointerEvents: obj.locked || isThinLinear ? 'none' : undefined, ... }}
```

这样斜箭头"死区误伤面板"的问题也一并解决：外层矩形不再兜底命中，命中完全交给沿线段走的
stroke，包围盒里离线段远的空白处不再拦截点击。

**风险与回归测试**：

不触碰任何几何计算/PDF 导出路径，只新增 `stroke='transparent'` 的 `<line>`，原有可见描边
不改，前后端几何同源约定不受影响。必须让新命中线的 `pointerEvents` 跟随 `obj.locked`
（上面代码已处理），否则锁定对象会重新变得可点选。已用 Playwright 验证祖先 div
`pointer-events:none` + 后代 SVG `pointer-events:'stroke'` 时，`onPointerDown`/
`onPointerEnter`/`onPointerLeave` 仍会通过事件冒泡正常触发在祖先 div 上（事件序列
`["wrap:enter","stroke:move","wrap:move","stroke:down","wrap:down","wrap:leave"]` 完整
触发）——`ObjectView.tsx:23-90` 的选择/右键/双击/hover 逻辑不需要改动，但 `onContextMenu`/
`onDoubleClick` 未逐一在真实浏览器里点击复测，建议合入前人工过一遍。8px 命中带下限参考
`OverlaySvg.tsx:133-141` 参考线拖拽已有的同款手法（`strokeWidth={7}`），换算到文档坐标是
2.12mm（100%缩放）到 8.47mm（25%缩放），不会大到吞掉相邻标注。

**工作量**：M　**置信度**：high

**验证方式**：临时文件 `web/src/__audit__/hittest.test.ts`（已删）跑
`pnpm exec vitest run --reporter=verbose` 量化 mmToWorld/bbox 面积比；另在
`scratchpad/hittest/` 用 Playwright v1.62.1 起真实 Chromium 复现点击结果矩阵（命令与输出
见上）。本次复核确认 `ObjectView.tsx:87-98`、`interactions.ts:461-462/485` 内容与素材一致
（未逐行重跑 Playwright，采信一手证据）。

### 2b. 旋转后手柄/端点全面脱离可视图形（详见 Part 2 critical 条目）

Part 2 中的"旋转的文字/箭头/形状：缩放手柄画错位置"是同一现象的更完整根因：`OverlaySvg.tsx`
的选择框、8 个缩放手柄、箭头端点手柄全部只用未旋转 `x/y/w/h` 换算屏幕坐标，从不读
`rotationDeg`；`interactions.ts` 的 resize 反算同样不含旋转。旋转 90° 时端点手柄与真实视觉
相距 28.28mm（约半个对角线），任何缩放级别下都清晰可见错位。详细修复方案见 Part 2。

**用户体感的完整解释链**：ArrowObject 本身其实已经有端点拖拽能力（且这段代码是已提交状态，

## 缺陷 3：复制功能（⌘D / 右键"复制" / 检查器"复制"）100% 崩溃，从未真正复制过

**现象**：选中一个对象（箭头/文字/形状/面板都一样）后按 ⌘D，或右键菜单点"复制"，或在右侧
检查器菜单点"复制"：画布上不会真的多出一个对象；如果走右键菜单，菜单本身会卡在屏幕上不消失，
全程没有任何错误提示。用户描述的"新出现的箭头会自动消失"，更准确的解释是"点了复制、菜单卡住、
什么反应都没有"——这个函数是 100% 静默崩溃，从未真正把副本写进过文档状态，浏览器里根本不会
有第二个箭头闪现一下再没掉，它压根就没出现过。

**复现步骤**：
1. 画布上放一个任意对象，选中它
2. 按 ⌘D（Windows 上 Ctrl+D），或右键该对象点"复制"，或检查器菜单点"复制"
3. 观察：画布上对象数量不变；DevTools Console 有一条未捕获的
   `DataCloneError: #<Object> could not be cloned.`，堆栈指向 `src/store/actions.ts:223`
4. 若走右键菜单，菜单会卡在屏幕上不消失

**根因**：

`web/src/store/actions.ts:215-237`（本次复核实测原文，与素材一致）：

```ts
export function duplicateSelected() {
  const ids = useSelectionStore.getState().ids
  if (!ids.length) return
  const clones: string[] = []
  commit('复制对象', (d) => {
    const regroup = new Map<string, string>()
    for (const o of d.objects.filter((x) => ids.includes(x.id))) {
      const copy = structuredClone(o)   // <-- d 是 Immer 草稿，o 是草稿 Proxy
      copy.id = newId(o.type[0])
      ...
      d.objects.push(copy)
    }
  })
  select(clones)
}
```

`d` 是 `produceWithPatches` 传入的草稿（`documentStore.ts:163`），Immer 默认用 ES6 Proxy
实现草稿——`d.objects.filter()` 内部逐个访问元素都会经过 Proxy 的 get trap，返回的是**该
元素的草稿 Proxy**，不是原始 plain object。根据 HTML 结构化克隆算法规范，任何带
`[[ProxyHandler]]` 内部槽的对象传给 `structuredClone` 都会被直接拒绝、抛
`DataCloneError`——这是 V8/浏览器引擎级别的行为，不是 jsdom 测试环境的特例（已用纯 Node
对 immer@11.1.16 验证同样行为）。异常在 for 循环第一次迭代就抛出（在 `d.objects.push(copy)`
之前），Immer 的 `produce()` 捕获到 recipe 抛错后直接向外重新抛出，`commit()` 里
`set({doc:next,...})` 永远执行不到——文档状态、Zustand store、撤销历史全部原封不动。

这不是箭头独有的问题：同一份 recipe 换成 `type:'text'` 的对象一样崩（已用 Node 直接跑
immer 复现）。三个 UI 入口（⌘D 键盘快捷键 `useKeyboard.ts:86-90`、右键快捷菜单"复制"
`QuickEdit.tsx:496-510`、检查器菜单"复制" `Inspector.tsx:341`）全部指向同一个
`duplicateSelected()`，三处全部失效。

`git blame -L 215,237 web/src/store/actions.ts` 显示这段代码从首次提交起从未改动过，
`git diff HEAD -- web/src/store/actions.ts` 为空——当前代码库既有状态下的缺陷，与本轮会话
未提交改动无关。

**修复方案**：

把"对象克隆"从 Immer recipe 内部挪到外面，对已经 finalize 过的 plain object（不是草稿）
做 `structuredClone`，克隆好的 plain 对象数组整体 push 进 commit——这正是同文件里
`materializePaste`（`web/src/lib/clipboard.ts:226`）和 `duplicateCanvas`
（`documentStore.ts:365`）已经在用、且已验证可用的模式：

```ts
export function duplicateSelected() {
  const ids = useSelectionStore.getState().ids
  if (!ids.length) return
  // 必须在 commit 的 recipe 外面克隆：recipe 内 d.objects.filter(...) 拿到的是
  // Immer 草稿 Proxy，structuredClone 对任何 Proxy 都会抛 DataCloneError
  const regroup = new Map<string, string>()
  const clones: CanvasObject[] = doc()
    .objects.filter((o) => ids.includes(o.id))
    .map((o) => {
      const copy = structuredClone(o)
      copy.id = newId(o.type[0])
      copy.x += 4
      copy.y += 4
      if (copy.groupId) {
        const next = regroup.get(copy.groupId) ?? newId('g')
        regroup.set(copy.groupId, next)
        copy.groupId = next
      }
      return copy
    })
  if (!clones.length) return
  commit('复制对象', (d) => { d.objects.push(...clones) })
  select(clones.map((c) => c.id))
}
```

（`doc()` 是文件顶部已有的 `const doc = () => useDocumentStore.getState().doc` helper；
`CanvasObject` 类型已 import，无需新增依赖。）

配套：`QuickEdit.tsx:496-499` 的 `run()` 包装器加 `try/finally`（详见 Part 2 medium 条目），
避免下一次类似异常再次让菜单卡死不提示。

**风险与回归测试**：

风险低：只是把克隆时机从"recipe 内部"挪到"recipe 外部"，不改变对外行为契约——依然是"一次
用户操作 = 一条 commit 历史"，依然保留 `select(clones)` 让选区跟随新对象，group 重新分组的
逻辑原样保留、只是数据源从草稿换成 plain 对象。`doc().objects` 在 map 过程中读的是调用
`duplicateSelected()` 那一刻的快照，与 `materializePaste` 现有实现面临的是同一种可接受语义。

建议补的回归测试：


## High

### worker 卡死后无法被 kill，退出时留下僵尸进程

**现象**：脚本写了死循环或极慢计算，前端渲染请求转圈到看门狗超时后提示"已断开请求"，但该
面板永远渲染不出来，重试也卡住，唯一解法是重启整个应用。用户直接退出应用（或后端受控关闭）时，
卡死的渲染子进程根本不会被杀掉，作为孤儿进程持续跑死循环占 CPU。

**根因**：`EngineWorker.request()`（`pool.py:369`）在 `with self.lock:` 临界区里对子进程做
无超时阻塞读 `self.proc.stdout.readline()`（`pool.py:376`）——脚本一旦卡住，这个 readline
永远不返回，线程和锁一起被永久占住。`shutdown()`（`pool.py:428`）走的是同一个
`self.request()`，也要抢同一把 `self.lock`，于是 `shutdown()` 同样卡死在获取锁那一步，
**永远走不到 finally 里的 `self.proc.kill()`**（`pool.py:436`）。LRU 淘汰和
`/api/shutdown`/进程退出时的 `shutdown_all(wait=True)`（`pool.py:482`，
`t.join(timeout=10)`）对这类 worker 全部失效：join 超时只是不再等，不会真的杀掉子进程。

**修复方案**：只在 `shutdown_all(wait=True)`（pool.py:482）这个"进程即将退出，必须干净
收尾"的路径上加硬性兜底——线程 join 超时后直接 kill 子进程：

```python
def shutdown_all(figures_dir=None, wait=False):
    with _lock:
        ...
    threads = [threading.Thread(target=w.shutdown, daemon=True) for w in victims]
    for t in threads:
        t.start()
    if wait:
        for t, w in zip(threads, victims):
            t.join(timeout=10)
            if t.is_alive():
                LOG.warning("worker 关停超时（可能卡在死循环脚本里），强制 kill: %s", w.script_name)
                try:
                    w.proc.kill()
                except OSError:
                    pass
```

子进程被 kill 后，原本卡在 `readline()` 上的 `request()` 线程会因读到 EOF 而返回、抛
`WorkerError` 并释放锁。这只解决"进程退出不留僵尸"；"同一个卡死 worker 之后永远不可用"
这个子问题需要给 `request()` 本身加超时（后台读线程+队列实现可超时的 readline），改动面
更大，建议后续单独排期。

**风险与回归**：只加在 `wait=True` 分支（仅 `/api/shutdown` 与 `reset_projects(wait=True)`
会用到），不影响 LRU 淘汰路径，正常运行时合法 heavy 脚本冷启动（几分钟）不会被误杀。

**独立验证者补充发现**（未改变本条裁决，但提醒后续优先级）：`pool.py:445-448` 的 `get()`
在 entry 变化且旧 worker 仍 `alive()`（挂住）时，会在持有模块级 `_lock` 的情况下同步调用
`w.shutdown()`——这会让**整个引擎池（所有项目、所有脚本）永久锁死**，比原描述的影响面更大，
触发条件更窄（脚本挂住 + entry 恰好被改），但建议后续处理 request() 超时那一项时一并覆盖。

**严重度**：high　**工作量**：S　**置信度**：high

### 拖动中途按 ⌘Z：留下一段永远撤不回去、也进不了历史的残留位移

**现象**：拖着一个对象时手滑按了 ⌘Z，对象啪地弹回起点，但鼠标还按着、还在动，图形又跟着继续

调用里 `get().past.at(-1)` 取到的正好是刚提交的这条，立刻把它撤销——"结算+撤销"在一次 ⌘Z

pointermove/pointerup 监听器完全不知情，仍持有对 `store.txnUpdate` 的引用；此后每次
pointermove 都会走 `txnUpdate` 里"没有 txn 就直接 `set({doc:next})`"的分支——这个分支彻底
绕过 `pushHistory`，是静默写入。松手时 `endTxn()` 因为 txn 早已是 null，直接空转。

`get().txn` 非空时拒绝执行或先 `endTxn({discard:true})` 丢弃当前拖动，但会改变"松手前折叠
成一条历史"的既有语义，改动面更大，不建议顺手改。

**风险与回归**：只在拖动进行中屏蔽 ⌘Z，需要确认不会误伤"输入框里正常撤销文字输入"的场景——

两者互不冲突，风险很低；不涉及后端契约或几何同源约定。

### 自动保存的磁盘写入队列是全局单槽变量，不同文档背靠背排队写盘时会互相覆盖丢弃

**现象**：在还没打完字、上一次自动保存的网络请求还没返回时，就切换到另一个文档，刚才那份
文档最后一次修改会悄无声息地丢失——磁盘上和浏览器本机备份里都没有，且界面无任何报错或提示。

**根因**：`documentStore.ts:591-592` 把"正在等待落盘的下一份文档"存成一个全局单槽变量
`let diskQueue: [string, ProjectDocument] | null = null`，而不是按 documentId 分开排队。
`scheduleDiskWrite()`（594-620行）在 `diskBusy` 为 true 时，无条件用 `diskQueue = [id, pd]`
覆盖掉这个槽位——不检查槽位里原本排的是不是同一个 id。`switchDocument()`（433-459行）切
文档时连续调用两次 `flushAutosave()`：先为旧文档落一次（435行），状态切完后又立刻为新文档
落一次（457行）。如果旧文档自己有一次 PUT 请求还在网络在途中（`diskBusy=true`），旧文档
这次 flush 会被排进 `diskQueue`；但紧接着新文档的 flush 一到，又把 `diskQueue` 整个换成
新文档的——旧文档刚排队等待落盘的那份内容永久消失。更糟的是：在途请求成功后，`.then()`
（602-607行）只认"这个 id 的写盘曾经成功过一次"就删掉它在 localStorage 的兜底副本，本机
兜底副本也被清空，双重丢失。

**修复方案**：把 `diskQueue` 从单槽变量改成按 id 排队的 Map：

```ts
let diskBusy = false
const diskQueue = new Map<string, ProjectDocument>()

function scheduleDiskWrite(id: string, pd: ProjectDocument): void {
  if (diskBusy) {
    diskQueue.set(id, pd) // 同一个 id 天然合并成最新一份，不同 id 不再互相覆盖
    return
  }
  diskBusy = true
  void putAutosave(id, pd)
    .then(() => { try { localStorage.removeItem(slotKey(id)) } catch {} })
    .catch(() => {
      window.dispatchEvent(new CustomEvent('magplot:autosave-error', { detail: { id } }))
    })
    .finally(() => {
      diskBusy = false
      const next = diskQueue.entries().next()
      if (!next.done) {
        const [qid, qpd] = next.value
        diskQueue.delete(qid)
        scheduleDiskWrite(qid, qpd)
      }
    })
}
```

**风险与回归**：改动完全局限在 `documentStore.ts` 里两个未导出的模块级变量与一个函数体内，
不改对外签名，不涉及后端/PDF 后端/进程边界约定，也不改 schema。如果同时有很多不同文档排队
（正常使用几乎不会发生），会依次串行 PUT，比现在"后来者直接顶替"略慢，但正确性优先。

**严重度**：high　**工作量**：S　**置信度**：high

**验证方式**：临时文件 `web/src/__audit__/docstate.test.ts`（已删）用可控延迟的 fetch mock
复现两个不同文档背靠背排队写盘的场景，实跑
`cd web && NODE_OPTIONS=--no-experimental-webstorage pnpm exec vitest run src/__audit__/docstate.test.ts`
→ 4/4 通过；断言"带 Y 的那次 docA 写盘从未发生"（`idsWithY === 0`）且本机兜底副本已被清空。
**未收到独立验证者裁决**，单独标注。

### 文字换行算法前后端不同源：窄框长英文单词画布强制断词，导出 PDF 却整词溢出边框

**现象**：在较窄的文字框里输入一长串不含空格的英文（长化学式、DOI、URL、驼峰变量名等），
画布上文字自动换行、老实待在框内，导出成 PDF 后这段文字却直接横向冲出文本框、可能压到旁边
内容——用户拿着"画布上看着好好的"文件去投论文，排版是错的。

**根因**：`pymupdf_backend.py:278-312` 的 `_draw_text` 自己实现了一套独立换行算法：CJK
按字符切换行单元、拉丁文按空格分词切换行单元，贪心装行循环只在"已有内容的行装不下新 unit"
时才换行；如果单独一个 unit（一个英文单词）本身宽度就超过 `box_w`，代码没有任何再拆分它的
路径，超宽 unit 会原样占满一整行、超出右边界。`web/src/canvas/TextView.tsx:114-115` 完全
交给浏览器原生换行，显式设置 `whiteSpace:'pre-wrap', wordBreak:'break-word'`
（`overflow-wrap:break-word`，单词放不下容器时允许词内断开）。两边的换行策略不是同一套实现，
只是短单词场景下碰巧结果一致，长单词场景分道扬镳。

真实导出量出的越界：`box_right_pt=85.0 max_x1=236.3 overflow=151.3pt`（约 53mm，超过框宽
本身两倍多）。

**修复方案**：在 `_draw_text`（233 行起）贪心装行循环里加一个"单个 unit 本身超宽"的兜底
分支，把这类 unit 退化为逐字符断行（复用已有的 CJK 逐字策略）：

```python
def _force_break_chars(u: list[tuple[str, str]]) -> list[list[tuple[str, str]]]:
    out: list[list[tuple[str, str]]] = []
    for seg_text, sc in u:
        for ch in seg_text:
            out.append([(ch, sc)])
    return out

line: list[tuple[str, str]] = []
for u in units:
    if not line and _unit_w(_rstrip(u)) > box_w and sum(len(t) for t, _ in u) > 1:
        for cu in _force_break_chars(u):
            cand = line + cu
            if line and _unit_w(_rstrip(cand)) > box_w:
                lines.append(_rstrip(line)); line = list(cu)
            else:
                line = cand
        continue
    cand = line + u
    if line and _unit_w(_rstrip(cand)) > box_w:
        lines.append(_rstrip(line)); line = list(u)
    else:
        line = cand
lines.append(_rstrip(line))
```

关键是"只在 `not line`（当前行是空的，即这个词自己独占一行都放不下）时才退化为逐字符"，
正常短单词场景完全不受影响，不会连累 `test_compose_text.py` 等既有几何看护用例。

**风险与回归**：`_draw_text` 是几何看护测试重点覆盖的函数，改动前必须跑一遍
`test_compose_text.py`、`test_compose_annotations.py` 确认无回归；前端 `word-break` 的
具体断点位置理论上仍可能与后端逐字符测宽度算出来的断点有细微出入（浏览器用实际字体度量，
后端用 pymupdf 基础字体度量）——本修复解决的是"整词溢出"这个量级的问题，不保证逐字符断点
像素级完全一致。

**严重度**：high　**工作量**：M　**置信度**：high

**验证方式**：独立验证者不满足于只信 CSS 规范文字，用仓库已装的 `@playwright/test` 起真实
Chromium 渲染同等窄度（56.7px）+ 同字号(12px)+ 同样 `white-space:pre-wrap;word-break:
break-word` 的 `<div>` 塞入同一串 26 字符，`getBoundingClientRect()` 测得文字实际宽度
56.02px ≤ 容器 56.69px——真实浏览器里确实不溢出，与后端 151.3pt 溢出形成实锤的不同源。
命令：`.venv/bin/python -m pytest tests/test_audit_export-v.py -q -s` →
`box_right_pt=85.0 max_x1=236.3 overflow=151.3pt`，与原始报告数字逐位吻合。

### render.started/failed/done 三个 SSE 事件不带 pj，跨项目污染渲染状态

**现象**：同时开着两个不同论文项目的标签页，若两边恰好有同名的面板文件（示例里到处都是的
"Fig1.pdf"），A 标签页触发渲染会让 B 标签页里同名但完全不相关的面板莫名其妙显示"正在构建…"
且不会自动清除。

**根因**：CLAUDE.md 明确写"SSE 事件带 pj，前端只处理属于本标签页项目的那些"。
`panel.file_changed`、`registry.changed` 确实都带了 `pj`。但 `api_engine_render()`
（`app.py:1214-1236`）里三处 `sse_publish` 调用——`render.started`（1225-1226）、
`render.failed`（1232）、`render.done`（1236）——payload 里都**没有 `pj` 字段**（本次复核
用 `grep -n 'sse_publish("render\.'` 确认行号 1225/1232/1236 逐字一致）。前端过滤逻辑
`if ('pj' in ev && ev.pj && mine && ev.pj !== mine) return`（`useServerEvents.ts:29`）
对没有 `pj` 键的事件直接判定为"不过滤"，三类事件被所有标签页无条件处理，`useRenderStore
.byFile` 是按 `fileId` 索引的全局单例，不区分项目，两个项目里同名的 fileId 写进同一个 slot。

**修复方案**：在三处 `sse_publish` 调用里补上 `pj`：

```python
pj = current_ctx().id
sse_publish("render.started", {"id": rel_id, "cost": info.get("cost", ""), "cold": cold, "pj": pj})
...
sse_publish("render.failed", {"id": rel_id, "error": str(exc), "pj": pj})
...
sse_publish("render.done", {"id": rel_id, "rev": worker.rev, "pj": pj})
```

`_engine_worker`/`require_project` 已保证 `current_ctx()` 非空，可安全取 `.id`。

**风险与回归**：纯加字段，前端过滤逻辑已经按 `'pj' in ev` 正确处理带 pj 的事件，不需要改
前端代码，不改变其它语义，风险极低。

**严重度**：high　**工作量**：S　**置信度**：high

**验证方式**：独立验证者用真实 Flask test_client 发起 `POST /api/engine/render`（打桩
`Registry.for_stem` 与 `engine_pool.get` 返回 FakeWorker，spy 包裹 `sse_publish` 记录
实际 payload），200 成功后捕获到的 `render.started`/`render.done` 两个 dict 里均无 `pj`
键。本次复核 `grep -n 'sse_publish("render\.' src/magplot/app.py` 输出行号
1225/1232/1236，与对照组（`registry.changed` 在 1149、1173 带 pj）核对一致。
