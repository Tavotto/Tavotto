# Journal facts API v2

This is a separate **source-fact** protocol, not a publication-profile override. It preserves several statements about the same subject, their units, strength, conditions, stages, origins and sources. The Python and MCP v2 clients read source facts; there is no v2 preflight evaluator or desktop selection UI in this change. A client that cannot interpret a condition must report the fact as not evaluated; it must not drop that condition and apply the value globally. A font example is not an exhaustive allowlist. A recommendation or preference is not a mandatory constraint. A permitted value is an allowed option, not evidence that unlisted values are forbidden. Publication still requires independent source and semantic review; the structural validator does not perform it.

## Routes and storage

`DATA/v2/index.signed.json`, `DATA/v2/r<rev>/journals/<id>.json` and `DATA/v2/snapshots/<sha256>.webp` back `/v2/journal-catalog/index.signed.json`, `/device`, `/journals/<id>?rev=<rev>` and `/snapshots/<sha256>.webp`. Devices and reads use the existing v1 database and token/IP limits, so the same token and journal ID count once across both protocols. Requests for one version do not read the other version's files. A malformed, mismatched or unverified v2 journal returns 503 `catalog_invalid` without recording a read. A v2 snapshot must exist and its bytes must match its content-addressed name; a mismatch returns 503 rather than an immutable response. Other errors and cache headers match v1.

The v2 index is signed with the established Ed25519 envelope: `{alg, key_id, payload, sig}` where `payload` is base64 of the raw UTF-8 index and `sig` signs exactly those decoded bytes. Index contents have `schema: 2`, `kind: "tavotto-journal-facts-index"`, `catalog_rev`, `issued`, `publishers`, and `journals`. Publisher entries carry `{label}`; journal entries carry `{label, publisher, issn?, eissn?, aliases?, bundle:{sha256,bytes}}`. `tavotto.engine.journalfacts_contract.validate_index` (re-exported by `services.journal_catalog.facts`) checks structure but **does not verify the signature**. `ValidatedIndex` snapshots a checked index so many bundle checks are linear in the combined bundle size; `validate_bundle` checks each bundle's hash, size, identity and verified facts. The caller must first verify the signature against a trusted key and enforce a version-specific rollback floor. The service itself returns the index bytes; clients must verify the envelope and bundle hash before use.

## Bundle

A bundle is `{schema:2, journal_id, journal:{label,publisher_id,issn?,eissn?}, sources, facts, coverage?}`. Sources are keyed by source ID with `url` (HTTPS without fragment or credentials), `kind` (`html` or `pdf`), `retrieved` (real ISO date), and optional PDF `page` and `archive_url`. Facts are a list; every item has:

- `id`, `subject`, `relation`, `value`, `strength`, `stage`, `source`, `quote`, `origin`, `review`.
- Optional `context:[{source,quote}]` carries verbatim, separately located section headings or introductory wording that qualifies a fact. Every context source must be included in `sources` and independently verified; do not concatenate nonadjacent text into one quotation. The publisher must bind the context excerpts and their source-text hashes to review evidence.
- Optional `unit` for numeric relations, `conditions` (a conjunction of named string/boolean equalities or `{relation,value,unit?}` predicates), and `condition_text` for a qualification that cannot be safely normalized. Both kinds of condition remain part of the statement. All named conditions are ANDed; alternatives are represented as separate facts or by `in` predicates. An absent or empty `conditions` object imposes no named condition, but does not erase `condition_text`, stage, strength, origin, or source context. If a consumer cannot determine a condition, applicability is unknown: the condition must not be omitted or treated as true. Predicates are stored facts, not an automatic preflight check. `anchor`, `mark`, `derivation`, and `snapshot:{file,width,height}` are optional provenance; `mark` must occur verbatim in `quote`, while snapshot paths are content-addressed `snapshots/<sha256>.webp`.
- `relation`: `eq`, `gt`, `gte`, `lt`, `lte`, `interval`, `in`, `not_in`, or `text`. Numeric values have a unit. An interval value is `{lower,upper,lower_inclusive,upper_inclusive}`. Membership values are non-empty lists of strings. Arbitrary textual requirements use `text` and cannot be mechanically interpreted without a separately validated evaluator.
- `strength`: `required`, `recommended`, `preferred`, `permitted`, `typical`, `example`, or `unspecified`. `preferred` preserves an explicit source preference; `permitted` records permission for the listed value(s) without asserting an exhaustive list. Even with `relation: in`, consumers must not treat an individual permitted or preferred record as a closed whitelist; use the source and independently reviewed scope. `stage`: `submission`, `revision`, `accepted`, `production`, `any`, or `unknown`; `origin`: `journal` or `publisher`. Revision, acceptance and production are distinct stages, never aliases; if a source states a requirement for multiple stages, retain separately scoped facts. Unknown stages and condition text are not equivalent to unconditional requirements.
- `review`: `{status, reviewed?, method?, evidence?}`. Status is `verified`, `pending`, or `rejected`; verified requires `reviewed` and `method`. The HTTP endpoint requires every returned fact to be verified. The publisher must independently verify the review evidence and source text: setting a label is not proof. Empty facts do not imply the source has no requirements.

`coverage` may record a bounded finding that a subject was not stated in a specific inspected scope: each entry is `{id, subject, result:"not_stated", scope, sources:[source_id,...], review}`. Its sources must exist in the bundle and scope must identify the reviewed material; this is not a claim that the subject is absent from the publisher's entire site. Production requires every coverage review to be verified. An empty `facts` list may be published only with at least one independently verified scoped coverage record; a draft may remain empty or pending. The publisher must bind coverage and every cited source-text hash to the independent review evidence just as it does for facts. Missing coverage is unknown, not an implicit not-stated result. Neither the presence of facts nor scoped coverage establishes that all journal requirements have been reviewed; this protocol does not assert whole-journal completeness.

Each fact has one source and a short verbatim quote; do not put full pages or archives in bundles. Repeated subjects, such as image-kind-specific DPI, remain separate records. Origin and condition remain visible rather than applying an implicit publisher-over-journal merge. Consumers must treat conflicting or unrecognized requirements as unresolved. Validation is all-or-nothing, rejects unknown fields, duplicate fact IDs / JSON keys, broken source references, invalid dates and non-finite numbers. The current implementation is a typed storage and transport contract, not proof that the vocabulary can express every possible requirement; unsupported requirements retain evidence as `text` with the relevant condition, and remain non-executable.

The isolated `journalfacts_dpi` experiment does not interpret source `context` or structured membership predicates. Any fact with source context, free-text conditions, or an unsupported predicate remains unknown even when its review status is verified. This conservative behavior does not certify that unqualified facts have authentic sources or independent review, and the experiment is not wired into preflight.

## Legacy and deployment

The v1 endpoint and schema remain unchanged. Do not add a v2 condition to a v1 foldable rule: old clients ignore it and apply the number to every figure. A separately audited v1 projection may contain only unconditional rules it can represent faithfully; publisher inheritance and bundled seeds must be checked independently. Old clients reject v2 index schema; seeded IDs are not automatically replaced by same-ID remote v1 bundles. Existing project snapshots remain unchanged.

The `preferred` and `permitted` strengths were added before the first v2 release. Validators predating these values reject bundles containing them; deploy compatible services, clients and publisher first, then introduce such facts. Never send these facts to an older v2 deployment or fold them into v1.

Deploy behind an explicitly configured `/v2/journal-catalog/` reverse proxy only after a signed verified dataset and a v2 signature-verifying client exist, with staging tests for quota, rollback, old clients, CDN and proxy query preservation. Add v2 to the overseas proxy separately; the v1 proxy configuration does not automatically route it. Keep v1 and v2 caches, revision floors and data roots separate, retain older v2 revisions during rollout, and never publish a pending or rejected fact.

## Client and Agent

Each direct journal-facts read refreshes the public signed index before selecting a cached bundle, so updated requirements are not silently frozen. The index request includes no journal ID or device token. If refresh fails, the response reports `sync_state` / `sync_code` and may return previously verified cached facts; no cache means explicit unavailable. If a journal is absent from a cached index while refresh is offline, disabled or rejected, its existence is unknown: return the sync failure and status, not `unknown_journal`. Only a successfully refreshed signed index can establish that an ID is absent from that index. Clients should send the first page’s `catalog_rev` as `expected_catalog_rev` on each subsequent facts or search page. A mismatch before or during the read fails with `catalog_changed`; the MCP tool reports `journal_catalog_changed` and the client must discard prior pages and restart. When offline, a matching previously verified revision can be paged with the offline status visible. The parameter is optional for compatibility: legacy offset-only clients are not protected against mixing revisions and must compare every returned `catalog_rev` themselves.

`journalfacts_remote` verifies the index using the existing production key authority, checks each on-demand bundle against its signed hash and ID, and verifies every cached or fetched snapshot against its content-addressed name. A separate `journal-catalog-v2/cache.sqlite3` transaction stores the current signed index and enforces a monotonic v2 revision; v1 and v2 share only the existing device token. A missing v2 cache is an explicit unavailable result, never a v1/seed facts response. `TAVOTTO_NO_JOURNAL_SYNC` stops v2 network access as well.

The v2 transport uses the shared platform HTTPS trust but refuses redirects, including redirects to another host, to avoid forwarding a device token. It targets `www.tavotto.com` directly for the overseas endpoint; that route still requires a separately configured and tested website proxy before it is available. On network/server failure it can try the other configured host; on signature, hash, rollback or quota failure it does not switch hosts to hide the error.

The optional MCP tool `tavotto_get_journal_facts` searches the v2 index or reads one journal by ID. Its shared `offset` pages facts followed by coverage; responses include `facts_total`, `coverage_total`, all referenced sources and a `next_offset`; totals count records in the bundle, not complete journal coverage. `catalog_completeness: "unknown"` explicitly reports that whole-journal completeness has not been established, even when some facts or scoped coverage have been verified. Incomplete/unknown conditions remain explicit. This new tool emits no anonymous usage event, so it does not change the telemetry consent scope. Existing preflight and project snapshots remain on v1.
